# stick-fight

A browser fighting game. Stick figures animated at Xiao Xiao quality, lit like a modern 2D game.

## Run

```sh
npm install
npm run dev          # Vite on http://localhost:8077/ (also reachable through the dev tunnel)
npm run dev:worker   # the online-rooms Worker under wrangler dev on :8787 (Vite proxies ./api to it)
npm run typecheck    # tsc over src/, then over worker/
```

Online play needs both: `npm run dev` for the game and `npm run dev:worker` for the room server. Vite forwards `/api/*` (HTTP and WebSocket) to `http://127.0.0.1:8787/stick-fight/api/*`. To run the production layout instead, `npm run build` and then `npx wrangler dev` serves the game at `http://localhost:8787/stick-fight/` with the API beside it.

The game is plain ES modules with canvas 2D for drawing and WebGL for the lighting composite. Vite serves it in development and bundles it for deploys. New modules can be TypeScript (`.ts`) next to the JavaScript ones; `tsconfig.json` has `allowJs` on and `checkJs` off, so add `// @ts-check` to a JS file to type-check it. The demo pages (`demo/*.html`) and the capture tool work against the dev server as before.

## Hosting

The game is a Cloudflare Worker on two zone routes, `askscottpierce.com/stick-fight` and `askscottpierce.com/stick-fight/*`, on the Scott Personal Account. Every other path on askscottpierce.com stays with the main site. `/stick-fight` redirects to `/stick-fight/`, so the page's relative asset paths resolve.

Static files come from the assets binding (`dist/`). The Worker script (`worker/index.ts`) runs first only for `/stick-fight/api/*` (`run_worker_first`), where it serves quick rooms through a Durable Object class `Room` (binding `ROOMS`, migration `v1` with `new_sqlite_classes: ["Room"]`), crew rooms through a second class `Crew` (binding `CREWS`, migration `v2` with `new_sqlite_classes: ["Crew"]`, `worker/crew.ts`), and profiles and email sign-in (`worker/auth.ts`). A request that reaches the script anywhere else gets a 404. The first deploy with the script creates each Durable Object class from its migration. Workers rate limiting bindings cap things per IP (see Multiplayer, Limits): `ROOM_LIMIT` (namespace `7101`, quick rooms), `JOIN_LIMIT` (`7102`, WebSocket joins to either kind of room), `CREW_LIMIT` (`7103`, 5 new crew rooms a minute) and `AUTH_LIMIT` (`7104`, 20 profile and sign-in calls a minute); they're free on every plan, and a namespace id must be unique on the account.

**D1, email and cookies** (for profiles; see Multiplayer, Profiles and sign-in). The D1 database `stick-fight-auth` (id `8a0ea2d9-9d74-466f-a6ff-5a0446d35653`, created 2026-11-08, binding `DB`) holds accounts, hashed sign-in codes, hashed sessions and the send and guess counters; its schema is `migrations/0001_profiles.sql`. The `send_email` binding `EMAIL` sends the sign-in codes from `EMAIL_FROM` (`hey@askscottpierce.com`, a var in `wrangler.jsonc`; Email Sending is already set up for that address on the zone). The only cookie is `sf_session` (HttpOnly, Secure, SameSite=Lax, `Path=/stick-fight` because the origin is shared, 30 days). `.dev.vars` (gitignored) holds `DEV_LOGIN_CODES=1`, which sends no email and returns the code to the page instead, and `DEV_HOOKS=1`, which turns on the crew expiry test route; neither is ever set in production. Locally, apply the schema once with `npx wrangler d1 migrations apply stick-fight-auth --local`. `npm run types:worker` regenerates `worker/worker-configuration.d.ts` after a change to `wrangler.jsonc`.

```sh
npx wrangler d1 migrations apply stick-fight-auth --remote   # once per new migration, before the deploy that needs it
npm run deploy       # vite build into dist/stick-fight/ (file path = URL path), then wrangler deploy
```

**Secrets.** The Worker has two, for Cloudflare Realtime TURN (see Multiplayer): `TURN_KEY_ID`, the id of the TURN key named `stick-fight` on the account, and `TURN_KEY_API_TOKEN`, that key's secret. `GET /stick-fight/api/ice` uses them to mint TURN credentials that expire after an hour. Without them the endpoint answers with public STUN only, which is what local dev gets unless `.dev.vars` (gitignored) holds the same two lines. Secrets persist across deploys. To rotate the key, create a new one and point the Worker at it, then delete the old one:

```sh
# a token with "Calls Write" on the account (the dashboard, or minted with CF_TOKEN_MANAGER)
curl -X POST -H "Authorization: Bearer $CALLS_TOKEN" -H "Content-Type: application/json" \
  https://api.cloudflare.com/client/v4/accounts/0223b96fe77599b23ff8ec7fcd32e2f1/calls/turn_keys \
  -d '{"name":"stick-fight"}' > key.json             # result.uid and result.secret
jq -r .result.uid key.json    | npx wrangler secret put TURN_KEY_ID
jq -r .result.secret key.json | npx wrangler secret put TURN_KEY_API_TOKEN
rm key.json
# then DELETE .../calls/turn_keys/<old uid>; credentials minted from it stop working
```

The same key list is in the dashboard under Realtime, TURN Server. TURN bills $0.05 per GB sent out past the free allowance (the account's first 1,000 GB of Realtime a month, as of 2026-11), and a match's input packets are tiny. Only matches whose phones can't reach each other directly use it.

The places that hard-code the `stick-fight` path are `wrangler.jsonc` (routes, `run_worker_first`), `worker/index.ts` (the API prefix), and `vite.config.ts` (`outDir`, and the dev proxy's rewrite). Vite builds with `base: './'` and the game code uses only relative paths, so it runs the same at `/`, on the dev tunnel and at the subpath. The askscottpierce.com origin is shared by every app on it, so localStorage keys start with `stick-fight-`. The page carries the site's Plausible tag (`data-domain="askscottpierce.com"`), so visits count under the main site by path.

Serving the game publicly ships the vendored Strudel bundle, which is AGPL-3.0, so the game is AGPL-3.0 too (see License and credits).

## Install as an app

The game is installable (`public/manifest.webmanifest`, icons in `public/icons/`, made by rendering a neon fighter on a canvas): it opens full screen in landscape with its own icon.
- **Android and desktop Chrome or Edge:** an INSTALL button appears on the title when the browser offers to install, and runs the browser's own prompt (`src/install.js` keeps the `beforeinstallprompt` event).
- **iPhone and iPad Safari:** Safari has no install prompt and no Fullscreen API, so a home-screen app is the only way to full screen. INSTALL opens a short how-to (Share, then Add to Home Screen). The `apple-mobile-web-app-*` tags make the home-screen app run full screen under a see-through status bar; the touch layer already pads for the safe areas.
- **Installed:** `<html>` gets `.standalone`, and INSTALL and the touch fullscreen button go away.
- **Updates:** every build writes `version.json` (`{ build, at }`, the short git commit plus the build time, from `vite.config.ts`) and bakes the same id into the page as `__BUILD_ID__`. `src/update.js` checks `version.json` 20s after load, every 5 minutes, and when the tab or app comes back; when a newer build is out it offers UPDATE: a button on the title (reachable by controller) and a small NEW VERSION pill on menu screens. Never mid-fight or in an online session (a reload would drop the room). UPDATE asks the service worker to update and reloads.
- **Service worker** (`public/sw.js`, registered on https only and never on `?scene=` test pages): hashed `assets/*` files are cache-first, everything else network-first with the cache as the fallback, so a deploy shows up on the next launch and the installed game plays offline. The room API and other origins are left to the network. Bump `CACHE` in `sw.js` if the cached core list changes.

**Balance pass after faster stamina (2026-11-08).** Faster regen favored the heavy kits: SECURITY won about 70% against TEMP and the INTERN, mostly on jabs and crosses plus the armored Shoulder Check. SECURITY is now health 100 (was 106), regen 0.85 (0.95), damage 0.86 (0.92), and Escort reaches 92 px for 10 damage and 30 stamina (116, 12, 24); COURIER is health 97 (90), weight 0.9 (0.88), regen 1.25 (1.15), damage 1.03 (0.97). Measured at CPU 0.7, 24 matches a pairing: SECURITY 63% v TEMP, 57% v COURIER, 43% v HELPDESK; COURIER 48% v TEMP; INTERN 41% v TEMP, 49% v THE MANAGER.

**Colors in a matchup.** Each character has a main and an alt color (`src/characters/`). P2 switches to its alt when P1 is the same fighter or when the two main colors are close in hue (`colorFor` in `src/characters/registry.js`; INTERN's amber against ACCOUNTANT's yellow read as one color), and to cyan or pink if even the alt clashes. TEMP against TEMP stays white against orange.

## Analytics

Cookieless and with no player ids, names or emails: the page sends small events to its own Worker (`src/analytics.js` → `POST /stick-fight/api/e`), which writes them to Cloudflare **Workers Analytics Engine**, dataset `stick_fight_events` (binding `EVENTS` in `wrangler.jsonc`). Off on `?scene=` pages, on localhost, and when the browser sends Do Not Track. The Worker only accepts a fixed list of event names, cuts labels short, and rate-limits per IP (`EVENT_LIMIT`).

| Event (blob1) | Labels (blob2…) | Number (double1) | Sent by |
|---|---|---|---|
| `visit` | touch or mouse, app or web, referrer host, direct / crew-link / room-link | | page load |
| `install` | | | the browser installed the app |
| `mode` | arcade / horde / training, fighter | | starting a mode |
| `stage` | fighter | stage reached | arcade |
| `arcade_end` | fighter, over / clear | last stage | arcade |
| `horde_end` | fighter | floors cleared | horde |
| `online_match` | host's fighter, guest's fighter, crew / quick | match number | the host, once per match |
| `room_create`, `crew_create` | | | the Worker |
| `crew_match` | host's fighter, guest's fighter, win / draw | | the crew room, per recorded result |

The last blob is the visitor's country (from Cloudflare). Query with the SQL API using a token with **Account Analytics Read**:

```sh
curl -s https://api.cloudflare.com/client/v4/accounts/0223b96fe77599b23ff8ec7fcd32e2f1/analytics_engine/sql \
  -H "Authorization: Bearer $TOKEN" \
  -d "SELECT blob1 AS event, count() AS n FROM stick_fight_events WHERE timestamp > NOW() - INTERVAL '7' DAY GROUP BY event ORDER BY n DESC"
```

For example, favorite fighters: `SELECT blob3 AS fighter, count() AS n FROM stick_fight_events WHERE blob1 = 'mode' GROUP BY fighter ORDER BY n DESC`. Data is kept for three months.

The page also carries the main site's Plausible tag, and Cloudflare Web Analytics (visitor dashboard) can be turned on for askscottpierce.com in the Cloudflare dashboard.

## Arcade flow

Plain `index.html` runs like a cabinet. Everything around a fight is one state machine in `src/flow/index.js`; every move between screens goes through one `go()` that refuses any move not in its transition table, so a double press can't skip a screen.

**Every screen** that waits on the player has at least two buttons you can reach with the keyboard, the pad, a tap or the mouse, opens with the focus on its main action, and shows a footer legend of what each key or button does there (see Controls, Menus). MAIN MENU always means the mode select.

**Title (attract).** Two CPU fighters play one round under the title, with START, HIGH SCORES and CONTROLS buttons and a DEMO tag. Between demo bouts a high score table shows for 7 seconds, like a cabinet's attract loop; the arcade and horde tables take turns. The demo is silent; at most the music keeps playing.

- **Only START starts.** Tap or click the START button, press Enter, Space or A with it focused (it is, when the title opens), or press Start on a gamepad from anywhere on the title. A tap or click anywhere else, and every game key, only wakes the sound (browsers keep a page silent until it's touched). The sound button, its panel and the SOURCE & CREDITS link don't start anything either.
- The START button sits where the title card's prompt is and fades the same way when a fighter is under it; HIGH SCORES and CONTROLS sit in a row under it. CONTROLS is the full fight and menu table, keyboard and gamepad side by side, with MAIN MENU and BACK.

**Mode select.** ARCADE, VERSUS ONLINE, HORDE, TRAINING, and BACK to the title. The mouse hovers and clicks, and a tap picks.

**Character select** (`src/flow/select.js`, the `charSelect` state) comes after every mode. A grid of the registered roster (see Characters), each card a live idle rig in that character's neon, and a sheet for the one under the cursor: a bigger rig that throws one of its unique moves every few seconds, the name and tagline, stat bars (power, speed, health, stamina, weight) and its unique moves with their inputs. Keys, D-pad and stick move the cursor; Enter, A or the PICK button picks; Esc, B or the BACK button goes back. A tap only focuses a card and a second tap picks it, so a stray touch never starts a fight. Arcade goes on to the first stage card, horde straight into the run (the goons stay TEMPs), versus online to HOST and JOIN (your pick rides the handshake), and training asks a second time, PICK YOUR DUMMY. A `?room=CODE` link opens the select first, then JOIN with the code filled in. The cursor starts on your last pick.

**Arcade.** Six stages up the building, best of 3 rounds each, against a named CPU that gets harder and plays its own way (opt-in AI styles in `src/combat/ai.js`). Each stage is a roster character (`char` in `src/flow/ladder.js`); `buildLadder(pick)` makes the run's ladder. You don't fight yourself: a stage whose character you picked is taken by ACCOUNTANT ("read the fine print. then the overhead"), then WINDOW WASHER, in that stage's slot (number, CPU, look, floor). If you pick THE MANAGER, the boss is the HEAD OF SECURITY (SECURITY, "nobody gets past the front desk") and an extra takes SECURITY's stage. A stage whose character isn't built yet fights a TEMP under the stage's own name and color, so the ladder works while the roster fills in.

| Stage | Opponent | CPU | Style | Look |
|---|---|---|---|---|
| 1 | INTERN, "unpaid, and swinging like it" | 2 | the normal scrapper | night with rain, orange-amber |
| 2 | HELPDESK, "have you tried blocking?" | 4 | turtle: guards more, waits at range, punishes whiffs | dry night, cyan |
| 3 | COURIER, "delivers in thirty seconds or less" | 5.5 | rushdown: runs in, swings more, never backs off | the bright neon street, pink |
| 4 | SECURITY, "will escort you out. through the railing" | 7 | grappler: throws up close, hunts the wall and the stairwell | night with rain, green |
| 5 | JANITOR, "works the lower floor" | 8.5 | aerial: jumps in from further out, much more often | the lower floor, violet |
| 6 | THE MANAGER (boss) | 10 | showcase, the expert the demo uses | neon street with rain, red |

The ladder lives in `src/flow/ladder.js`. Each stage opens on a card (STAGE 3, YOU VS COURIER, the tagline, the ladder's pips) with FIGHT and MAIN MENU; FIGHT, a tap on the card, or 3.4 seconds starts the fight. A won match says YOU WIN, then STAGE CLEAR with the stage bonus (NEXT STAGE, MAIN MENU); the boss says BOSS DOWN, then the credits roll (CONTINUE, MAIN MENU) and the score goes to the table. A lost (or drawn) match says YOU LOSE, then **CONTINUE?** with a 10 second countdown and YES / NO: YES retries the stage with the score set back to what it was when the stage started, NO or the countdown running out is GAME OVER (CONTINUE to the initials or the table, MAIN MENU). The stage card, CONTINUE? and GAME OVER ignore back on purpose: B is a kick, and a player mashing through a card mustn't throw away a run or a continue.

**Score** (shown in the HUD after P1's name, with the last bonus next to it):

| For | Points |
|---|---|
| damage you deal | 10 per point of health |
| a hit in a combo | 30 times its place past the first (2nd +30, 3rd +60, ...) |
| counter hit | 200 |
| ender | 500 |
| wall splat, wall bounce, ground bounce | 300 |
| floor break | 1,000 |
| breaking a throw | 300 |
| KO by an ender (FINISH) | 1,000 |
| round won | 1,000, plus 100 per second left on the clock |
| perfect round (no damage taken) | 5,000 more |
| stage clear | 2,000 times the stage number |
| horde: goon down / floor clear | 300 / 2,000 |

**High scores.** A top-5 table for arcade and one for horde, kept in localStorage as `stick-fight-scores` (the origin is shared with the rest of askscottpierce.com). After a game the table has CONTINUE (back to the title) and MAIN MENU; from the title or the attract loop, MAIN MENU and TITLE; either way a third button swaps the arcade and horde tables. The attract loop's table turns over after 7 seconds; one the player opened or just signed waits for 30 idle seconds. A score that makes the table gets three initials: type them, or pick them on the on-screen keyboard (D-pad and A, or tap), then ENTER. DEL (Backspace, pad X) steps back a slot. Left alone for 30 seconds the initials go in as they stand.

**Horde** is the floor-by-floor mode, scored the same way; it ends when the hero goes down, then GAME OVER, initials and the horde table. **Training** is the dummy scene, no score.

**Pause** (P, Esc, pad Start or Select, or the small pause button in the top-left corner on a touch screen) in arcade, horde and training: RESUME, RESTART STAGE (RESTART RUN in horde, RESET in training), BOTCHES ON/OFF, SHOW CONTROLS (swaps the right panel between the techniques found and the fight controls, keyboard and gamepad), MAIN MENU. P, Esc, Backspace, B or Start resumes. Nothing runs while paused, the round clock included.

**Idle.** 30 seconds with no input goes back to the title only where nothing is lost: mode select, the online menu and join screen, the profile screen, the end of a quick-room match, and training. Never the crew lobby (friends wait there), the typing screens, or sign-in (the code takes a trip to the inbox). Never mid-match: an arcade or horde run left alone plays itself out (the CPU or the goons win), CONTINUE runs down, a table score is entered as it stands, and the cabinet is back on the demo. A paused game stays paused. An online match never times out, and neither do the screens between matches in an online room (post-match and NEW CHARACTERS): only a player's own LEAVE ROOM or MAIN MENU, or the other player leaving, ends a room.

**Versus online.** The first time a player goes online (VERSUS ONLINE, a `?room=` link or a `?crew=` link) the game asks for a name first: WHAT DO WE CALL YOU?, 3 to 12 letters, digits and spaces, typed or picked on the on-screen keyboard, with OK, SIGN IN (a returning player on a new device restores the profile instead) and BACK. The online menu has two columns: CREW ROOMS (up to three recent crews by name, focused first when there is one, then CREATE CREW ROOM and JOIN A CREW) and QUICK MATCH (HOST A GAME, focused when there's no crew, and JOIN A GAME), with PROFILE, BACK (to the character select) and MAIN MENU under them. The crew screens, the profile and sign-in are under Multiplayer, Crew rooms and Profiles and sign-in. The quick-match side works as before: HOST A GAME shows the room code, the link (COPY LINK, and SHARE where the phone has a share sheet; both dim until the room is open), WAITING FOR A FRIEND, CANCEL and MAIN MENU. JOIN A GAME takes the code from the keyboard or an on-screen keyboard (tap, mouse, or D-pad and A; DEL is Backspace or pad X); JOIN stays dim, and the focus skips it, until the code is whole. JOINING has CANCEL and MAIN MENU. A `?room=CODE` link opens JOIN with the code filled in. When the match starts the menus go away; Esc, P, pad Start or Select, or the touch LEAVE button opens `online.js`'s LEAVE / STAY confirm (online has no pause), with STAY focused; B, Esc, Backspace or Start again is STAY. When a match ends the room stays open and both players get the post-match screen (below). When a connection ends, or the other player leaves, the notice says why, with ONLINE MENU and MAIN MENU, plus HOST AGAIN or TRY AGAIN when a room didn't open or a join didn't connect. See Multiplayer for the network side.

**After an online match** (the `onlinePost` state) both players see the result (YOU WIN, YOU LOSE or DRAW, the match number, the fighters, the rounds), the room's running tally from their own side in big type (YOU 3 – 2 RIVAL, then the rounds, draws, and the all-time record against this rival when there's more than this room's), and REMATCH, NEW CHARACTERS, LEAVE ROOM and MAIN MENU, with REMATCH focused. The point is to keep a session going with as few presses as possible:

- **Nobody does anything:** REMATCH IN 5 counts down and the next match starts with the same fighters, so a couch session keeps going. Any press from either player (a direction, back, another button) stops it.
- **REMATCH from both** (one press each, in either order), or from the host while the guest hasn't said anything: REMATCH IN 3, then it starts. The host pressing REMATCH again starts it at once. The guest can hold it with back or WAIT, or by choosing NEW CHARACTERS.
- **The guest's choice is a request.** The host's screen says RIVAL WANTS: NEW CHARACTERS and marks that button, and the host's cursor jumps to it (unless the host moved it in the last second; a press within 0.3 s of the jump doesn't count), so one press accepts. The guest's screen says what the host's cursor is on (HOST IS ON: REMATCH) and what the guest asked for.
- **The host's choice is final.** NEW CHARACTERS from the host takes both to the pick screen at once. REMATCH from the host over a guest who asked for something else is the host's call: REMATCH IN 3 that only the host can stop (back or STOP), and the guest's screen says HOST'S CALL. Back, or the STOP button beside the countdown, stops any countdown on the host's side.
- **LEAVE ROOM** goes to the online menu and **MAIN MENU** to the mode select, for either player, at once; the other player gets YOUR RIVAL LEFT (a host's notice then offers HOST AGAIN first: a fresh room in one press). Back on this screen never leaves: it's WAIT for the guest and STOP for the host. STOP or WAIT sits beside the countdown and is dim (and skipped by the focus) while there's no countdown you can stop.

**NEW CHARACTERS** (the `onlineSelect` state) is the character select for both at once, opening on each player's last pick so one press confirms it. Under the title a line reads YOU: PICKING or YOU: READY · COURIER, and RIVAL IS PICKING… INTERN (the rival's card under their cursor, live) or RIVAL READY: INTERN; the rival's card wears a RIVAL tag (green when locked in), and the subtitle carries the match number and the tally. PICK (Enter, A, or a second tap) locks your card in; back un-readies (CHANGE), and never leaves the room. The footer has LEAVE ROOM and PICK, and for the host START. Once both are ready the host's START lights up and STARTING IN 3 runs (START starts at once; either player un-readying stops it). The guest sees WAITING FOR HOST. If the guest hasn't sent anything (no cursor move, no pick) for 20 seconds while the host is ready, START lights up anyway as START · RIVAL: INTERN and starts with the guest's current card: a guest who walked away doesn't hold the room hostage, but the host has to press it; nothing starts without a ready guest on its own.


**Touch.** The stick and the buttons show only while fighting; menus are tapped directly. The sound button stays in the top-right gutter on every screen.

**Swallowed presses.** On every screen change, whatever key or button is held is ignored until it's let go, both by the menus (`menuInput.swallow`) and by the fighter (`input.swallowHeld`), so the press that changed screens never acts on the next one or throws a punch. A round rolling over mid-fight isn't a screen change, so a held guard stays held. STAY on the online confirm swallows its press too.

**`?scene=` URLs skip all of this** and behave as before: the scene they name, no menus, no timeout, and the old hotkeys (G horde, R reset, P pause). `?scene=attract` is the old demo, where any key starts `play`. `__gauntlet.setScene` and `__game.setScene` also turn the flow off, so the capture tool works on plain `index.html` too.

Each demo bout draws a random pair from the registered roster (a mirror match gets the alt color). The demo fighters are the CPU at difficulty 10 in its **showcase** flavor (`sim.setAI(i, 1, { style: 'showcase' })`, `src/combat/ai.js`): it keeps spacing at the edge of reach, steps out of pokes and punishes the whiff, reads and guards highs, mids and lows, opens with string starters at all three heights instead of jabs, blocks rather than mashing out of hitstun, keeps its stamina up (it never presses the strike that would faint it), jumps in and meets jump-ins with an uppercut or a standing guard, and saves the stairwell for later in the round. THE MANAGER fights the same way.

**Anti-airs.** Every CPU decides at your takeoff whether it read the jump: 12% at difficulty 0.3 or below (INTERN mostly gets jumped on, but not always), then rising with difficulty to 80% (0.85 for showcase, +15% for the aerial style). A read drops whatever it was doing, stands its ground until you come into the uppercut's reach about when it would go live, and presses d+2 (a jab instead if you're already on top of it with a strike out); a jump that will land short is let land. A CPU that doesn't read it still has the old once-per-jump uppercut reflex.

**Stamina and faints.** No CPU presses the strike that would empty its bar, except that the bottom of the ladder slips now and then ((1 - difficulty) x 40% of the times it would, never the showcase), so INTERN and HELPDESK faint a round or so and THE MANAGER doesn't. A CPU under about 30 stamina backs off or guards while it refills, and only starts a string's ender when the rest of the string fits in the bar. When you faint it runs in and opens a string on you: 35% plus 65% of its difficulty of the time, every time for the showcase.

## Controls

Tekken-style, one button per limb, from the fighter's own point of view:

| Key | Button | Limb |
|---|---|---|
| U | 1 | left punch (jab) |
| I | 2 | right punch (cross) |
| J | 3 | left kick |
| K | 4 | right kick (roundhouse) |

- **Move** A/D or arrows. **Hold back** (away from the opponent) to step back, Tekken style: you walk back (at the character's back-walk speed; TEMP's is the forward walk's) and the guard snaps on by itself only when a strike is coming that can reach you (one in startup or out, inside its reach plus any slide or charge travel plus a little, about to go live) or a jump-in is closing. It holds through blockstun and a beat after, then you're walking back again. Standing guard stops highs and mids, lows go under it (and don't make you snap: down-back is the answer), and throws beat it. A hit that lands while you hold back in a guard-capable state (walking back, idle, crouching back) is blocked even if the snap missed a frame. B, and the touch GUARD button, mean the same as holding back, so they walk back too. Walking back costs no stamina; blocking costs what it always did, and the guarding regen rate applies only while actually blocking.
- **Crouch** S or down. A crouch ducks highs completely; **down-back** guards lows. Mids hit a croucher.
- **Jump** W, **run** Shift (or double-tap forward). **Throw** 1+3 or 2+4; the same press during the grab breaks a throw. Throws can't be guarded, but they whiff on a croucher.
- **In the air:** jump with W (hold a direction for a forward or back jump; you can steer a little in the air), then 1 jump jab, 2 jump cross, 3 flying kick, 4 air roundhouse (knockdown), down+4 dive kick (cuts the jump short). One air attack per jump. Air attacks are overheads: they hit a croucher, so guard them standing. Land a jump-in hit and keep pressing for a ground string; whiff one and you land with a short lag. An uppercut (d+2, or rising 2) meeting a jump-in is a counter hit that launches; a jab stuffs a late one. In the rig an air attack eases its hip onto the jump's arc over its startup (and a dive kick never climbs the arc, it drops from where it was). Its homing lunge (up to 70px toward the defender) and torso swing don't land in the 50ms pre-roll the sim skips: the head travels in a straight line, evenly over the frames from the press to the moment the strike can hit, and the hips carry the difference; from then on, and at contact, the body is exactly where it was before. The jump's push-off is drawn with softer eases than the arc air attacks ride, so takeoff has no big frame. Leaving the air for anything grounded lowers the hip over 160ms (220 after a dive) instead of in one frame; a strike thrown on landing finishes that descent by its contact key, so it lands at standing height. Where the head still has to travel farther than 20px in one frame to make contact (a jump jab or dive kick from far out, a landing push-apart, the stairwell vault and its handoff to standing), `drawOffset()` in `src/main.js` holds the drawing to 20px per 60fps frame and lets it catch up. It's visual only: hit detection, contact and the netcode state use the real positions. A connecting strike snaps the drawing to the real pose on the contact frame, under the impact flash, so hits always draw touching. Launched, thrown and juggled bodies draw raw. On the ground the same idea is `frameDraw()`'s turnaround and snap fade (Controls, Sides).
- **Crouching:** all four crouch attacks come out of a crouch or a crouch-walk (hold down and forward) without standing up, and you stay down after a low while down is held. d+1, d+1, d+3 is the Low Rush string. On touch, stick down plus a button.
- **Directions:** d+1 low jab, d+2 uppercut (launcher), d+3 low kick, d+4 sweep, f+1 body blow, f+2 lunge cross, f+4 overhead (mid, beats crouch), b+4 spin kick. Release down, then 2 = rising uppercut, 4 = rising knee (both launch).
- **Heights:** high = jab, cross, roundhouse, spin kick, spin heel. Low = low jab, low kick, sweep. Everything else is mid.
- **Stamina** (the thin bar under health, out of 100) is your attack budget. Jab 17, low jab 15, cross 21, body blow 19, lunge cross 22, low kick 18, the other kicks 22, launchers 24, throws 22, any ender 30; air attacks 12 to 18, a jump 8, running 14 a second (running stops at the last point, it never faints you). Mashing jab empties it on the 6th press, crosses and kicks on the 5th. A full four-hit string fits from full but leaves you low (1,1,2,4 costs 85, 1,2,3,4 costs 90, Sky Spike 92). It comes back at 90 a second once you've gone 0.3s without spending (none while attacking or running), and at 36 a second while guarding, so it refills in about a second of walking. **Knocked down, it refills to the top:** the bar fills (with a white flash on the bar and the overhead track) the moment you hit the floor, from a hit, a throw, a trip, a floor break or a stair tumble, and a faint ends there too. Blocking a hit costs a third of its price and never takes the last point. Under 35 the bar turns pink and flashes LOW.
- **Sides:** you keep your side of the opponent, and sides only change through motion you can see. Classic 2D fighters work the same way: solid pushboxes that always resolve toward each body's own side, jumps that cross over, specific throws and moves that visibly carry someone past, and a turn when facing flips. Here:
  - **Bodies are solid and push back toward their own side.** When two standing bodies overlap, each is pushed back toward the side it was on when the step began (`separatePair()` goes by `prevX`, a pushbox), so a lunge, a glide or a slide into someone never comes out the far side. A body is moved at most 6px a step by the pushing apart (`SEP_CAP`, 720 px/s), so a deep overlap (a getup turning solid under someone at the wall, a landing on top of someone, a body coming to rest past the man standing over it) is a visible shove over a few frames, never one snap.
  - **The root goes where the body is.** A travelling clip (a cross's step, a stagger, the getup's rise, a botch's stumble, the vault) moves the rig's root when it ends or is cut short; the sim's root follows it the same step (`takeRoot()` after every rig update, and `safePlay()` around every `play()`), so the drawn body never jumps back by the step. The getup used to stand the fighter up at his old root, a body-length from where his hip lay, often on the far side of the man standing over his legs: that was most of the "teleports". Now he stands up where his hip is, on his own side. A body getting up isn't slid along the floor (its feet may be past the wall, its hip never is), and a body coming to rest from a tumble keeps the root and facing the rig gave it (a clamped root or the old facing re-posed it a body-length away).
  - **Lying bodies.** You can stand over a body on the floor (and step farther in under a juggled one), but you can't walk, run or lunge out the far side of it, and a body rolling or sliding along the floor stops under you. A body getting up rises on its own side, because a standing fighter can only reach a little way onto it. Sides and facing go by where a lying body actually is (its hip), since its root sits at its feet. After a knockdown the attacker's ride (he follows the launch to be on the body when it lands) stops at the body's near end, a string's chase step stops at contact, and a body getting up is pushed apart by the sides the two had. A body against the wall slides off it (300 px/s), and a rolling one stops against that pad instead of being thrown out of it.
  - **What still changes sides:** jump cross-ups (a real arc over him), launches and juggles that carry the body over, a floor break and the follow-down vault, a roll, Window Washer's double jump and wall jump, Janitor's Mop Spin landing behind him (`bothSides`), and a body sliding under a standing fighter. Hits knock the defender away from the attacker, not the way the attacker faces, and a roll faces the opponent. A throw holds the victim 70px in front: he is pulled there at 720 px/s over the grab's first frames (`grabTo`), never put there, and one caught behind the thrower turns the thrower round instead of passing through him.
  - **How it reads on screen** (`frameDraw()` in `src/main.js`, visual only: hit detection, contact and the netcode's state keep the real pose). A grounded fighter whose facing flips is drawn turning on his feet over 100ms, squashed horizontally about his root from the old facing through zero to the new one, instead of mirroring in place. Anything that would still move the drawn body farther than 18px in one frame, far more than it moved the frame before (a lying body re-posed for a roll, a knockdown clip snapped to its landing), is cross-faded from where it was drawn over 110ms, relative to the root so the root's own motion passes straight through. Launched, thrown, falling and ragdoll bodies draw raw, air moves keep `drawOffset()`'s catch-up, and both end on a hit's contact frame, so hits still draw touching. The one instant relocation left in a fight, a body jammed in the stairwell set down on the floor (`unwedge()`, the `relocate` event), leaves an afterimage where the body was and a flash at both spots.
  - **Measured** with a logger (40 CPU fights across all nine characters, three seeds by 90s each, plus the attract showcase, horde-ai, horde-floors-ai and floor-break-test; drawn head and hip per 60fps frame after the smoothing, side swaps by `bodyX()`, every write to a unit's `x` trapped with its stack): see Characters, **Measurements (side swaps)**.
  - Each fighter's walls come from the floor he's on, so after a floor break the attacker upstairs isn't pulled across to the lower floor's wall before he vaults.
- **Faint:** spend the last point and you faint. The strike that emptied the bar still comes out, but nothing cancels out of it; once you're back on your feet you're out on them for 1.5s (the dizzy sway, a FAINT callout and a violet bar refilling): no attacks, no guard, no crouch, no jump, and you stagger at a third of walking speed. You come to with 30 stamina. A knockdown, a launch or a throw wakes you early, and so does taking 20 damage while fainted, so it's a free string for the other guy, not a free round. Every hit on a fainted body counts in the same combo, so the decay below keeps running through it.
- **Combo decay:** nothing loops. A button press cancels only as the next hit of a string from the table below, so mashing one button gives you that button's string and then you wait out the recovery (1,1,1 is three jabs; a fourth jab can't cancel out of the third). A move cancels into itself at most once in a row outside a string. Hitstun shrinks from the 3rd hit of a combo (100, 100, 85, 65, 45, then 30%), so a long chain drops and the defender can guard. Damage is full for the first three hits, then 80, 65 and 50%, and once one combo has done 30 damage the rest counts a quarter. Juggles keep their own scaling and the four-hit cap, whichever is lower. Counter hits still do 35% more damage and stun.
- P or Esc pauses (the pause menu, see Arcade flow), F1 shows the move list, H shows hitboxes. On a `?scene=` page G toggles horde mode, R resets and P just pauses.
- **Online match:** Esc or P (pad Start or Select, touch LEAVE in the top-right gutter, where HORDE usually sits) asks whether to leave. Pause, reset, horde and the difficulty keys do nothing in an online match; H and F1 still work, since they only change your own screen.
- **Sound:** M turns the music on and off, N skips to the next track. The speaker button in the bottom-left corner (on a phone, the speaker button in the touch layer's top-right gutter) opens the sound panel: a SOUND switch for everything, a MUSIC switch, the track playing with NEXT, and MUSIC and EFFECTS volume sliders. The settings are remembered in localStorage (`stickfight-audio`). Browsers keep a page silent until it's touched, so the first tap or key starts the sound (the button pulses until then).
- Gamepad, USB or Bluetooth (any pad the browser reports with the standard mapping: Xbox, PlayStation, 8BitDo, most Android pads): X/Y/A/B = 1/2/3/4, D-pad or left stick moves, L1/L2 guard, R1 throw (1+3), R2 run, Start or Select pause (in an online match, both ask to leave). R3 does nothing in the arcade flow. On a `?scene=` page Select restarts and R3 toggles horde. Menus are in the table below. Pressing any button hides the touch controls; touching the screen brings them back. Browsers don't count a pad press as a user gesture, so tap the screen once to turn the sound on.
- Touch devices get a floating stick (down crouches, away walks back and guards what's coming) and a 2x2 diamond of arcade buttons in the same 1 2 / 3 4 layout plus GUARD (src/touch.js).

### HUD

The fight HUD is its own 2D canvas over the game (`src/combat/hud.js`), in the arena's neon (Bungee and Teko, glow, no terminal look). Nothing on it may cover a live fighter (owner requirement 5): every block is laid out against the fighters' screen boxes and steps aside or fades.

- **The bars.** Two slanted health bars with a thin stamina bar under each (it flashes pink with LOW under 35, and shows FAINT while fainted), round pips at the inner end, and the ringed timer with ROUND under it. In an online fight the room's running tally shows small under ROUND, from your side on both screens: `YOU 3–2 RIVAL` (plus draws when there are any), from `flow.hud().tally`; it fades if a fighter is under it.
- **Name line.** The character's name in its own neon, then a small player marker: YOU or RIVAL online, P1 or P2 for a local player, CPU 7 for the computer at difficulty 7, TRAINER for a test scene's script, the stage (STAGE 3, BOSS) in the arcade ladder. The arcade score sits after it.
- **Move hints.** The line under the name cycles through that character's special moves every 3.6 seconds, input first in amber and then the name: `→→3 EXPRESS SLIDE`, `←2 SHOULDER CHECK`, `↓3, 3, 2 WRITE-OFF`, `1, 2, 3, 4 NEON TORNADO`. It reads the character's `moveList` (src/characters/), so a new character's moves show up with no HUD change. Arrows follow the move lists: → is forward, toward the opponent. Both bars show their own fighter's moves, so it teaches the matchup too. A keyboard screen adds the move list's short note; a touch screen (`touch-ui`) shows just the input and the name, bigger. Happy accidents appear only once this browser has found them (`discovered()` in `src/flow/techniques.js`, read only), as `3 › 4 SCISSOR KICK` in the accident green, and only for a character who can do them.
- **Overhead status track.** A compact readout over each fighter's head (the hero and the one he's on in horde), so you can read the fight without looking at the corners. Only what's active shows, top line first:
  - STUN (hitstun) with a red bar that drains to the middle as the stun runs out; GUARD (blockstun) with a cyan one; GUARD or LOW GUARD, dimmer, while the guard is up; FAINT with a violet bar and two stars chasing round the word; DOWN (or TANGLED after an air botch) while knocked down, GET UP with a filling bar; BOTCH during a botch; ARMOR while Security's shoulder check still has its armor; PARRY while Helpdesk's stance is live; OPEN during a whiffed strike's recovery (punish it).
  - Flashes for half a second: COUNTER on the fighter who ate a counter hit, ARMOR when the armor absorbs one, PARRY when the stance catches one.
  - A thin stamina bar under it once any stamina is spent (amber, pink and flashing under 35, violet while fainted); it lingers a beat after refilling and then goes, so an idle fighter shows nothing.
  - Diamond pips for the air jumps left while a Window Washer is in the air.
  - It sits above the head, slides sideways off the other fighter, clamps on screen below the hint line, moves beside the head when a jump takes it to the top, and fades to a ghost when it has nowhere clear to go. The callouts step around it. It maps through `camera.mirror`, so the `?mirror=1` debug view still lines up.
- **Callouts and the hit counter** stack on the attacker's side under the hint line, else the other side, else the middle; banners (FIGHT, KO) take the first free slot. A happy accident found for the first time gets TECHNIQUE FOUND under them.
- **On the bodies** (`src/fx/status.js`, drawn on the FX emissive layer, which the compositor hides wherever a fighter is, so these show only as rims and glints around them): a red halo and red light in hitstun that fade as the stun drains; a dashed cyan shimmer arc in front of a raised guard (brighter in blockstun); stars circling the head and a wobbling violet ring while fainted; an amber halo while armored and a flare when it absorbs; a white-cyan shield ring in front of a parry stance; a hot white halo and a harder body flash on a counter hit; a cyan ring kicked out under the feet when an air jump is spent; breath puffs under 35 stamina, plus sweat flicks and steam when nearly empty or fainted; a gold glint over the head when a happy accident lands. Tier 1 (`?tier=1`) drops the sweat, steam and the halos' outer pass.
- The HUD and the status effects only read the sim (and its events, forwarded by `main.js` through `hud.event` and `statusFX.event`); they never write to it, so the sim stays deterministic.

### Botches and happy accidents

Mashing doesn't just wait in the buffer any more. A strike pressed in the middle of another one, before that one is allowed to finish, fights it for the same body, and the fighter messes up.

**The rule.** Everything that legally carries on from a strike behaves exactly as before: a string's next press, a listed cancel (a move the CPU names), a throw pressed a frame after a jab or kick (1, then 3 a beat late), any press after a launch, knockdown or stomp connected (their recovery is cut short for the follow-up), any press while your juggle is in the air or on the wall, and anything in the last 8 steps (about 4 frames) of the recovery, which still buffers into the next move. Any other strike pressed during the startup, the active frames or the rest of the recovery is **mistimed** and botches. Throws, specials and character moves follow the same rule; holding a direction, guarding, jumping and moving never botch. In the air you still get one air attack per jump, and a second one pressed while the first is still swinging tangles you up (after it connects, or just before you land, it buffers for the landing like before). A tangled fighter loses his presses until he's back.

**What happens comes from the forces involved.** The sim measures the strike that was out (which limb, which way it turns the body, startup, active or recovery, how fast the hips and the striking limb were moving, the lean, a glide or a lunge under it) against what the new press wants (its limb, its height, forward or not), and that picks one of five families:

| Family | Callout | Typical cause | What it looks like |
|---|---|---|---|
| Overbalance | OVERBALANCED | a forward strike on top of a lunge, a glide or a deep lean | lurches forward and catches himself with two steps, open the whole time |
| Spin-out | SPUN OUT | the body still turning one way (a spin kick, a rear-side strike) while the new strike turns it the other | the turn carries him round until his back is to you, a stooped beat, then round again; a hit while his back is turned is a counter |
| Trip | TRIPPED | a kick on top of a kick (worst with the same leg still up), a low on a kick | the feet cross and he goes down: a self-knockdown on the point simulation, then the usual getup |
| Flail | FLAIL | both arms at once | a weak, ugly double swing (it can touch, 2 to 3 damage, but never extends a combo) and he hangs there blowing |
| Whiff | WHIFF | the first strike mostly done | the new limb shoots out half-formed and hangs there, a long recovery |

A second air attack mid-swing is **TANGLED**: the body tumbles out of the air and lands in a heap. Every botch costs stamina (8 + 0.6 of the new move's price, more for two kicks, an ender under it or a harder botch, most for a flail; 20 to 40 in practice), and a botch with under 30 left empties the bar: he faints standing (never a trip, since a knockdown would wake him).

None of it is a canned animation. Each family is built on the spot from those numbers and the pose the body is in (`play('botch', { botch })` in `src/fighter/index.js`): play() blends into it from the current pose carried forward by its momentum, the trip and the tangle hand the body to the point simulation (`launch`), and the flail is a real, weak strike. Positions never teleport: a stumble's travel stops short of the other body and the wall, the root takes the step when the clip ends (or when a hit cuts it short), bodies stay solid, and sides follow the usual rules.

**Unpredictable, but the same every time.** The family comes from the forces, quantized to small integers (hip speed in 40 px/s steps, limb speed in 100 px/s steps, the lean in 5 degree steps, the phase), plus one draw from `sim.rng` for variety. That makes a botch feel random but exactly reproducible from the same state, which is what lets a player find the techniques, and it keeps rollback and every browser engine bit-identical. The new per-fighter state is plain unit fields (`botchKind`, `botchSev`, `botchShift`, `botchFwd`, `botchAt`, `activeAt`, `recoverAt`), which the snapshot copies; the generated clips ride the rig's `getState()` like any move. `NET_VERSION` is 7.

**Happy accidents.** A few presses that would botch, landing in a narrow window of a particular strike, come out as a hidden technique instead, with a HAPPY ACCIDENT callout: SCISSOR KICK, SUPERMAN PUNCH, PIVOT BACKFIST, FLASH KICK, HELICOPTER, FLYING TACKLE, CROSS KNEE and SPRING UPPERCUT. Everyone has all eight. They're strong (14 to 16 damage, launches, a wall splat, an unblockable tackle) and risky (long recoveries, little blockstun). They aren't in the move list until you find one; then the F1 move list shows it, the pause menu lists all eight as TECHNIQUES FOUND 3/8 (the rest as ???, each with a hint), and the character select shows the count. What you've found is kept in localStorage as `stick-fight-techniques`. A window's step count runs on the strike's own clock, so a hit's freeze holds it.

*Developer note:* the exact windows (which strike, which press, which steps) live in `ACCIDENTS` in `src/combat/botch.js`, and `?scene=accident-test` shows each one landing and the same press a step early and a step late botching instead. They're kept out of this section on purpose.

**The CPU.** It mostly holds a press that would botch until it's clean. The lower its difficulty, the more often it lets one go and mashes a button mid-strike on its own (about a third of strikes at INTERN's 0.2, a few percent at 0.7, never at 1.0 or for the showcase), so the bottom of the ladder shows the system off. Every CPU punishes a botch it sees, the better ones more often. The showcase (the attract demo and THE MANAGER) never botches but now and then presses into a technique's window for flavor.

**The switch.** On by default. BOTCHES: ON/OFF in the pause menu (from the next fight; kept in localStorage as `stick-fight-botch`), or `?botch=0` on the URL (`?botch=1` forces it on). Online, the host's setting rides the start message, so both sims play the same rules. With botches off the game is bit-for-bit the old one.

**Measurements.** Mashers against a TEMP CPU, three matches each, before and after: random mashing dealt 404 and 333 damage (CPU 0.3 and 0.7) before, 108 and 96 after, best combo 5 and 7 before, 1 and 3 after, and spent 39% and 50% of the fight open (botching, fainted or on the floor) before, 64% and 62% after. Mashing 1 alone dealt 444 and 406 before, 347 and 272 after (average combo 2.8 to 2.1 and 2.7 to 1.6). Every scripted scene (combo-test, string-test, scripted-combo, string-ender-test, jump-in-test, anti-air-test, wall-test, juggle-test, floor-break-test, guard-test, mixup-test, trade-test, throw-test and the eight character tests) gives the same max combos, callouts and damage as before; with botches off all 96 phases have the same per-step state hash as the build before botches. stamina-test, which is literally spam on a guard, now botches. Three test scripts pressed every few steps regardless of their own strike (floor-break-test's chase, helpdesk-test's and janitor-test's punishers); those presses were already thrown away by the buffer, and they now skip a press that would botch. CPU vs CPU at 0.7, 40 matches a pairing with sides swapped, rounds won before and after: TEMP v TEMP 46-51 / 54-47, TEMP v COURIER 60-34 / 55-45, SECURITY v HELPDESK 52-46 / 53-42, MANAGER v INTERN 56-44 / 61-39, JANITOR v WINDOW WASHER 59-43 / 60-41, ACCOUNTANT v TEMP 68-33 / 59-47 (inside the 10-point swing of the sample), with 1.5 to 3 botches a match. The attract demo shows no botches and a happy accident every few minutes. Save/restore: six recorded CPU bouts with botches and accidents (9,000 steps each, inputs, the rng state after each CPU call and `grabId`, `rollId`, `aaJump` recorded) replayed identically, then took 1,037 rollbacks of 1 to 16 steps (save, run, restore, run, restore, run), with save points inside botches and accidents: all 26,397 restored steps matched the reference's deep hash of `saveState()`; clearing `botchKind` or nudging `botchShift` on restore made it differ on the first step. The same bouts plus botch-test and accident-test hash identically on every step in Chromium, Firefox and WebKit.

### Floors

- **The building** is a cutaway of two office floors (3 and 2 on the elevator's indicators) joined by a stairwell. Each floor's floor is a wet plane running from the back wall (the line fighters stand on) forward to the cut edge, then the concrete slab cut through, and the slab's underside is the ceiling of the floor below. The stairwell is a hole through the main floor's plane and slab; the guard rail is fixed to its far lip, with its end posts on the solid floor either side, and the first flight runs down through the hole to a landing that bears on the stair shaft's wall, then switches back to the lower floor. Everything in the rooms stands on a floor, hangs from a ceiling or is mounted on a wall, the floor's mirror stops at the walls and at the hole, and the only thing in front of the cut is the street lamp outside, whose pole runs down to the street.
- **Floor break:** an ender, a throw, a launcher or a heavy knockback that carries someone over the stairwell railing (the opening in the main floor, right of the vending machine) sends him tumbling down the stairs to the lower floor: a FLOOR BREAK callout and 10 extra damage on landing. The attacker vaults the rail after him and the fight goes on downstairs, with that floor's walls. Once per round; the lower floor has no way down. The next round starts upstairs.
- The tumble is a ragdoll, and now and then it jams: in the opening above the slab (the body is longer than the opening is wide) or resting on a stair tread. A jam in the opening gets a straight push down; a fall that stops making headway for 0.9s, or runs past 3s, is set down flat on the lower floor (and any ragdoll still up after 5s is set down on its floor). An attacker on the far side of the opening, pinned by the lower floor's walls before he reaches the rail, vaults from where he stands.
- **Never stranded on two floors:** nobody can climb the stairs back up, so the attacker vaults down after a floor break, from his feet (a vault begun in the air used to be cancelled by the landing and left him upstairs for the rest of the round). As a safety net, whenever the two fighters have been on different floors for 1.5s with neither falling nor vaulting, whoever is upstairs runs to the railing and vaults down (`regroup()` in `src/combat/sim.js`; not in horde, where floors are the point).
- **Horde, floor by floor:** each floor sends a wave of 5 to 8 goons through its doors (two at a time from the third). Clear it for FLOOR CLEAR, and the hero vaults down to the next floor; after the lowest floor the run loops back to the top. The bodies stay on the floor where they fell, except that none rests over the stairwell's opening: one that would lie across the hole slides off to the nearer lip as it settles (`arena.addBody`). The HUD tracks the floor, the wave and the goons downed.

### Adding a character

Replace your character's file in `src/characters/` with a default export like `courier.js` and `security.js`. Nothing else needs editing unless you need a mechanic no hook covers. Then add a generic hook in `src/combat/sim.js`, read from frame data or `mechanics`, and document it here. The definition:

- `id` (the file's name: `intern`, `helpdesk`, `janitor`, `manager`, `accountant`, `windowWasher`), `name` (caps, on the HUD and the select screen), `tagline`.
- `color` (the body's neon), `altColor` (P2 in a mirror match), `accent` (the accessory and highlights). Neon arcade only: no monospace, no terminal look.
- `stats`, each relative to TEMP (all default 1 except health): `health` (out of 100), `walk`, `backWalk` (a share of the walk), `run`, `jump`, `dash` (multiplies every `travel`), `weight` (knockback taken: x by 1/weight, y by 1/sqrt(weight)), `stamina` (the bar's size), `regen`, `damage` (every hit he lands).
- `body`, for the rig (`createFighter({ body })`, `rig.setBody`): `scale`, `headR`, `upperArm`, `lowerArm`, `upperLeg`, `lowerLeg`, `lowerTorso`, `upperTorso`, `limbW`, `limbTip`, `torsoW`, `hipW` (defaults in `RIG`, `src/fighter/index.js`), `lean` (degrees of extra forward pitch), `stance` (degrees each leg spreads), and `accessory(ctx, joints, { scale, facing, color, accent, headR })`: a few strokes drawn over the head on the figures layer, so it's lit like the body. Hit and hurt radii and the contact surface scale with `scale` and the limb and torso widths, and a walk or run cycle plays at the rate that keeps feet planted at the character's speed. Watch the reach: a longer arm or a thicker fist wins the poke game outright (SECURITY's first build won three rounds in four on jabs and crosses alone).
- `moves`: `{ name: { rig, frame } }`. Names are global: never reuse a shared or another character's name (registration throws). `rig` is a clip in the `MOVE_DEFS` format, built with `RIG_KIT` from `src/fighter/index.js`: `K(pose, ms, ease, ev)`, the IK helpers `F`, `L`, `leg`, the guard feet and hip `LF`, `RF`, `HIP`, the crouch `crouchP` and `CH`, and `base(name)` with `deepKeys` to start from a shared clip. A clip has `blend`, `limb` (the joint that carries the hitbox: `lHand`, `rHand`, `lFoot`, `rFoot`, `lKnee`, `rKnee`, `lElbow`, `rElbow`; button 1 is the lead hand, 2 the rear, 3 the lead foot, 4 the rear), `keys` with one `'active'` key (more for a multi-hit) and a `'recover'` key (the cancel window runs from it), and optionally `shift` (root travel when it ends), `air`, `chainFrom`. `frame` is a `FRAME_DATA` entry (`src/combat/frameData.js`; `addFrameData` fills what's left out): `limb` ('hand' or 'foot', for its radius), `damage`, `kb`, `hitstun`, `blockstun`, `hitstop`, `knockdown`, `height` ('high', 'mid', 'low', 'overhead', 'throw'), `cost`, `cancels`, `reach`, `flashR`, `juggle`, `splat`, `groundBounce`, `ender`, `callout`, `tc`, `react` (a reaction clip), and the hooks below. A frame-only entry (no `rig`) plays another clip through `anims: ['clip']` (SAME DAY's ender plays the slide).
- `commands`: `{ button, motion, move }`. Buttons '1' to '4', '1+3', '2+4'; motions '' (neutral), 'f', 'b', 'd', 'df', 'db', 'ff' (dashing: running or just after), 'run', 'rise' (released down), 'air', 'airDown'. A command replaces the shared move for that button and motion, and the most specific motion wins. A string continuation still beats a command.
- `strings`: `{ drop: ['SKY SPIKE'], add: [{ name, keys, moves }] }`. Keys are tokens ('1'..'4', 'd1'..'d4'; after the first, a plain token also matches its down variant), moves the move for each press, the last being the ender. Strings that share a prefix must agree on its moves. Registration warns about conflicts, including a sequence that collides through the down variant (1, 2, d3 is UPTOWN).
- `mechanics`: `airJumps` (extra jumps on a fresh jump press in the air; each refreshes the air attack), `wallJump` (a jump press within 34 px of a wall kicks off it, at most twice a jump), `airJumpClip` (the clip a double jump plays, 'jump' by default; its own clip gets the jump's landing beat too). After an air jump or a wall jump, an air attack doesn't home on the body (from that height the homing swung the leg back under him and lunged the hips past the defender), it connects only once the drawn limb touches the drawn body (2 px), and seating it never slides the defender under the attacker and out the far side.
- `ai`: `style` (the CPU's default personality: null, 'turtle', 'rushdown', 'grappler', 'aerial'; an arcade stage's or the demo's style wins) and `specials`: `{ move, min, max, when, chance, run, cooldown }`. In range [min, max] px and when `when` holds (a function `(me, opp, sim, dist)`, or 'standing', 'crouching', 'guarding', 'attacking', 'whiff', 'wall', 'far'), it's pressed with that chance (scaled by difficulty); a little short of range it walks in (runs with `run: true`). The CPU also runs the character's own strings through its usual string logic. A special can carry `plan(me, opp, sim, dist, toward, kit)` instead of a single move (then `name` keys its cooldown and `cost` is the stamina it needs): it returns the CPU's own list of acts, built with the kit (`move`, `attack`, `press`, `blockFor`, `closer`, `landed`, `chance`), for what one press can't do: a jump, a second jump, a wall jump, a press of a token so a string carries on (WINDOW WASHER's and INTERN's files are the examples). An act's `until` and `onlyIf` see `(me, opp)` every step, so a plan can react mid-air.
- `moveList`: `{ name, input, note }` for the select screen (arrows and digits, e.g. '→→ 3').

**Hooks** (frame data fields the sim reads, `src/combat/sim.js`):
- `travel: { vx, at, ms }`: the body glides vx px/s (x the dash stat) from `at` ms into the clip for `ms`, stopping at the body.
- `armor: { hits, dmg }`: absorbs that many hits from the press until recovery, taking `dmg` of each (0.5 by default), with an ARMOR callout. Throws still take him.
- `parry: { heights, reversal, stun, callout }` (HELPDESK's counter stance): a strike of one of those heights (high and mid by default; never a throw or an air attack) landing in the move's startup or active frames is caught. The striker reels for `stun` frames (40 by default), PARRY (or the callout) pops, and the stance turns into the `reversal` move, which then hits the ordinary way. The stance itself never strikes (its own frame data is never tested as a hit), anything the parrying side had buffered or queued is dropped, and the reversal's step-in glide or `travel` waits out the parry's freeze instead of running down during it.
- `bothSides: true` (JANITOR's Mop Spin): the strike can land behind him. A hit sends the body the way the striking limb points from his root (not toward his facing), it seats on the body on that side, a hit behind makes that his side of her for the side-keeping rule (`home`), and the move is never re-aimed at a jumper or a juggled body, so the spin keeps its shape.
- `throw: true, grab: true, range, hold, noBreak` (a command grab): range px at the press, held `hold` frames, `noBreak` refuses the 1+3 break; `unblockable`, `splat` and the stairwell toss work as on a throw.
- `hits: n` (MANAGER's multi-hit): each later `'active'` key in the clip may connect again, up to n hits. `hitKey` (a unit field) counts the active keys; the first one never re-opens, since a strike can already land in the 45 ms before its key. `rush: { ... }` holds frame data fields for every hit but the last (PERFORMANCE REVIEW's hooks: light, no knockdown, `ender: false, callout: null`); the hit on the last active key is the move itself, so only it knocks down, calls out and scores as an ender. A blocked earlier hit doesn't bounce the attacker off (the rest still meet the guard). Every hit counts in the combo, so the decay and the soft cap apply hit by hit.
- A character's own move that opens one of its strings, named directly by the CPU (`ai.specials`), starts that string from its first key, the way a shared move starts one from its button (ACCOUNTANT's Fine Print).
- `height: 'overhead'`: a mid (a crouch can't duck or low-guard it, a standing guard holds) flagged as an overhead for the CPU and the move list.
- `lowInvuln: true`: lows pass under it from the press until recovery (a hop, a flying knee).
- `wallBounce: true`: near a wall the body bounces off it into a juggle (like WALL SPIN).
- `owner` (set by registration): only that character can press it, by button or by the CPU naming it.

The CPU's reach comes from measuring each character's clips on its own rig (`sim.reachOf(unit, move)`, keyed `id:move`), so a new body needs nothing extra. Rollback needs nothing extra either, as long as new per-fighter state lives in plain unit fields (the snapshot copies every one; `armorLeft`, `hitN`, `airJumpsUsed`, `wallJumps` and the travel `glide` are examples) and any math the sim depends on uses `src/combat/dmath.js` (drawing code like an accessory may use `Math`). A new sim field that isn't on a unit belongs in `SIM_SCALARS` in `src/combat/snapshot.js`. Test it the way courier-test and security-test do: a phase per unique move in `PHASES` in `src/main.js`, with the character as P1 in `SCENE_CHARS`.

## Multiplayer

Two players, each on their own phone or computer, fight online. One hosts a room and gets a four-character code and a share link (`https://askscottpierce.com/stick-fight/?room=K7QX`); the other opens the link or types the code. Codes skip 0, O, 1, I and L so they survive being read aloud.

**How it fits together.**

- `worker/index.ts`: `POST /stick-fight/api/rooms` makes a room and returns its code; `GET /stick-fight/api/rooms/<code>/ws?role=host|guest` opens the room's WebSocket. Each room is one Durable Object (hibernating WebSockets). It passes every message from one player to the other unchanged, and writes only its own `{"t":"sys"}` notices: welcome, peer joined or left, and errors (`no-room`, `full`, `busy`, `flood`). `GET /stick-fight/api/ice` returns `{ iceServers, ttl, turn }`: Cloudflare STUN plus TURN credentials good for an hour (see Hosting, Secrets), or public STUN only with `turn: false` when the Worker has no TURN key or Cloudflare doesn't answer. Each Worker isolate reuses one set of credentials for 10 minutes, so every set handed out has at least 50 minutes left.
- `src/net/link.js`: fetches `api/ice` as the link opens (2.5 seconds at most, else public STUN), then the WebSocket carries the WebRTC offer, answer and ICE candidates; game packets then go peer to peer over a DataChannel (unordered, no retransmits). With TURN, two phones on carrier NAT that can't reach each other directly still get a DataChannel, through Cloudflare's TURN servers. If the DataChannel isn't open within 5 seconds, packets go through the room's WebSocket instead (the relay); a DataChannel that opens later takes over. `link.candidate` says which path it took (`host` on the same network, `srflx` through a NAT, `relay` through TURN). `?relay=1` on the URL forces the WebSocket relay, and `?ice=relay` allows TURN candidates only, both for testing.
- **Limits** (`worker/index.ts`, `wrangler.jsonc`): per client IP (an IPv6 address counts by its /64), 10 new rooms a minute, 5 new crew rooms a minute, 30 WebSocket joins a minute (quick and crew rooms together) and 20 profile and sign-in calls a minute, counted per Cloudflare location (the sign-in caps per email and per hour are in D1; see Profiles and sign-in). Over the limit, `POST /rooms` answers 429 `{"error":"busy","message":"Too many tries from your network. Try again shortly."}` with `Retry-After: 60`, and a join gets a socket that sends `{"t":"sys","ev":"error","reason":"busy"}` and closes, so the page can say why; the menus show SERVER BUSY: TRY AGAIN SHORTLY. In a room, a message over 16 KB is dropped, and each socket gets a bucket of 480 messages refilling at 240 a second (about 4x a match's traffic); past it, messages are dropped, and after 1,000 drops the socket gets `reason: "flood"` and is closed. A room nobody has joined lasts 30 minutes; once its players have all left, its code stops working after 5 minutes (time to reload a page), and the alarm then deletes its storage and itself, leaving nothing behind.
- `src/net/rollback.js`: rollback netcode, GGPO style (see Rollback below). Both machines run the whole sim. Each runs its own input after a 2-frame delay (17 ms at 120 Hz), guesses the other player's input by repeating the last one it got, and keeps going; when the real input arrives and differs from the guess, it loads the state saved before that frame and re-runs the sim to the present, silently. Each side sends its input with every input the other side hasn't acknowledged, so a lost packet is covered by the next one. Every 30 frames, once a frame is confirmed (both real inputs in), each side hashes the sim (`src/net/hash.js`: positions, velocities, states, health, stamina, timers and every rig joint, by exact bits) and sends the hash; on a mismatch both show DESYNC and log the fields that differ to the console.
- `src/net/codec.js`: an input is 11 bits (direction, jump, guard, crouch, run, the four limbs, and whether it came from the touch stick, which turns off double-tap run). An input packet is 15 bytes (with the match number) plus 2 per frame.
- `src/net/online.js`: the session (host, join, start, leave), the connection readout (bottom-left; centered under the timer on a touch screen: `P2P 13 MS · RB 3 · DELAY 2`, the round trip, how many frames the last correction re-ran, and the input delay; amber when relayed, plus DESYNC or WAITING FOR RIVAL), and a lobby panel. The host is P1 (left), the guest P2; each plays the character picked on the select screen (`net.setCharacter(id)`, sent with the `ready` message; the host's `start` message carries `chars: [host's, guest's]` and both sims build their fighters from it), in its own neon (a mirror match gives the guest the character's alt color; TEMP vs TEMP is white and orange as before). The HUD names them YOU and RIVAL after the character's name. Both screens show the same thing: the host is P1 on the left and the guest P2 on the right, the HUD's YOU bar on whichever side is yours (nobody's view is mirrored; two players in the same room see the same layout on both screens). When both are linked the host picks the seed and both start the `online` scene from frame 0. A match ends on a frame both machines agree on, and the room stays open for the next one (see Between matches below). If the other player leaves, or nothing arrives for 10 seconds, the match ends; with the arcade flow running that's its VERSUS ONLINE end screen (YOUR RIVAL LEFT, CONNECTION LOST), and on a `?scene=` page it's a notice and the demo.

**Starting a match.** The game's menus call the API on `window.__net` (also returned by `createOnline` in `main.js`): `net.host()` resolves to `{ code, url }`, `net.join(code)`, `net.leave()`, `net.roomFromUrl()` reads `?room=`, and `net.on('status' | 'connected' | 'start' | 'peer-left' | 'end' | 'desync', fn)`. `net.openLobby('menu' | 'host' | 'join', code?)` opens the built-in panel (keyboard, gamepad and touch: arrows or D-pad move, Enter or A presses, Esc or B backs out, and on the code box up and down turn the letter like arcade initials). `net.busy` is true while that panel is up, so the title screen shouldn't start a game then. The menu flow (`src/flow/`) owns the VERSUS ONLINE entry, its own HOST and JOIN screens and the `?room=` hand-off; it talks to `online.js` only through `src/flow/netApi.js` (`adaptOnline`), ignores its own input while `net.busy`, and gets the end of a match through the `endMatch` hook in `main.js` (which closes the lobby's notice in favor of the flow's screen).

**No mirrored view.** Online, nobody's view is flipped: both screens show the host on the left and the guest on the right. `?mirror=1` on the URL still draws any scene mirrored left-right as a debug view (`main.js` `syncMirror()`: the WebGL canvas gets a CSS `scaleX(-1)`, the HUD reads `camera.mirror`, `src/combat/input.js` flips `dx` at capture, and the stereo pan flips), but it never turns on by itself.

**Between matches (the room session).** `online.js` keeps the room's session after a match: the match number `n`, the tally, and the post-match and pick choices. The agreement rules are its, the screens the flow's.

- **The end of a match.** `rollback.js` notes the frame on which the sim first shows the result (`phase` becomes `'match'`; a correction that re-runs that frame finds it again). `online.js` halts the netcode 150 frames later (`END_HOLD`, 1.25 s of the WINS card; the sim's own 1.8 s hold would reseed and start another match) and ends the match once that frame is confirmed, so both machines stop on the same state and count the same result from `sim.wins`. The finished netcode keeps sending its inputs and acks every 100 ms until the next match starts, so the other side can confirm its last frames even if the final packets were lost. Each side then hashes the final state; the host sends `{t:'result', n, tally, hash, f}` and the guest checks the hash and takes the host's tally if its own ever differs (it hasn't in testing).
- **The tally** counts matches (best of 3), host wins, guest wins and draws, plus rounds, for the room session; `net.tally` (and the flow's `hud().tally`, for the fight HUD) gives it from this side: `{ you, rival, draw, roundsYou, roundsRival, games }`. Each `start` message carries the host's tally too. **All time:** each browser keeps a random id (`stick-fight-pid` in localStorage) that rides the `ready` message, and a win, loss and draw count per rival id (`stick-fight-rivals`, the 30 most recent rivals). It's from this browser's side only and resets if either player clears site data. That's the record for quick rooms; in a crew match the record is the crew's, kept on the server (see Crew rooms), and this one isn't touched. The `ready` message also carries the player's name (`net.setName`), which the post-match and pick screens show in place of RIVAL.
- **Messages** (control JSON through the room, all carrying `n` so a late one from another match is dropped): `post` (each side's choice, `want`: rematch, chars or wait, its cursor, `focus`, and `poke` for a press that stops the auto countdown), `cd` (host to guest: a countdown's kind, `auto`, `agree` or `host`, and the ms left; the host's clock runs every countdown and starts the match), `go` (host to guest: NEW CHARACTERS), `pick` (each side's card and whether it's ready), `result`, `alive` (every 3 s between matches; 15 s without a word from the other side is CONNECTION LOST), and `start` (`seed`, `chars`, `botch`, `n`, `tally`). Every input packet carries the match number (one byte) and every hash and desync dump the match number too, so nothing from one match can land in the next one's input history or hash check.
- **Without the menus** (a `?scene=` page, which only has `online.js`'s lobby panel) nobody sees a post-match screen, so the host's auto countdown starts the next match every time, as rematches did before.
- **Robustness.** Both pressing at once: the host decides, so crossed messages settle on the host's side (a guest's NEW CHARACTERS arriving after the host's REMATCH stops the agree countdown, puts the request on the host's screen, and the host presses again; a guest request that arrives after the host started is ignored, and the guest follows the `start`). A guest whose last frames confirm late still follows: a `start` or `go` that arrives before its match ended ends it and applies. A player who leaves, closes the tab or loses the connection between matches ends the room for the other with YOUR RIVAL LEFT or CONNECTION LOST. The room server only passes messages on, so none of this needed a Worker change, and a room stays alive while either player is connected. `NET_VERSION` is 10 (8 was the room session; 9 adds the name in `ready` and the crew match's `go` at match 0; 10 is the side-swap fixes and the stamina change, Controls, Sides and Stamina): older builds get YOUR GAMES DIFFER: RELOAD BOTH.
- **Tested** with two browsers (Chromium host, Firefox guest) through the local Worker: an auto rematch, the guest asking for REMATCH and the host accepting, the guest asking for NEW CHARACTERS and the host overriding with REMATCH, crossed presses, NEW CHARACTERS with the guest on a gamepad and the host's START by touch, the guest leaving from the post-match screen, 32 idle seconds on it with both still in the room and the host then leaving, a guest vanishing on the pick screen, a stale room code and a version mismatch. Every match's hash checks and its final state hash matched on both sides, and both tallies agreed after every match.

**Crew rooms** (bookmarkable rooms for a group of friends). A quick room is a one-off four-letter code; a crew room is a permanent link the crew keeps, `https://askscottpierce.com/stick-fight/?crew=tuesday-crew-7k2qm`: the crew's name in lower case with dashes, then five random characters (no 0/o, 1/i/l), so it reads well and can't be guessed (28 million per name, behind the join limit). It's a query parameter rather than a path because the page is one static `index.html` with relative asset paths; `?crew=` needs no routing. While you're in the lobby the address bar holds that link (`history.replaceState`), so a bookmark taken there works; leaving the crew takes it off.

- **Making and joining one.** CREATE CREW ROOM asks for a crew name (3 to 20 letters, digits and spaces) and `POST /stick-fight/api/crews` makes the room. JOIN A CREW takes the code (the part after `crew=`) typed, or the whole link pasted. Opening the link does the same. Every crew you open goes to the top of your crew list (the profile's `crews`), and the online menu shows the three most recent.
- **The lobby** (`crewLobby`): the crew's name and link, COPY LINK and SHARE (the phone's share sheet where there is one), the standings (every member who has opened the link, most wins first: wins, losses, draws, your record against each of them, and each one's favorite fighter in its neon), the last three results, a status line, and PLAY (focused), ONLINE MENU and MAIN MENU. A square dot before each name is presence over the room's WebSocket: cyan HERE, amber READY (with a chip), pink PLAYING, hollow for a member who isn't here.
- **Playing.** PLAY means "I'll fight whoever else is ready" (it turns into CANCEL while you wait; a press while still connecting counts). When two members are ready, the one who pressed first hosts: the crew room claims a quick room code and tells each page its role, and both go to the pick screen (VS BOB, opening on each one's last pick in this crew, else the favorite) and then the match, all on the usual quick-room machinery (`online.js` with `pickFirst`). After each match the post-match screen works as always (rematch countdowns, NEW CHARACTERS, the host's final call); its LEAVE ROOM reads BACK TO CREW, and the other player's notice says ALICE WENT BACK TO THE CREW with BACK TO CREW. A rival who never connects sends you back to the lobby after 20 seconds (BOB DIDN'T CONNECT).
- **Winner stays on.** A third member who presses PLAY while two are fighting waits (PLAY THE WINNER). When that match ends with a winner, the crew room tells both players: the screen says YOU STAY ON or BACK TO THE CREW, WINNER STAYS ON · CAROL IS NEXT, the rematch countdown stops, and after 4 seconds both go back to the lobby, where the winner is ready at once at the front of the line and gets paired with the one waiting. A draw changes nothing.
- **Recording.** The host's page is authoritative, as in every online match: when a match ends it sends `{ t: 'result', match, n, winner, wins, chars }` over the crew socket. The crew room accepts it only from the member it made host of that match, and counts it once, keyed by `<match id>:<n>`, so a resend or a reconnect can't count it twice. It updates both members' wins, losses, draws, rounds and last pick, their play count per fighter (the favorite is the most played), the head to head for the pair, and the recent list, then sends the new standings to everyone in the lobby. The post-match screen shows CREW RECORD VS BOB 3–2 from the server instead of this browser's record.
- **What a crew room keeps** (its Durable Object's own SQLite storage, `worker/crew.ts`): the crew's name, slug and dates; each member's display name, first and last seen, wins, losses, draws, rounds won and lost, and last pick; play counts per fighter; head to head for every pair that has played (wins each, draws, rounds each); the last 300 matches (when, who hosted, who joined, the winner, rounds, fighters; the lobby shows the latest); and the matches it started (a day). Members are stored by a hash of the player id salted with the crew's slug, never the id itself. At most 50 members (a 51st gets THIS CREW IS FULL) and 80 open sockets.
- **Expiry.** Every visit and every result pushes the crew's expiry to 90 days out and re-arms its alarm; when the alarm finds it past due and nobody connected, it deletes all of the crew's storage and its alarm. A link to a deleted (or mistyped) crew shows NO CREW AT THAT LINK with ONLINE MENU and MAIN MENU. With `DEV_HOOKS=1` (`.dev.vars` only), `POST /stick-fight/api/crews/<slug>/dev-expire` expires a crew at once, for testing.
- **Messages** on the crew socket (JSON; `src/net/crew.js` on the page, which reconnects by itself after a drop and keeps a pending PLAY): from the page `hello {pid, name}` (first), `name`, `play {on, stay}`, `lobby` (back from a match), `result`; from the room `welcome {you}`, `state {crew, members, h2h, recent}` (to everyone, on every change), `match {id, code, role, rival}`, `rotate {match, stay, next}` and `error {reason}` (`no-crew`, `crew-full`, `full`, `bad-hello`, `flood`; the Worker's `busy`). Each socket gets 4 KB per message and 10 messages a second (a burst of 30).

**Profiles and sign-in.** Nobody needs an account. A player is a random 128-bit id plus a display name, kept in localStorage as `stick-fight-player` (`{ id, name, email, crews }`, `src/net/profile.js`; every storage call wrapped, so a private window just keeps it for the page). The name is the only thing other players see. The id only ever goes to our own server, which uses it to know you in each crew (hashed there); it never goes to the other player. PROFILE in the online menu shows the name, CHANGE NAME, and SAVE MY PROFILE (or SIGN OUT once saved), BACK and MAIN MENU.

- **SAVE MY PROFILE** asks for an email (the on-screen keyboard has @ . - _; a paste works), then sends a 6-digit code and a one-click link from `hey@askscottpierce.com`. Typing the code (VERIFY; SEND AGAIN for a new one) links this device's player id to that email in D1. On another device, SIGN IN on the first name screen (or SAVE MY PROFILE) with the same email restores the same id, name and crew list, and with the id every crew record: WELCOME BACK, ALICE: PROFILE RESTORED. The crew lists merge. A device whose id is already saved under another email is told to sign in with that one (making it a fresh id would cut it off from its own records). SIGN OUT (press twice) ends the session and starts this device fresh with a new id, for a shared machine.
- **The link** is `https://askscottpierce.com/stick-fight/#signin=<email>&code=<code>`. The fragment never reaches a server log, and the page submits it from JavaScript, so a mail scanner that opens links can't use the code up. Opened in the same tab (only the fragment changes), the page notices and starts over on the code screen.
- **Protections** (`worker/auth.ts`): codes are 6 digits, last 10 minutes and take 5 tries, and only their hashes are stored (SHA-256 of the email and code); a used code is deleted, so it works once. Sends: one per email per 30 seconds, 5 per email and 20 per IP an hour. Guesses: 10 per email an hour and 20 a day, 30 per IP an hour, counted before the code is checked. All of it also sits behind `AUTH_LIMIT` (20 calls a minute per IP). Sessions are 30 days, stored as hashes, in an HttpOnly, Secure, SameSite=Lax cookie with `Path=/stick-fight` (the domain is shared with other apps). Requests that change something must be JSON, which a cross-site form can't send. An email is never shown to another player and only ever goes back to its signed-in owner (`GET /me`). Expected refusals (a wrong code, a cooldown) answer 200 with `{ error }`, so the page's console stays clean.
- **API:** `POST auth/start {email}`, `POST auth/verify {email, code, pid, name}` (sets the cookie), `GET me` (`{ email, pid, name, crews }` or `null`), `PUT me {name?, crews?}`, `POST auth/logout`, all under `/stick-fight/api/`. The page calls `GET me` when the online menu opens, so a session from another visit is picked up and an ended one noticed.
- **Google sign-in** would plug in beside the code: an OAuth callback under `/stick-fight/api/auth/google` that, once Google vouches for the email, calls the same `linkAccount()` and `createSession()` as a verified code. It needs an OAuth client registered by the owner (Google Cloud console, redirect URI on askscottpierce.com) and its secret as a Worker secret, so it isn't built.
- **Dev mode.** With `DEV_LOGIN_CODES=1` in `.dev.vars`, no email is sent: `auth/start` returns the code, and the code screen shows DEV MODE: YOUR CODE IS 123456. Vite's dev proxy rewrites the cookie's path to `/`, because the dev page is served at `/`.
- **Tested** (local Worker and Vite, Playwright, 2026-11-08): A (Chromium, keyboard) named itself, created TUESDAY CREW and got the link in the address bar; B (Firefox, mouse on the on-screen keyboard) and C (Chromium, touch) opened the link and were asked their names first; presence showed all three on all three screens. A and B played a match ended by the same scripted KO frame on both sides (`net.haltAt` to a common confirmed frame, then `debugKO` on both): no desync, and the result showed in the standings on all three screens and as CREW RECORD VS BOB 1–0 on the post-match screen. A went back to the crew and B got ALICE WENT BACK TO THE CREW. In a second match C waited, B won, and winner stays on sent A to the lobby and B and C to the pick screen. After reloading all three: same crew, names, 1–1 records, and favorites (INTERN, COURIER); match 2's pick screen opened on each one's last pick. Then A saved its profile (a wrong code: 4 TRIES LEFT; SEND AGAIN at once: WAIT 30 SECONDS), and a fourth context on a fake gamepad typed and deleted on the name screen, reached SIGN IN on the D-pad, signed in with the email link, and came back as ALICE with the same player id, the crew in its list and the 1–1 record in the lobby. With curl: the sixth crew in a minute got 429, the 19th code send from one IP in an hour got `too-many` and AUTH_LIMIT then `busy`, guesses ran out per code and per email, and the expiry hook deleted a crew. Zero console errors; `npm run typecheck` passes.

**Determinism.** Netplay that runs the sim on both machines only works if both compute the same sim to the last bit. Run the same recorded input log through the sim in Chromium, Firefox and WebKit, with the builtin `Math.sin`, `cos`, `atan2`, `acos`, `hypot` and `pow`, and the rig's joints differ in the last bit by step 6 to 40 in every engine pair (the outcome still matched over 100 seconds, but every hash check would fail and the drift can flip a close hit). The sim and the rig now use `src/combat/dmath.js` instead: fdlibm's polynomials written with only + - * / and `Math.sqrt`, which IEEE 754 makes identical on every engine. With it, all three engines produce identical hashes on every step over 6000 steps, for a scripted bout and for a CPU-vs-CPU match. A match also starts with `sim.resetMatch({ fresh: true })`, which clears every leftover of earlier play (unit fields, the rig's jump arc and fall surfaces, the reach table the sim learns from hits): without it, each player's attract demo leaked in and the first hash check already failed.

**Rollback.** `src/net/rollback.js` keeps every frame's real inputs for both players in a 1024-frame history and moves the sim only through `simulate(frame)`.

- **Guessing.** A remote input that hasn't arrived is guessed as the newest one held. Before a frame runs on a guess, the whole sim is saved (`sim.saveState()`) into a ring of reused snapshots; frames run on real inputs need no snapshot. When a real input arrives and differs from the guess used for its frame, the next `advance()` loads the snapshot from before that frame and re-runs `simulate()` up to the present.
- **Depth.** At most 12 frames (100 ms) ever run on guesses (`MAX_ROLLBACK`); past that the sim waits for the other side (a stall: WAITING FOR RIVAL after 300 ms). Time spent stalled is given up, not banked, so a side doesn't burst ahead and stall again. The side that's ahead of the other (from the frame number in each packet and half the ping) runs 10% slow, 30% past 6 frames.
- **Delay.** The local input runs 2 frames late (17 ms). When half the ping plus the jitter is longer than the rollback window covers, the delay grows one frame a second (up to 10), and a second with stalls while not ahead adds one; it comes back down with headroom.
- **Save and restore.** `src/combat/snapshot.js` (`sim.saveState(reuse?)` / `sim.loadState(s)`) captures everything that feeds the next tick: the sim's fields (phase, timers, round, wins, card, callouts, combo, the horde and its ragdolls, the measurement log), the rng's state (`mulberry32` exposes `rng.state`), the reach table the sim learns from hits, the bounds, every unit field by value (its `prevJoints` points copied), each rig through `rig.getState()` / `rig.setState()`, and the arena state `tick()` mutates (its clock, door swings, the body pile and how settled each body is). The rig's state is its closure: the move and key list, the clock inside it, the pose and its velocity, the reaction layer, the springs, the point simulation (every point), the crossfade, the jump arc and landing ease, the fall surfaces and walls. What the rig mutates in place is copied both ways; poses, keys and move defs never change, so they're shared. A restore writes into the same unit and rig objects, so events, the HUD and the camera keep valid references. Saving takes about 20 µs, loading about 20 µs.
- **Effects.** The sim's events go through `sim.eventFilter` while the netcode runs it. The first simulation of a frame fires all its events and records them by identity (type, the units involved, move, callout text; position only for events with no unit, coarsely). A re-run of that frame fires only events beyond what already fired for it, counted, so two footsteps stay two: a hit the guess missed sparks and sounds up to 100 ms late, and nothing fires twice. An effect from a wrong guess isn't taken back (a stray spark or whoosh now and then). Sound, particles, lights, shake, callouts and the flow's scoring all hang off these events, so they all follow this policy; the HUD draws the current state, so a correction shows at once.
- **Hashes.** Only confirmed frames are hashed and compared: a frame is confirmed once both real inputs are in and no correction is waiting to re-run it. Every 30th frame's hash goes out then.
- **Proof of the save and restore.** A recorded CPU-vs-CPU bout (two showcase CPUs, their inputs and rng recorded, 14,000 steps each over six seeds, including round and match ends) was replayed with about 5,500 rollbacks: at random frames and, more often, at frames in hitstop, throws, wall splats, juggles, ragdolls, KOs, floor breaks, the stair tumble, the follow-down vault, getups and match ends, save, run 1 to 16 steps, restore, run again, restore, run again. A deep hash of every sim field, every unit field and the rig's whole `getState()` matched the reference run on all 132,000 checked steps; leaving out the rig, the rng or the arena clock from the restore fails it at once. The stamina faint and combo decay (sim behavior, so `NET_VERSION` is 3) keep their state in plain unit fields (`faint`, `faintDmg`, `faintAt`, `comboDmg`, `selfChain`, `lastHitAt`), which the snapshot copies with every other unit field; a save, run 480 to 900 steps, restore and replay of the recorded inputs (and the CPU's rng state after each of its calls) matched the full snapshot on every step, saved mid-faint, mid-combo and before either, and knocking one step off the restored faint clock made it differ on the first step.
- **Proof for characters and the back-walk** (`NET_VERSION` 5). Seven CPU-vs-CPU bouts at difficulty 0.9 (COURIER vs SECURITY three times, SECURITY vs TEMP twice, COURIER vs TEMP twice; about 56,000 steps) were recorded with their inputs, the rng state after each CPU call and the unit fields the CPU writes (`aaJump`, `grabId`, `rollId`), then replayed with 1,616 rollbacks: save, run 1 to 16 steps, restore, run again, comparing a deep hash of the whole `saveState()` (every sim field, every unit field, every rig's `getState()`) with the reference on each step. Half the frames inside a unique move (Express Slide, Drop-Off Knee, SAME DAY, Escort and its grab, Shoulder Check and its armor, LOCKDOWN) were save points, plus back-walks, blocks, blockstun, ragdolls and random frames. All 13,662 restored steps (and the 42,000 plain replay steps) matched. Restoring with `armorLeft` zeroed, the travel `glide` dropped, or the unit's character swapped made it differ on the first step. The same three pairings, run 6,000 steps from one seed, give the same hash on every step in Chromium, Firefox and WebKit. Two pages through the local room Worker started an online match from the handshake with COURIER (host) vs SECURITY (guest) on both, with matching confirmed hashes.
- **Cost.** The worst case, every rendered frame restoring the state from 8 frames back and re-running 8 frames (saving each), over a 12,000-step bout on an M-series Mac: Chromium 0.35 ms per rendered frame on average (p99 0.9 ms, one 5.7 ms garbage-collection spike), WebKit 0.18 ms, Firefox 0.23 ms, Node 0.34 ms (max 1.5 ms). At 12 frames, Chromium 0.41 ms average, 1.4 ms max. A plain step is 16 to 36 µs. In the network tests below the netcode's whole `advance()` averaged 0.2 to 0.4 ms per frame, and the longest single correction took 2 ms.
- **Network tests.** Two browsers of different engines played 3,600 frames (30 s) of scripted, human-paced input through the local Worker with `?netsim=` on both pages, peer to peer (Chromium and Firefox) and through the forced relay (`?relay=1`, Chromium and WebKit). Every confirmed hash (120 checks a side) and the final hash matched on both sides in all eight runs. Rollbacks are per side over the 30 s; depth in frames of 8.3 ms.

## Layout

- `index.html`, `src/main.js` — the game. Wires the modules below.
- `src/fighter/` — stick figure rig, poses, animation. Draws to a 2D context.
- `src/fx/` — lighting and effects compositor (WebGL), particles, camera shake.
- `src/combat/` — input, state machine, frame data (heights, stamina costs, enders), the string table (`strings.js`), hitboxes, AI, the neon HUD, rounds.
- `src/characters/` — the roster (see Characters): one file per character, `registry.js` (merging each one into the shared tables), `index.js` (registering them all).
- `src/flow/` — the arcade flow (see Arcade flow): `index.js` the state machine and its screens, `ui.js` the DOM overlay (neon, hard corners, scales with the stage), `select.js` the character select, `menuInput.js` keys and pad for menus, `controls.js` the one control table, the device in use and the footer legend, `ladder.js` the six stages and `buildLadder`, `scores.js` score rules and the high score tables, `netApi.js` the seam to `src/net/online.js`, `techniques.js` the happy accidents found and the botch switch (localStorage).
- `src/combat/botch.js` — botches and happy accidents: the family picker, the stamina cost, the accident windows, the flail's and the eight techniques' clips and frame data (see Botches and happy accidents).
- `src/net/` — online play (see Multiplayer): `online.js` session, readout and lobby; `crew.js` the crew lobby connection; `profile.js` the player id, name and sign-in; `link.js` WebSocket and WebRTC; `rollback.js` netcode; `codec.js` wire format; `hash.js` state hash. The sim's save and restore for rollback is `src/combat/snapshot.js` (plus `getState()`/`setState()` on the rig in `src/fighter/index.js`).
- `worker/` — the Worker: routes, ICE and the quick room Durable Object (`index.ts`), the crew room Durable Object (`crew.ts`), profiles and email sign-in (`auth.ts`), shared helpers and the bindings (`env.ts`), with its own `tsconfig.json`. `migrations/` is the D1 schema.
- `src/combat/dmath.js` — bit-identical trig for the sim and the rig on every browser engine (see Multiplayer, Determinism).
- `src/touch.js` — mobile touch controls (synthetic key events, active only on coarse pointers).
- `src/arena/` — the stage: geometry, background art, static lights.
- `src/audio/` — sound effects and music (see Sound). `main.js` makes two calls into it: `gameAudio.attach(sim)` and `gameAudio.event(ev)` from its event router. During the attract demo (and the menus over it) it holds the events back and attaches `null` instead of the sim (so the whiff watcher is quiet too), then attaches the sim again when a game starts.
- `demo/*.html` — one page per module so each can be judged alone.
- `window.__game.advance(ms)` steps the game without drawing a frame (fast, for counting events over a long demo); `window.__gauntlet.step(ms)` steps and draws.
- `gauntlet/` — the quality loop: the brief (with the owner requirements), the capture tool and the workbench log. The reference images and per-round critic captures stay out of the public repo (see `.gitignore`); the reference images belong to their owners.

## Sound

Everything audio lives in `src/audio/`, and none of it uses sample files.

- `index.js` — the router: turns sim and fighter events into effects, pans each by the fighter's screen x (flipped by `gameAudio.setMirror(true)` in a mirrored view), and watches for whiffs (a strike reaching recovery without contact) and for which pool the music belongs in. It also owns the unlock on the first touch or key, M and N, the settings, and the phone's media player (`navigator.mediaSession`: "Stick Fight · <track>" with play, pause, next and previous). `window.__audio` exposes it for tests.
- `sfx.js` — the effects, built on the spot from a second of white noise and a few oscillators, each with a little random variation: whooshes by limb (a jab short and high, kicks longer and lower, the spinning enders longest), hits, block, counter (the heaviest hit short of an ender, a second snap and a bright ping), footsteps, landings, the jump, a body fall with a slide, wall splat, wall bounce, ground bounce, the throw (a grab rustle, then a slam), whiff, the exhale of a faint, ROUND and FIGHT, KO, the slow-motion ender KO (pitched down with a long tail of echoes), combo notes that climb with the hit count, the ender stinger, a horde goon down, the match end, and UI clicks. The multi-floor events have theirs too: a floor break (a crash, debris and a railing clanging), a knock per stair tread, a vault landing, and a floor-clear stinger. A hit is built in layers scaled by its weight (a jab light, a cross a bit more, a heavy, a counter, an ender or a KO the most): a crack of a few milliseconds for the contact, a punch falling through 300 to 120 Hz that a phone speaker can play, a sub thump into 40 to 55 Hz for headphones, a lowpassed tail, a crunch through a tanh shaper on the heavies, and on an ender or a KO a long low boom with a harmonic a phone can hear. A light hit stays about 0.15 s long so a fast string doesn't smear, and the combo note and the ender stinger come in 15 and 30 ms behind the crack, under it. Effects go through a compressor, a limiter and a soft clip, so a horde pile-up can't clip. Impacts (hits, wall splats and bounces, the ground bounce) skip the compressor on a bus of their own, because through it every hit came out at the same peak, a jab as loud as a KO. At most 16 sound at once (a new one steals the oldest of the lowest priority; footsteps go first). The effects have their own AudioContext.
- `music.js` + `tracks.js` — the soundtrack, written as [Strudel](https://strudel.cc) code and played through Strudel, after cf-quarry's player. Strudel is only imported the first time music turns on. A track plays its form twice, then the next track in the current pool starts. The pool follows the game: `menu` on the title and its attract demo, the mode select, the online menus, the high score tables, game over, initials and the ending; `fight` for a normal match, `horde` in horde mode (each cleared floor moves to the next horde track), `calm` in training (the dummy scene). The arcade flow names the pool for each screen through `gameAudio.setMusicPool(pool)` (null hands it back); without the flow (a `?scene=` page) the audio module guesses it from the sim four times a second, and `?scene=attract` plays `menu`. The music ducks under the KO stingers, the slow-motion ender, the floor break and FIGHT, and gets a quick sidechain-style dip under a hit (`music.pump`): none for a jab, so a fast string doesn't wobble it, about 2.5 dB for a cross, 6 for a heavy, 8 for a counter or a throw, and 10.5 for an ender or a wall splat, down in 10 ms and back in 0.1 to 0.35 s. A silent looping `<audio>` plays beside it so a phone shows its media player.
- `ui.js` — the sound panel and the speaker button. Its sliders are drawn in the DOM and driven by pointer events, because `touch.js` cancels every touchmove on the page.

The tracks share one theme (`THEME`, a four-bar call, answer, fall and rest), one set of changes (i VI VII i, iv VI VII v), and one form (an intro, `a` with the drums, `b` with the theme, a `drop` without drums, and `c` with everything). They use only Strudel's built-in synths and noises, so nothing is fetched to play them, and any of them pasted into strudel.cc plays there.

**Phones get a lighter mix.** On a touch device (`pointer: coarse`) `music.js` thins each track before playing it: supersaws drop to 2 unison voices and the distortion and bit-crush worklets come out, because the full mix was more than a phone's audio thread could keep up with alongside the game (choppy music). Reverb, delays and filters stay.

**The Strudel bundle.** `public/vendor/strudel.mjs` is the `@strudel/web` 1.3.0 bundle (850 KB), copied from cf-quarry with one marked patch (the cyclist looks 0.45s ahead instead of 0.1, so a long game frame on a phone doesn't make it skip slices of the music; search the file for "stick-fight patch"), with its license text beside it in `public/vendor/LICENSE`. It lives in `public/` so Vite copies it into the build untouched; `music.js` imports it at runtime by URL, because the bundle resolves its own helper files relative to itself. Its source is at https://codeberg.org/uzu/strudel.

## Practices

- No framework, no npm deps at runtime. Game modules stay plain `.js` (not `.ts`) so the capture tool's raw file server can load them; the Worker is TypeScript, built by wrangler. Playwright (global) only for `gauntlet/capture.mjs`.
- Logical resolution 1280x720, DPR-aware. Everything positions in logical pixels.
- Each module owns its folder and its demo page. Cross-module contracts live in `gauntlet/BRIEF.md`.
- Commit after every gauntlet round with the round number in the subject.
- The capture tool serves files raw, without Vite, so anything `main.js` imports has to be plain JavaScript; that's why `src/flow/` is JS with JSDoc types rather than TypeScript.
- Capture output is large (about 1.3 MB per frame). Delete capture folders when a round is done; `gauntlet/captures/` is gitignored.
