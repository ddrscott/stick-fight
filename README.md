# stick-fight

A browser fighting game. Stick figures animated at Xiao Xiao quality, lit like a modern 2D game.

## Design pillars

Read these before adding a mechanic. When a change is a judgment call, these decide it.

- **Timing, not speed.** Skill is pressing one thing at the right moment because you read what the other player committed to. It is never how many inputs you can enter a second. Nobody should win on fast, simple input, and nothing should need a reflex younger than its player.
- **Give and take, like tai chi and aikido.** Wait for the other player to commit, then use their own force. The harder someone commits, the harder they fall when it's read. Every option has an answer, and every answer costs something when it's guessed wrong.
- **Mashing loses.** A press thrown where it doesn't belong botches (Botches), every swing costs stamina, and the last point leaves you fainted and open. A new mechanic must not hand mashers a way back in: no defense that a held direction or a repeated button triggers by accident, no escape you mash out of.
- **Simple bodies, deep systems.** The stick figures and their inputs are the easy part: a direction plus one button, no motion inputs, strings with a rhythm rather than a speed. The sophistication lives in the botch and technique system, where the same physics that tangles a mistimed press rewards an exactly timed one.
- **Windows a person can learn.** A timing window can be generous if missing it, or using it when nothing was coming, is committal and punishable. Tight-and-free is a reflex test; wider-and-committal is a read.

## Run

```sh
npm install
npm run dev          # Vite on http://localhost:8077/: the homepage, the game at /play/, fighter pages at /fighters/
npm run dev:worker   # the online-rooms Worker under wrangler dev on :8787 (Vite proxies ./api to it)
npm run typecheck    # tsc over src/, then over worker/
```

Online play needs both: `npm run dev` for the game and `npm run dev:worker` for the room server. Vite forwards `/api/*` (HTTP and WebSocket) to `http://127.0.0.1:8787/stick-fight/api/*`. To run the production layout instead, `npm run build` and then `npx wrangler dev` serves the site at `http://localhost:8787/stick-fight/` (the game at `/stick-fight/play/`) with the API beside it.

The game is plain ES modules with canvas 2D for drawing and WebGL for the lighting composite. Vite serves it in development and bundles it for deploys. New modules can be TypeScript (`.ts`) next to the JavaScript ones; `tsconfig.json` has `allowJs` on and `checkJs` off, so add `// @ts-check` to a JS file to type-check it. The demo pages (`demo/*.html`) and the capture tool work against the dev server as before.

## Hosting

The game is a Cloudflare Worker on two zone routes, `askscottpierce.com/stick-fight` and `askscottpierce.com/stick-fight/*`, on the Scott Personal Account. Every other path on askscottpierce.com stays with the main site. The homepage is `/stick-fight/`, the game `/stick-fight/play/`, the fighter pages `/stick-fight/fighters/` (see Site). The assets binding's `auto-trailing-slash` redirects `/stick-fight`, `/stick-fight/play` and `/stick-fight/fighters/courier` to the same path with a slash, so each page's relative asset paths resolve.

Static files come from the assets binding (`dist/`). The Worker script (`worker/index.ts`) runs first only for `/stick-fight/api/*` (`run_worker_first`), where it serves quick rooms through a Durable Object class `Room` (binding `ROOMS`, migration `v1` with `new_sqlite_classes: ["Room"]`), crew rooms through a second class `Crew` (binding `CREWS`, migration `v2` with `new_sqlite_classes: ["Crew"]`, `worker/crew.ts`), and profiles and email sign-in (`worker/auth.ts`). A request that reaches the script anywhere else gets a 404. The first deploy with the script creates each Durable Object class from its migration. Workers rate limiting bindings cap things per IP (see Multiplayer, Limits): `ROOM_LIMIT` (namespace `7101`, quick rooms), `JOIN_LIMIT` (`7102`, WebSocket joins to either kind of room), `CREW_LIMIT` (`7103`, 5 new crew rooms a minute) and `AUTH_LIMIT` (`7104`, 20 profile and sign-in calls a minute); they're free on every plan, and a namespace id must be unique on the account.

**D1, email and cookies** (for profiles; see Multiplayer, Profiles and sign-in). The D1 database `stick-fight-auth` (id `8a0ea2d9-9d74-466f-a6ff-5a0446d35653`, created 2026-11-08, binding `DB`) holds accounts, hashed sign-in codes, hashed sessions and the send and guess counters; its schema is `migrations/0001_profiles.sql`. The `send_email` binding `EMAIL` sends the sign-in codes from `EMAIL_FROM` (`hey@askscottpierce.com`, a var in `wrangler.jsonc`; Email Sending is already set up for that address on the zone). The only cookie is `sf_session` (HttpOnly, Secure, SameSite=Lax, `Path=/stick-fight` because the origin is shared, 30 days). `.dev.vars` (gitignored) holds `DEV_LOGIN_CODES=1`, which sends no email and returns the code to the page instead, and `DEV_HOOKS=1`, which turns on the crew expiry test route; neither is ever set in production. Locally, apply the schema once with `npx wrangler d1 migrations apply stick-fight-auth --local`. `npm run types:worker` regenerates `worker/worker-configuration.d.ts` after a change to `wrangler.jsonc`.

```sh
npx wrangler d1 migrations apply stick-fight-auth --remote   # once per new migration, before the deploy that needs it
npm run deploy       # vite build into dist/stick-fight/ (file path = URL path), then wrangler deploy
```

**Deploys run on push.** Every push to `main` deploys through GitHub Actions (`.github/workflows/deploy.yml`): `npm ci`, `npm run typecheck`, the D1 migrations (`apply stick-fight-auth --remote`, a no-op when there's nothing new), then `npm run deploy`. One deploy runs at a time, in push order, and a running one is never cancelled; Actions, Run workflow deploys `main` by hand. The repo needs the variable `CLOUDFLARE_ACCOUNT_ID` (`0223b96fe77599b23ff8ec7fcd32e2f1`) and the secret `CLOUDFLARE_API_TOKEN`, a token named "stick-fight GitHub Actions deploy" with Workers Scripts Write and D1 Write on the account and Workers Routes Write on the askscottpierce.com zone. `scripts/ci-token.sh` makes it with `CF_TOKEN_MANAGER` and pipes it straight into `gh secret set`, never printing it; running it again makes a second token, so delete the old one in the dashboard. Migrations only add tables and columns, so they run before the deploy and the old Worker keeps working on top of them. The commands above still work for a deploy from this machine.

**Secrets.** The Worker has two, for Cloudflare Realtime TURN (see Multiplayer): `TURN_KEY_ID`, the id of the TURN key named `stick-fight` on the account, and `TURN_KEY_API_TOKEN`, that key's secret. `GET /stick-fight/api/ice` uses them to mint TURN credentials that expire after an hour. Without them the endpoint answers with public STUN only, which is what local dev gets unless `.dev.vars` (gitignored) holds the same two lines. Secrets persist across deploys. To rotate the key, create a new one and point the Worker at it, then delete the old one:

```sh
# a token with "Calls Write" on the account (the dashboard, or minted with CF_TOKEN_MANAGER)
curl -X POST -H "Authorization: Bearer $CALLS_TOKEN" -H "Content-Type: application/json" \
  https://api.cloudflare.com/client/v4/accounts/0223b96fe77599b23ff8ec7fcd32e2f1/calls/turn_keys \
  -d '{"name":"stick-fight"}' > key.json             # result.uid and result.secret
jq -r .result.uid key.json    | npx wrangler secret put TURN_KEY_ID
jq -r .result.secret key.json | npx wrangler secret put TURN_KEY_API_TOKEN
rm key.json
# then DELETE .../calls/turn_keys/<old uid>; credentials minted from it stop working
```

The same key list is in the dashboard under Realtime, TURN Server. TURN bills $0.05 per GB sent out past the free allowance (the account's first 1,000 GB of Realtime a month, as of 2026-11), and a match's input packets are tiny. Only matches whose phones can't reach each other directly use it.

The places that hard-code the `stick-fight` path are `wrangler.jsonc` (routes, `run_worker_first`), `worker/index.ts` (the API prefix), and `vite.config.ts` (`outDir`, and the dev proxy's rewrite). Vite builds with `base: './'` and the pages use only relative paths, so they run the same at `/`, on the dev tunnel and at the subpath. Anything shared at the root (the API, `sw.js`, `version.json`, `vendor/`) goes through `src/root.js`, which reads how deep the page is from `<html data-root="../">`. The askscottpierce.com origin is shared by every app on it, so localStorage keys start with `stick-fight-`. Every page carries the site's Plausible tag (`data-domain="askscottpierce.com"`), so visits count under the main site by path.

Serving the game publicly ships the vendored Strudel bundle, which is AGPL-3.0, so the game is AGPL-3.0 too (see License and credits).

## Install as an app

The game is installable (`public/manifest.webmanifest`, icons in `public/icons/`, made by rendering a neon fighter on a canvas): it opens full screen in landscape with its own icon. The manifest's `start_url` is `./play/` (the game) and its `scope` is `./`, so the homepage and fighter pages are inside the app too; `id` stays `"./"` so an app installed before the move is the same app. The homepage and the game both link the manifest, so the browser offers to install from either, and the homepage shows an INSTALL hint (the browser's prompt where there is one, the Add to Home Screen how-to on an iPhone). An app installed before the game moved to `play/` (its saved start URL is the old `/stick-fight/`, which an iPhone never updates) opens the homepage, which sees it's running standalone and goes on to `play/`.
- **Android and desktop Chrome or Edge:** an INSTALL button appears on the title when the browser offers to install, and runs the browser's own prompt (`src/install.js` keeps the `beforeinstallprompt` event).
- **iPhone and iPad Safari:** Safari has no install prompt and no Fullscreen API, so a home-screen app is the only way to full screen. INSTALL opens a short how-to (Share, then Add to Home Screen). The `apple-mobile-web-app-*` tags make the home-screen app run full screen under a see-through status bar; the touch layer already pads for the safe areas.
- **Installed:** `<html>` gets `.standalone`, and INSTALL and the fullscreen buttons (touch and desktop, `src/fullscreen.js`) go away; F11 is left to the browser.
- **In the homepage's frame:** no INSTALL on the title (`install.kind` is null when `EMBEDDED`; browsers don't offer installs from a frame). The homepage's own install hint covers it.
- **Updates:** every build writes `version.json` (`{ build, at }`, the short git commit plus the build time, from `vite.config.ts`) and bakes the same id into the page as `__BUILD_ID__`. `src/update.js` checks `version.json` 20s after load, every 5 minutes, and when the tab or app comes back; when a newer build is out it offers UPDATE: a button on the title (reachable by controller) and a small NEW VERSION pill on menu screens. Never mid-fight or in an online session (a reload would drop the room). UPDATE asks the service worker to update and reloads.
- **Service worker** (`public/sw.js` at the root, so its scope covers every page; registered by `src/install.js` on https only and never on `?scene=` test pages, from the game and the site's pages): hashed `assets/*` files are cache-first, pages and everything else network-first with the cache as the fallback, so a deploy shows up on the next launch and the installed game plays offline. The core cache is the game (`play/`), the manifest and the icons; offline, a page that was never cached falls back to the game, and `play/?room=...` matches the cached `play/`. `version.json` always goes to the network. The room API and other origins are left to the network. Bump `CACHE` in `sw.js` (now `stick-fight-v2`) if the cached core list changes.

## Site

The address everyone has, `/stick-fight/`, is a traditional web page with the game playable in a frame near the top and the content around it; the game itself is one level down. Every page is a real HTML file in the build, so links share well and search engines can read them.

| Route | File | What it is |
|---|---|---|
| `/stick-fight/` | `index.html` | the homepage: header and nav (logo, Fighters, How to play, Online, About, GitHub, PLAY), the game in a 16:9 frame with FULL SCREEN and OPEN IN ITS OWN PAGE under it, the install hint, the story (a TEMP working their way up the tower) with a screenshot, life in the tower (the modes in the game's own voice), the cast (every fighter, linking to its page), how to play (the four buttons and links to the three guide pages), playing online, about and credits, footer |
| `/stick-fight/play/` | `play/index.html` | the game, unchanged (every `?scene=`, `?room=`, `?crew=`, `?pick=` and `#signin=` works here) |
| `/stick-fight/fighters/` | generated | the roster: a card per fighter with its idle loop (a sprite, see below), the tagline, health and unique moves |
| `/stick-fight/how-to-play/` | generated | the rules: the buttons, the rules list and the controls tables |
| `/stick-fight/how-to-play/philosophy/` | generated | the design pillars, written for players |
| `/stick-fight/how-to-play/strategy/` | generated | what beats what, stamina, punishing, the parry, the floor and the air, walls, and a tip per stage of the ladder |
| `/stick-fight/fighters/<id>/` | generated | one fighter's page (`<id>` is the character file's id: `courier`, `windowWasher`, `hrRep`...) |

**Fighter pages come from the character files, never written by hand.** `site/data.mjs` imports the registry in Node (the character files, the frame data and the rig need no DOM) exactly as the game does, then reads, for each registered character in roster order (TEMP included):
- name, tagline, colors (body, pants, accent, mirror) and the moveList;
- stats as bars against TEMP's (the tick on each bar), with the number and the difference;
- body: size, height, arms, legs, limb thickness and lean from `body`, and the reach of the jab, cross, snap kick and roundhouse measured the way the sim measures it (`calibrate()`: play the clip on that body and take the farthest hitbox while it's active);
- mechanics from the hooks its moves carry (armor, parry, throw counter, invulnerability, stance, status effects, shock, root, feint, side swap, command grab, juggle ender), `mechanics` (double jump, wall jump) and the CPU style;
- unique moves: one card per own move, with every input that presses it (its command, its place in a string, out of a stance, as a parry's or throw counter's reversal, a feint's follow-up), the moveList note, and frame data: damage (a multi-hit as `3+3+3+8`), height, startup, active and recovery frames, on block, stamina, reach or grab range, and properties (knockdown, launch, wall splat, armor, ducks highs, glides N px...). A card's animation plays the move on its rig in the character's colors, a string's earlier presses or a stance first (the clips the card names in `data-seq`), while it's on screen and again on a hover or tap;
- strings and enders: every string it keeps (unique ones first), its hits, the payoff, the damage the whole string does on TEMP with combo decay, and its stamina; dropped shared strings are named;
- shared basics (collapsed): the shared button table (`SHARED_INPUTS` in `src/combat/moveinfo.js`, shared with the game's MOVE LIST, which mirrors `resolveButton()` in `src/combat/sim.js` plus the stomp from `resolvePress()` and the wake-up strikes from `wakeFor()`; change them together), struck through where a command replaces one, then a line on the shared techniques with no button (parry, getting up, air recovery). The wake-up strikes and the stomp show no on block (nobody blocks a stomp; a wake-up strike springs from the floor, so its standing measurement is wrong, and its note carries getup-test's 17 to 24 frames minus) and the wake-up strikes no reach.

Timing is in 60fps frames from the rig's clips, as the sim reads them: startup is blend plus the active key's time less the sim's 50 ms pre-roll (it matches the measured numbers above: a jab 13 sim steps, Mandatory Training 27, Cold Call 19, Close the Deal 12); active runs from the active key to the recover key; recovery from there to the end of the clip; on block is blockstun less the frames from contact to the end of the clip (a multi-hit's from its last hit). On block is close, not measured: Fine Print comes out +3 against the +2.5 accountant-test measures. The happy accidents are never listed: the shared table and the character files are the only sources, and the techniques are in neither.

**How it's built.** `site/generate.mjs` writes `fighters/index.html`, `fighters/<id>/index.html`, the How to Play pages (`how-to-play/`, from `site/guide.mjs`), `.site/home.json` (the homepage's fills) and the idle sprites in `public/sprites/`. `site/vite-plugin.mjs` runs it in a fresh Node process before every `vite build` and dev start, lists every page as a build input, fills the homepage's markers from `home.json` (`<!--@roster-->` the cast grid, `<!--@count-->` the fighter count, `<!--@stages-->` the arcade ladder's length; a marker with no fill fails the build), and in dev regenerates and reloads when a character file, the frame data, the rig, `src/flow/controls.js`, `src/flow/ladder.js` or the templates change (and redirects `/play` to `/play/` like the Worker does). `fighters/`, `how-to-play/`, `.site/` and `public/sprites/` are build products (gitignored); run `node site/generate.mjs` to look at them by hand. Templates are plain template strings in `site/templates.mjs` (the header is `topbar()`; `index.html` carries a copy of it, so change both); styles in `site/site.css` (the game's neon: Bungee and Teko, glow only on the wordmarks and a page's one big title (Controls, The look), a plain sans for body copy and tables, square edges, each fighter's page in its own color). `site/site.js` runs on every page: the visit, the install hint, the homepage's FULL SCREEN button, and on a fighter page it loads `site/rigs.js`, which draws the move cards and the big rig live (`createFighter` + `play()`), only while they're on screen, never in a hidden tab, at a lower resolution on phones, and as still poses under `prefers-reduced-motion`. The homepage and the roster load none of the rig code.

**The homepage's content comes from the data where it can.** The cast cards are `rosterCards(..., { cast: true })`: name, tagline, a swatch each of body, pants and accent, and the first three entries of the character's `moveList`. The homepage's copy leads with the story: a TEMP working their way up the office tower, with the modes described in the game's voice. How the game was made (Xiao Xiao, the lighting, rollback) stays in About and Online, and the mechanics live on the How to Play pages. `site/guide.mjs` writes those three pages by hand from the README's numbers (Controls, Fundamentals), so change both together; they hint at the secret boss and the happy accidents but never name them. The controls tables on the rules page are `controlsTable()`, built from `FIGHT` and `MENUS` in `src/flow/controls.js` (the game's own CONTROLS screen table; `FACE` and `PILL` are exported for the gamepad glyphs) plus a touch column keyed by the row's label (`TOUCH` in `site/templates.mjs`, from `src/touch.js`'s layout; a row it doesn't know shows a dash). On phones each control row becomes a small card. The ladder hint reads `LADDER.length`; the secret boss and the happy accidents are hinted, never named.

**The embedded game.** The homepage's frame is just `<iframe src="./play/" allow="fullscreen; autoplay; gamepad" allowfullscreen>` showing the game's own attract demo, with nothing on top of it: a click into a same-origin frame focuses it (keys go to the game; the game's keys don't scroll the page) and is the gesture that turns its sound on, and the `gamepad` permission lets a pad work inside it (the policy's default is `self`, which covers a same-origin frame; the attribute says it out loud). The frame is as wide as the page allows, up to 1240px, but never taller than the screen under the header. Under it, a quiet row: FULL SCREEN calls `requestFullscreen()` on the iframe (and locks landscape where it can); where the element has no fullscreen (iPhone Safari) or the browser refuses, it opens `play/` instead. OPEN IN ITS OWN PAGE links `play/`. On a phone held upright (`(orientation: portrait) and (pointer: coarse)`) the frame is too small for thumbs: it still shows the demo, an invisible link over it opens `play/` on a tap (so a swipe there scrolls the page instead of landing in the game's touch layer), FULL SCREEN gives way to a big PLAY FULL SCREEN button, and the copy drops "click the game, then press Enter". A phone on its side gets a one-row header that scrolls away and a frame sized so header and frame fit the screen. Inside the frame the game only changes two things: `src/root.js` exports `EMBEDDED` (`window.top !== window`, in a try/catch, true if reading it throws), `src/install.js` then offers no INSTALL (the browser never fires `beforeinstallprompt` in a frame; the homepage around it has the install hint) and marks `<html class="embedded">`, and the visit is labeled `embed` (see Analytics). The redirect script never runs in the frame, since the frame loads `play/` itself. The update pill works inside the frame as on the game page. Note the cost: the frame runs the whole game, WebGL lighting and all, so on a slow phone the homepage costs what the game does (see the measurements below).

**Roster sprites.** The roster cards (the homepage's cast and `/fighters/`) don't run the rig in the browser: `site/sprites.mjs` draws each fighter's idle loop at build time with the game's own rig (`createFighter`, `setBody`, `draw`, in its body, colors, pants and the cards' glow and floor light) on [`@napi-rs/canvas`](https://github.com/Brooooooklyn/canvas) (Skia with prebuilt binaries for macOS and Linux, a devDependency, so `npm run build` needs no browser), into `public/sprites/<id>-idle.webp` (12 frames of 160x200 side by side) and `<id>-idle-2x.webp` (no `@` in the name: Cloudflare answers `@` with a redirect to `%40`). The idle clip is four 400 ms keys, so the loop is 1.6 s, sampled every 133 ms after 2.4 s of settling (checked: the joints at t and t+1.6 s match exactly). The sheets are drawn on the card's panel color (`PANEL` in `site/sprites.mjs`, `--panel` in `site.css`; keep the two together): an opaque sheet is about a fifth the size of one whose soft glow sits in a lossless alpha channel (WebP quality 75: about 17 KB at 1x and 38 KB at 2x per fighter). A card shows the sheet as a lazy `<img srcset>` twelve boxes wide inside an `overflow: hidden` box, slid a box at a time by a CSS `transform` animation with `steps(12)`, so the compositor runs it with no script and no repaint; cards start out of step (`--i`), and `prefers-reduced-motion` shows the first frame. A registered character that can't be drawn fails the build. The fighter pages keep their live rigs (measured cheap, below).

## Analytics

Cookieless and with no player ids, names or emails: the page sends small events to its own Worker (`src/analytics.js` → `POST /stick-fight/api/e`), which writes them to Cloudflare **Workers Analytics Engine**, dataset `stick_fight_events` (binding `EVENTS` in `wrangler.jsonc`). Off on `?scene=` pages, on localhost, and when the browser sends Do Not Track. The Worker only accepts a fixed list of event names, cuts labels short, and rate-limits per IP (`EVENT_LIMIT`).

| Event (blob1) | Labels (blob2…) | Number (double1) | Sent by |
|---|---|---|---|
| `visit` | touch or mouse, app or web, referrer host, direct / crew-link / room-link, page (`play`, `home`, `fighters`, `fighter:<id>`, or `embed` for the game inside the homepage's frame, so a homepage visit counts once as `home` and isn't also a `play`) | | page load, on every page |
| `install` | | | the browser installed the app |
| `mode` | arcade / horde / training, fighter | | starting a mode |
| `stage` | fighter | stage reached | arcade |
| `arcade_end` | fighter, over / clear | last stage | arcade |

## Arcade flow

Plain `play/index.html` (the game, at `/stick-fight/play/`) runs like a cabinet. Everything around a fight is one state machine in `src/flow/index.js`; every move between screens goes through one `go()` that refuses any move not in its transition table, so a double press can't skip a screen.

**Every screen** that waits on the player has at least two buttons you can reach with the keyboard, the pad, a tap or the mouse, opens with the focus on its main action, and shows a footer legend of what each key or button does there (see Controls, Menus). MAIN MENU always means the mode select.

**Title (attract).** Two CPU fighters play one round under the title, with START, HIGH SCORES and CONTROLS buttons and a DEMO tag. Between demo bouts a high score table shows for 7 seconds, like a cabinet's attract loop; the arcade and horde tables take turns. The demo is silent; at most the music keeps playing.

- **Only START starts.** Tap or click the START button, press Enter, Space or A with it focused (it is, when the title opens), or press Start on a gamepad from anywhere on the title. A tap or click anywhere else, and every game key, only wakes the sound (browsers keep a page silent until it's touched). The sound button, its panel and the SOURCE & CREDITS link don't start anything either.
- The START button sits where the title card's prompt is and fades the same way when a fighter is under it; HIGH SCORES and CONTROLS sit in a row under it. CONTROLS is the full fight and menu table, keyboard and gamepad side by side, with a note on the parry, the getup options, the stomp and the air recovery, and MAIN MENU and BACK.

**Mode select.** ARCADE, VERSUS ONLINE, HORDE, TRAINING, the two match rules (ROUNDS and TIME, below), and BACK to the title. The mouse hovers and clicks, and a tap picks.

**Character select** (`src/flow/select.js`, the `charSelect` state) comes after every offline mode (arcade, horde, training; online play picks in the room instead, below). A grid of the registered roster (see Characters), six columns of tall cards so three rows hold all 18 fighters beside the sheet (a character still `null` simply isn't there; a name over nine letters goes smaller and may wrap to two lines), each card a live idle rig in that character's neon, and a sheet for the one under the cursor: a bigger rig that throws one of its unique moves every few seconds, the name and tagline, stat bars (power, speed, health, stamina, weight) and its unique moves with their inputs. Keys, D-pad and stick move the cursor; Enter, A or the PICK button picks; Esc, B or the BACK button goes back. A tap only focuses a card and a second tap picks it, so a stray touch never starts a fight. Arcade goes on to the first stage card, horde straight into the run (the goons stay TEMPs), and training asks a second time, PICK YOUR DUMMY. The cursor starts on your last pick, in any mode and online too (kept in localStorage as `stick-fight-last-pick`, so it survives a reload); a `?pick=` link beats it for that visit. The cards it isn't on sit back (a faint border in the fighter's color, no glow, the rig dimmed), and the focused card lifts, scales up a touch and glows with a fill in its color, the same for mouse, keys, pad and touch. On the online pick screen your card is tagged YOU and the rival's carries an amber dashed frame and a RIVAL tag (lime when ready), and both read when you're on the same card. MOVE LIST (the footer button, F1, or pad Y) opens the highlighted fighter's full move list over the screen (see Controls, Move list).

**Match rules.** ROUNDS cycles BEST OF 3 (the default), 5 and 1; TIME cycles 99 seconds (the default), NO LIMIT, 30 and 60. Each press steps to the next choice and remembers it (`src/flow/rules.js`, localStorage `stick-fight-best-of` and `stick-fight-round-time`). Both buttons are on the mode select and in the pause menu (not in horde, which has no rounds), and take effect from the next fight. `setScene()` in `src/main.js` puts them on the sim as `sim.winsNeeded` (2 for a best of 3) and `sim.roundTime` (0 for no limit: the clock never runs and never times out) for the arcade, horde and training fights; online uses the host's (they ride the start message), and the attract demo and every `?scene=` page use the defaults, so the test timelines don't change with a player's settings. A match ends when someone has `winsNeeded` rounds, or after `2 × winsNeeded − 1` rounds when the last one is a draw. Horde uses the round time for each goon's clock. `sim.roundClock` counts the seconds fought in a round whatever the limit (the demo AI saves the floor break for after the first 14).

**Arcade.** Six stages up the building, best of 3 rounds each by default (see Match rules), against a named CPU that gets harder and plays its own way (opt-in AI styles in `src/combat/ai.js`). Each stage is a roster character (`char` in `src/flow/ladder.js`); `buildLadder(pick)` makes the run's ladder. You don't fight yourself: a stage whose character you picked is taken by ACCOUNTANT ("read the fine print. then the overhead"), then WINDOW WASHER, in that stage's slot (number, CPU, look, floor). If you pick THE MANAGER, the boss is the HEAD OF SECURITY (SECURITY, "nobody gets past the front desk") and an extra takes SECURITY's stage. A stage whose character isn't built yet fights a TEMP under the stage's own name and color, so the ladder works while the roster fills in.

**Perfect rounds.** A round the winner ends by KO without taking any damage (the 5,000-point perfect in the score table) ends with a show: the winner throws the beaten body into the camera. The body grows as it flies at the lens, hits the glass full screen with a thud, a crack and a shake, is squashed flat and splayed, then squeaks down the glass in jerks, leaving a smear, and drops out of the bottom. Then the round goes on as usual: the KO hold, the next round or the WINS banner, and the celebration dance on a match win. It plays in every mode with rounds (arcade, versus online, the attract demo, the `?scene=` fights) and never in horde. A time-out isn't a KO, so it never gets one.

- **It's sim state.** `src/combat/sim.js` decides it from the sim alone, inside the existing `ko` phase, so both machines in an online match play the same frames and agree on the end. Once the KO'd body comes to rest, the KO checks the winner's health against his full bar (`perfectReady()`); if he's in the air or reeling he gets up to 1.5 s to land, or there's no show. Then the winner (state `perfect`, no input) runs at the body for up to 0.7 s, stopping at its near end, and plays his character's `<id>_perfect` clip. The clip's `grab` key takes the body off the floor (the unit is hidden from here on and never joins the pile), its `release` key throws it, and its last key is the pose he holds after. The clock after the release is `PERFECT` in `src/combat/frameData.js`: the flight until 0.42 s, stuck on the glass until 0.7, sliding until 1.75, gone at 2.15. The sim fires `perfectGrab`, `perfectThrow`, `perfectSplat`, `perfectSlide`, `perfectDrop` and `perfectEnd` at those marks for the sound and the shake. A finisher takes about 3.0 to 3.4 s from the body coming to rest (all 18 measured with `perfect-test`). The new state is `sim.perfectT` (-1 undecided, -2 none, else seconds in), `perfectRel`, `perfectWait`, `perfectOn` and `perfectSkip` in `SIM_SCALARS` and the state hash, plus plain unit fields (`pfStage`, `pfFar`, `pfFrom`, `pfRel`, `pfGrabT`, `pfMask`). `NET_VERSION` is 22.
- **Skipping it.** A fresh press of any button (1 to 4, jump or guard; one held when it starts doesn't count) after its first 0.3 s skips to the end. Offline any player's press skips it, never a CPU's. Online only the winner's press does (`sim.perfectSkip = 'winner'` in the `online` scene): it's the winner's show, and a press is part of the inputs both sims already share, so both skip on the same frame. A skip cuts the squeak.
- **On another level.** When the body landed on another floor or a flight the winner can't walk to (`sameLevel()`), he plays the throw where he stands and the body leaves the floor where it lies at the release.
- **How it's drawn** (`src/fx/perfect.js`, drawn only; it never writes to the sim). From the grab to the release the body is the loser's own rig drawn with joints put together in its hand, on the figures layer so the room lights it like the winner: hung by the collar or the ankle on a damped pendulum that the hand's acceleration swings, or laid across the hands (`carry`). From the release it's drawn on the HUD canvas in screen space, under the HUD, so the bars stay on top and the PERFECT banner moves up into the strip. In flight its depth closes linearly, so it grows the way something coming at you does, with whole-turn spins or flips that land upright, its arc, two fading copies behind it and speed lines from the middle of the screen. On the glass it's sized to 92% of the screen's height. Fighters stay flat solid color. Only the glass marks glow: the crack, the streaks the hands and head leave, and the stamp. The splat also has a white flash and its own shake on top of the world's. The 16:9 stage letterboxes on a phone either way up, so it works on phones in both orientations.
- **Sound** (`src/audio/sfx.js`): the throw's swelling whoosh (`perfectWhoosh`), the body on the glass (`glassThud`: a padded thud, the pane's ring and the crack running out) with the music ducked under it, the squeak (`squeak`: rubber on glass, a squeal that jumps up in pitch on each of the slide's six slips and sags as it goes down, on the same beat the drawing slides on), and a little `unstick` as it peels off.

**Tested.** `?scene=perfect-test&p1=<id>` puts any fighter against a dummy that never fights back, with a low health bar, so every round is a perfect KO and ends in the finisher (`&p2=<id>&p2win=1` makes P2 the winner instead, `&hurt=1` takes a point off the winner each round, which is the same KO with no finisher). Skipping, in Node: a player's press 0.6 s in skips it offline whether he won or lost; a CPU winner's presses never do; online (`net` on both, `perfectSkip = 'winner'`) the winner's press skips it and the loser's doesn't. **High scores.** A top-5 table for arcade and one for horde, kept in localStorage as `stick-fight-scores` (the origin is shared with the rest of askscottpierce.com). After a game the table has CONTINUE (back to the title) and MAIN MENU; from the title or the attract loop, MAIN MENU and TITLE; either way a third button swaps the arcade and horde tables. The attract loop's table turns over after 7 seconds; one the player opened or just signed waits for 30 idle seconds. A score that makes the table gets three initials: type them, or pick them on the on-screen keyboard (D-pad and A, or tap), then ENTER. DEL (Backspace, pad X) steps back a slot. Left alone for 30 seconds the initials go in as they stand.

**Horde** is the floor-by-floor mode, scored the same way; it ends when the hero goes down, then GAME OVER, initials and the horde table. **Training** is the dummy scene, no score.

**Pause** (P, Esc, pad Start or Select, or the small pause button in the top-left corner on a touch screen) in arcade, horde and training: RESUME, MOVE LIST (the fighter you're playing; F1 or pad Y open it too, see Controls, Move list), RESTART STAGE (RESTART RUN in horde, RESET in training), BOTCHES ON/OFF, ROUNDS and TIME (Match rules; not in horde), SHOW CONTROLS (swaps the right panel between the techniques found and the fight controls, keyboard and gamepad), MAIN MENU. P, Esc, Backspace, B or Start resumes. Nothing runs while paused, the round clock included.

**Idle.** 30 seconds with no input goes back to the title only where nothing is lost: mode select, the online menu and join screen, the profile screen, the end of a quick-room match, and training. Never the crew lobby (friends wait there), the typing screens, or sign-in (the code takes a trip to the inbox). Never mid-match: an arcade or horde run left alone plays itself out (the CPU or the goons win), CONTINUE runs down, a table score is entered as it stands, and the cabinet is back on the demo. A paused game stays paused. An online match never times out, and neither do the screens between matches in an online room (post-match and NEW CHARACTERS): only a player's own LEAVE ROOM or MAIN MENU, or the other player leaving, ends a room.

**Versus online.** The first time a player goes online (VERSUS ONLINE, a `?room=` link or a `?crew=` link) the game asks for a name first: WHAT DO WE CALL YOU?, 3 to 12 letters, digits and spaces, typed or picked on the on-screen keyboard, with OK, SIGN IN (a returning player on a new device restores the profile instead) and BACK. The crew screens, the profile and sign-in are under Multiplayer, Crew rooms and Profiles and sign-in. When a match ends the room stays open and both players get the post-match screen (below). When a connection ends, or the other player leaves, the notice says why, with ONLINE MENU and MAIN MENU, plus HOST AGAIN or TRY AGAIN when a room didn't open or a join didn't connect. See Multiplayer for the network side.

**After an online match** (the `onlinePost` state) both players see the result (YOU WIN, YOU LOSE or DRAW, the match number, the fighters, the rounds), the room's running tally from their own side in big type (YOU 3 – 2 RIVAL, then the rounds, draws, and the all-time record against this rival when there's more than this room's), and REMATCH, NEW CHARACTERS, LEAVE ROOM and MAIN MENU, with REMATCH focused. The point is to keep a session going with as few presses as possible:

- **Nobody does anything:** REMATCH IN 5 counts down and the next match starts with the same fighters, so a couch session keeps going. Any press from either player (a direction, back, another button) stops it.
- **REMATCH from both** (one press each, in either order), or from the host while the guest hasn't said anything: REMATCH IN 3, then it starts. The host pressing REMATCH again starts it at once. The guest can hold it with back or WAIT, or by choosing NEW CHARACTERS.
- **The guest's choice is a request.** The host's screen says RIVAL WANTS: NEW CHARACTERS and marks that button, and the host's cursor jumps to it (unless the host moved it in the last second; a press within 0.3 s of the jump doesn't count), so one press accepts. The guest's screen says what the host's cursor is on (HOST IS ON: REMATCH) and what the guest asked for.
- **The host's choice is final.** NEW CHARACTERS from the host takes both to the pick screen at once. REMATCH from the host over a guest who asked for something else is the host's call: REMATCH IN 3 that only the host can stop (back or STOP), and the guest's screen says HOST'S CALL. Back, or the STOP button beside the countdown, stops any countdown on the host's side.
- **LEAVE ROOM** goes to the online menu and **MAIN MENU** to the mode select, for either player, at once; the other player gets YOUR RIVAL LEFT (a host's notice then offers HOST AGAIN first: a fresh room in one press). Back on this screen never leaves: it's WAIT for the guest and STOP for the host. STOP or WAIT sits beside the countdown and is dim (and skipped by the focus) while there's no countdown you can stop.

**The online pick screen** (the `onlineSelect` state) is the character select for both at once. Every room opens on it before the first match (titled VS and the rival's name; a crew match puts the crew's name at the front of the subtitle), and NEW CHARACTERS brings both back to it between matches. It opens on each player's last pick (or the fighter from a `?pick=` link) so one press confirms it. LEAVE ROOM backs out to the online menu (BACK TO CREW in a crew match), and a rival who leaves or drops here gets the same YOUR RIVAL LEFT or CONNECTION LOST notice as between matches, with HOST AGAIN for a host. Under the title a line reads YOU: PICKING or YOU: READY · COURIER, and RIVAL IS PICKING… INTERN (the rival's card under their cursor, live) or RIVAL READY: INTERN; the rival's card wears a RIVAL tag (green when locked in), and the subtitle carries the match number and the tally. PICK (Enter, A, or a second tap) locks your card in; back un-readies (CHANGE), and never leaves the room. The footer has LEAVE ROOM and PICK, and for the host START. Once both are ready the host's START lights up and STARTING IN 3 runs (START starts at once; either player un-readying stops it). The guest sees WAITING FOR HOST. If the guest hasn't sent anything (no cursor move, no pick) for 20 seconds while the host is ready, START lights up anyway as START · RIVAL: INTERN and starts with the guest's current card: a guest who walked away doesn't hold the room hostage, but the host has to press it; nothing starts without a ready guest on its own.


**Touch.** The stick and the buttons show only while fighting; menus are tapped directly. The sound button stays in the top-right gutter on every screen.

**Swallowed presses.** On every screen change, whatever key or button is held is ignored until it's let go, both by the menus (`menuInput.swallow`) and by the fighter (`input.swallowHeld`), so the press that changed screens never acts on the next one or throws a punch. A round rolling over mid-fight isn't a screen change, so a held guard stays held. STAY on the online confirm swallows its press too.

**`?scene=` URLs skip all of this** and behave as before: the scene they name, no menus, no timeout, and the old hotkeys (G horde, R reset, P pause). `?scene=attract` is the old demo, where any key starts `play`. `__gauntlet.setScene` and `__game.setScene` also turn the flow off, so the capture tool works on plain `index.html` too.

Each demo bout draws a random pair from the registered roster (a mirror match gets the alt color). The demo fighters are the CPU at difficulty 10 in its **showcase** flavor (`sim.setAI(i, 1, { style: 'showcase' })`, `src/combat/ai.js`): it keeps spacing at the edge of reach, steps out of pokes and punishes the whiff, reads and guards highs, mids and lows, opens with string starters at all three heights instead of jabs, blocks rather than mashing out of hitstun, keeps its stamina up (it never presses the strike that would faint it), jumps in and meets jump-ins with an uppercut or a standing guard, and saves the stairwell for later in the round. THE MANAGER fights the same way.

**Human reaction time** (2026-11-09; the owner and his son couldn't get past SECURITY, who "counters all my hits immediately"). Every CPU reflex used to fire on the first sim step of what it answered, about 8 ms, where a person needs 200 to 250 ms to see a move. Now each reflex that answers the opponent (the guard, duck and parry at a strike's startup, the whiff and botch punishes, the anti-air reads, the wake-up answer to a strike at the body, the faint punish, the characters' reflex specials like LAWYER's Objection) sees him as he was some steps ago: 330 ms at difficulty 0.2, falling evenly to 180 ms at 1.0 (the showcase 20 ms quicker, never under 160), plus up to a fifth more, re-rolled after each reaction. `perceive()` in `src/combat/ai.js` keeps a ring of shallow copies of the opponent, one a sim step. A reaction to something that is already over (the strike landed, the whiff recovered, the jumper touched down) is dropped. So a jab (13 steps of startup, 108 ms) or a cross can't be reacted to at all, and a CPU only stops one with a guard it was already holding: the **habit guard**, a guard on a hunch now and then inside your reach while you've been swinging (3% plus 6% of its difficulty per think, a third of them low; the turtle a little more). Slow strikes, overheads and command grabs are still read and guarded. It's all sim step counts and the sim's rng, so `?scene=` pages and recordings replay identically. `NET_VERSION` stays 14: only `ai.js`, `ladder.js` and the flow changed, an online match drives both fighters with the netcode's `net` controllers (the `online` scene in `src/main.js`), so no CPU ever runs under rollback, and nothing in the sim or the snapshot changed. The timeline test scenes script both fighters, so they can't move either; `getup-test`, `parry-test`, `stomp-test`, `air-recovery-test` and `string-test` end on the same health as before.

**No instant counters.** Two things made the CPU hit back the moment your hit ended. The swing-back reflex fired 55% plus 60% of its difficulty of the time (97% at the old SECURITY). The bigger one wasn't in any table: the CPU kept planning while in hitstun, picked a strike, and the sim buffered it onto the first free frame. Now nothing is planned in hit- or blockstun, the first plan after waits half a reaction time, and the swing-back is decided one reaction time after your last hit landed: 3% plus 40% of difficulty squared, capped at 40% (5% at the INTERN, 15% at SECURITY, 29% at THE MANAGER's 0.8, 20% for the showcase). Otherwise half the time it just eats it and resets, a short guard or a step back out of range. The other chances that came near certain at the top were trimmed: the guard reflex at a startup it saw is 10% plus 50% of difficulty (was 65%, the turtle +15 not +25; 70% for the showcase, was 85%), a whiff or botch it saw is punished 30% plus 45% (20% plus 45% on a strike that connected; was up to 100%), the botch reflex 20% plus 50% (was 25% plus 60%), the turtle's and showcase's whiff punish 45% plus 30% and 75% (both were 85%), the old anti-air uppercut 10% plus 50% (was 15% plus 65%), and the grappler's close throw 10% plus 27% of difficulty (was a flat 40%; 25% at SECURITY's 0.55), with its dash-in throw approach at 20% plus 20% of difficulty (was 45%).

**Breathing room.** After the CPU lands a combo of 3 or more hits, or while it leads by 30% of the health bar (tried every 1 to 1.5 s), it takes a breath of 0.4 to 0.7 s: it walks off, stands, or drifts, with a rare short guard, and doesn't swing, doesn't meaty you on the floor and doesn't swing back out of hitstun. An opening you hand it (a whiff it saw) is still punished. The top of the ladder skips more of them: every one below 0.7, 85% at THE MANAGER's 0.8, 55% at 1.0, 40% for the showcase. Not in horde.

**Anti-airs.** Every CPU decides, when it sees your takeoff (a reaction time after it happens, and only if you're still in the air), whether it read the jump: 12% at difficulty 0.3 or below (INTERN mostly gets jumped on, but not always), then rising with difficulty to 65% (was 80%; 75% for showcase, was 85%; +15% for the aerial style). A read drops whatever it was doing, stands its ground until you come into the uppercut's reach about when it would go live, and presses d+2 (a jab instead if you're already on top of it with a strike out); a jump that will land short is let land. A CPU that doesn't read it still has the old once-per-jump uppercut reflex.

**Stamina and faints.** No CPU presses the strike that would empty its bar, except that the bottom of the ladder slips now and then ((1 - difficulty) x 40% of the times it would, never the showcase), so INTERN and HELPDESK faint a round or so and THE MANAGER doesn't. A CPU under about 30 stamina backs off or guards while it refills, and only starts a string's ender when the rest of the string fits in the bar. It knows the refunds (Controls, Stamina): after a clean hit it counts the rest of the string at half price, and a string's next press only needs the bar to hold half that press's price, since a press that empties the bar and hits leaves it standing. When you faint it runs in and opens a string on you: 35% plus 65% of its difficulty of the time, every time for the showcase. **Fainted itself, it shakes its head at a human pace** (`shakeOff()` in `src/combat/ai.js`, decided once per faint; it no longer staggers away, since a fainted body can't walk). It starts a reaction time in, and how often it shakes and how cleanly both go up with difficulty. The showcase always shakes, a press every 14 to 16 steps where 12 is the best allowed. The bottom of the ladder shakes in about half its faints, on a slower beat, sometimes pressing the same way twice or missing a beat. Measured over 40 faints each with nobody hitting it (`node gauntlet/measure.mjs cpufaint`, average / best): difficulty 0.1 1.40 / 1.20s (it shook in 43% of them), 0.3 1.34 / 1.10s (53%), 0.5 1.27 / 1.10s (68%), 0.7 1.18 / 1.00s (75%), 0.9 0.99 / 0.90s (95%), showcase 0.90 / 0.88s (100%).

## Controls

Tekken-style, one button per limb, from the fighter's own point of view:

| Key | Button | Limb |
|---|---|---|
| U | 1 | left punch (jab) |
| I | 2 | right punch (cross) |
| J | 3 | left kick |
| K | 4 | right kick (roundhouse) |

- **Move** A/D or arrows. **Hold back** (away from the opponent) to step back, Tekken style: you walk back (at the character's back-walk speed; TEMP's is the forward walk's) and the guard snaps on by itself only when a strike is coming that can reach you (one in startup or out, inside its reach plus any slide or charge travel plus a little, about to go live) or a jump-in is closing. It holds through blockstun and a beat after, then you're walking back again. Standing guard stops highs and mids, lows go under it (and don't make you snap: down-back is the answer), and throws beat it. A hit that lands while you hold back in a guard-capable state (walking back, idle, crouching back) is blocked even if the snap missed a frame. B, and the touch GUARD button, mean the same as holding back, so they walk back too. Walking back costs no stamina; blocking costs what it always did, and the guarding regen rate applies only while actually blocking.
- **Crouch** S or down. A crouch ducks highs completely; **down-back** guards lows. Mids hit a croucher.
- **Jump** W, **run** Shift (or double-tap forward). **Throw** 1+3 or 2+4; the same press during the grab breaks a throw. Throws can't be guarded, but they whiff on a croucher.
- **In the air:** jump with W (hold a direction for a forward or back jump; you can steer a little in the air), then 1 jump jab, 2 jump cross, 3 flying kick, 4 air roundhouse (knockdown), down+4 dive kick (cuts the jump short). One air attack per jump, plus a quick jab on the way down once a whiffed one has recovered. Juggled, a button at the right moment recovers you onto your feet. See Fundamentals, In the air. Air attacks are overheads: they hit a croucher, so guard them standing. Land a jump-in hit and keep pressing for a ground string; whiff one and you land with a short lag. An uppercut (d+2, or rising 2) meeting a jump-in is a counter hit that launches; a jab stuffs a late one. In the rig an air attack eases its hip onto the jump's arc over its startup (and a dive kick never climbs the arc, it drops from where it was). Its homing lunge (up to 70px toward the defender) and torso swing don't land in the 50ms pre-roll the sim skips: the head travels in a straight line, evenly over the frames from the press to the moment the strike can hit, and the hips carry the difference; from then on, and at contact, the body is exactly where it was before. The jump's push-off is drawn with softer eases than the arc air attacks ride, so takeoff has no big frame. Leaving the air for anything grounded lowers the hip over 160ms (220 after a dive) instead of in one frame; a strike thrown on landing finishes that descent by its contact key, so it lands at standing height. Where the head still has to travel farther than 20px in one frame to make contact (a jump jab or dive kick from far out, a landing push-apart, the stairwell vault and its handoff to standing), `drawOffset()` in `src/main.js` holds the drawing to 20px per 60fps frame and lets it catch up. It's visual only: hit detection, contact and the netcode state use the real positions. A connecting strike snaps the drawing to the real pose on the contact frame, under the impact flash, so hits always draw touching. Launched, thrown and juggled bodies draw raw. On the ground the same idea is `frameDraw()`'s turnaround and snap fade (Controls, Sides).
- **Parry:** tap toward the opponent (down-forward for a low) just before a strike lands. Not a hold, and not too early: see Fundamentals, The parry.
- **Over a body on the floor:** down + 4 is the Stomp, and a low that visibly touches the body (down + 3, the low kick; down + 1, the low jab; a character's lows) is a lighter ground hit, once per knockdown (Fundamentals, Hitting a body on the floor).
- **Knocked down:** you stay on the floor until you pick a getup option: **up** stands in place, a fresh press **away** from the other fighter rolls back and keeps your side of him, a fresh press **toward** him rolls toward him (under him to his other side if he's standing over or near you), and **any button** is a wake-up strike from the floor (1 or 3 the Wake Kick, 2 or 4, or anything with down, the Wake Sweep). Leave it alone and you stand up by yourself after 1 second. Every way up rises on your own side of him, facing him; only the roll under him changes sides. See Fundamentals, Getting up and Sides.
- **Crouching:** all four crouch attacks come out of a crouch or a crouch-walk (hold down and forward) without standing up, and you stay down after a low while down is held. d+1, d+1, d+3 is the Low Rush string. On touch, stick down plus a button.
- **Directions:** d+1 low jab, d+2 uppercut (launcher), d+3 low kick, d+4 sweep, f+1 body blow, f+2 lunge cross, f+4 overhead (mid, beats crouch), b+4 spin kick. Release down, then 2 = rising uppercut, 4 = rising knee (both launch).
- **Heights:** high = jab, cross, roundhouse, spin kick, spin heel. Low = low jab, low kick, sweep. Everything else is mid.
- **Stamina** (the thin bar under health, out of 100) is your attack budget. Jab 17, low jab 15, cross 21, body blow 19, lunge cross 22, low kick 18, the other kicks 22, launchers 24, throws 22, any ender 30; air attacks 12 to 18, a jump 8, running 14 a second (running stops at the last point, it never faints you). Mashing jab empties it on the 6th press, crosses and kicks on the 5th. A full four-hit string fits from full but leaves you low (1,1,2,4 costs 85, 1,2,3,4 costs 90, Sky Spike 92). **Landing hits gives some back** (`STAMINA.refundHit`, `refundBlock` in `src/combat/frameData.js`): a strike that hits refunds half of what it took the moment it connects, a blocked one a quarter (armor soaking it counts as a block), and a whiff, a parried strike or a botch nothing. That goes for strings, enders, juggle hits, the stomp, throws that land (a broken one gives nothing), character moves and wake-up strikes, once per strike. The **repeat decay** (`refundRepeat`, 1.5s): the same move refunded again within 1.5s of the last refund gives back half as much each time (jab, jab, jab on hit: 8.5, 4.25, 2.1), so mashing one button doesn't pay for itself, while a string of different moves keeps it all. NEON TORNADO on hit costs 90 and gets 45 back; two juggle jabs after it (8.5 back, then 4.25) and the stomp (9 back) leave about 25 from a full bar even with no regen in between (refund-test). The bar ticks up as each refund lands, and the gained piece flashes cyan on the bar and the overhead track for 0.45s. It comes back at 90 a second once you've gone 0.3s without spending (none while attacking or running), and at 36 a second while guarding, so it refills in about a second of walking. **Knocked down, it refills to the top:** the bar fills (with a white flash on the bar and the overhead track) the moment you hit the floor, from a hit, a throw, a trip, a floor break or a stair tumble, and a faint ends there too. Blocking a hit costs a third of its price and never takes the last point. Under 35 the bar turns pink and flashes LOW.
- **Sides:** you keep your side of the opponent, and sides only change through motion you can see. Classic 2D fighters work the same way: solid pushboxes that always resolve toward each body's own side, jumps that cross over, specific throws and moves that visibly carry someone past, and a turn when facing flips. Here:
  - **Bodies are solid and push back toward their own side.** When two standing bodies overlap, each is pushed back toward the side it was on when the step began (`separatePair()` goes by `prevX`, a pushbox), so a lunge, a glide or a slide into someone never comes out the far side. A body is moved at most 6px a step by the pushing apart (`SEP_CAP`, 720 px/s), so a deep overlap (a getup turning solid under someone at the wall, a landing on top of someone, a body coming to rest past the man standing over it) is a visible shove over a few frames, never one snap.
  - **The root goes where the body is.** A travelling clip (a cross's step, a stagger, the getup's rise, a botch's stumble, the vault) moves the rig's root when it ends or is cut short; the sim's root follows it the same step (`takeRoot()` after every rig update, and `safePlay()` around every `play()`), so the drawn body never jumps back by the step. The getup used to stand the fighter up at his old root, a body-length from where his hip lay, often on the far side of the man standing over his legs: that was most of the "teleports". Now he stands up where his hip is, on his own side. A body getting up isn't slid along the floor (its feet may be past the wall, its hip never is), and a body coming to rest from a tumble keeps the root and facing the rig gave it (a clamped root or the old facing re-posed it a body-length away).
  - **Lying bodies.** You can stand over a body on the floor (and step farther in under a juggled one): at its feet up to its drawn feet (84 px from its hip, `lieEnds()`; it used to be its root, a body-length past the feet, which kept every low but the stomp off the legs), at its head side no closer than 10 px short of its hip (`HIP_GAP`). You can't walk, run or lunge out the far side of it, and a body rolling or sliding along the floor stops under you. A body getting up rises on its own side, because a standing fighter can only reach a little way onto it. Sides and facing go by where a lying body actually is (its hip), since its root sits at its feet. After a knockdown the attacker's ride (he follows the launch to be on the body when it lands) stops at the body's near end, a string's chase step stops at contact, and a body getting up is pushed apart by the sides the two had. A body against the wall slides off it (300 px/s), and a rolling one stops against that pad instead of being thrown out of it.
  - **What still changes sides:** jump cross-ups (a real arc over him), launches and juggles that carry the body over, a floor break and the follow-down vault, a roll, Window Washer's double jump and wall jump, Janitor's Mop Spin landing behind him (`bothSides`), and a body sliding under a standing fighter. Hits knock the defender away from the attacker, not the way the attacker faces, and a roll faces the opponent. A throw holds the victim 70px in front: he is pulled there at 720 px/s over the grab's first frames (`grabTo`), never put there, and one caught behind the thrower turns the thrower round instead of passing through him.
  - **How it reads on screen** (`frameDraw()` in `src/main.js`, visual only: hit detection, contact and the netcode's state keep the real pose). A grounded fighter whose facing flips is drawn turning on his feet over 100ms, squashed horizontally about his root from the old facing through zero to the new one, instead of mirroring in place. Anything that would still move the drawn body farther than 18px in one frame, far more than it moved the frame before (a lying body re-posed for a roll, a knockdown clip snapped to its landing), is cross-faded from where it was drawn over 110ms, relative to the root so the root's own motion passes straight through. Launched, thrown, falling and ragdoll bodies draw raw, air moves keep `drawOffset()`'s catch-up, and both end on a hit's contact frame, so hits still draw touching. Last of all the floor guard (Floors, Bodies on the floor) keeps every drawn joint on top of the surface under it. The one instant relocation left in a fight, a body jammed in the stairwell set down on the floor (`unwedge()`, the `relocate` event), leaves an afterimage where the body was and a flash at both spots.
  - **Measured** with a logger (40 CPU fights across all nine characters, three seeds by 90s each, plus the attract showcase, horde-ai, horde-floors-ai and floor-break-test; drawn head and hip per 60fps frame after the smoothing, side swaps by `bodyX()`, every write to a unit's `x` trapped with its stack): see Characters, **Measurements (side swaps)**.
  - Each fighter's walls come from the floor he's on, so after a floor break the attacker upstairs isn't pulled across to the lower floor's wall before he vaults.
- **Faint:** spend the last point and you faint. **A strike that empties the bar waits to see whether it connects** (`u.faintPending`): if it hits, you're left on 1 plus its refund with the bar flashing LOW, and no faint; if it's blocked, parried, broken or whiffs (into its recovery with no contact, or you're hit out of it), you faint then. The save needs the bar to have held at least half the strike's price at the press (`STAMINA.saveShare`); pressed on fumes, you faint at once, as before, so a fighter on 1 can't jab forever on hits that leave him on 1. A jump, a botch or anything else that empties the bar faints at once. Once fainted, the strike that emptied the bar still comes out, but nothing cancels out of it; once you're back on your feet you're out on them for 1.5s (the dizzy sway, a FAINT callout and a violet bar refilling): no attacks, no guard, no crouch, no jump, no run, and no walking either, because you're rooted where you stand (hits still knock you back as usual). You come to with 30 stamina. A knockdown, a launch or a throw wakes you early, and so does taking 20 damage while fainted, so it's a free string for the other guy, not a free round. Every hit on a fainted body counts in the same combo, so the decay below keeps running through it.
  - **Shake it off** (`shakeOff()` in `src/combat/sim.js`, `STAMINA.shakeGap`, `shakeCut` and `faintMin` in `src/combat/frameData.js`). Left and right, pressed alternately, shake your head clear. A fresh press in the opposite direction to the last one counted, at least 0.1s after it, is a shake: the head whips side to side with the shoulders a little behind it (the `headShake` reaction on the rig's additive layer, over the faint sway), a small "brr" plays, a star flies off the ring circling your head, and 0.1s comes off the faint, so the FAINT bar drains faster. The first press only starts it (the head shakes, nothing comes off). Holding a direction is one press, and pressing the same direction again isn't an alternation, so neither gains anything. A press inside the 0.1s gap is dropped and doesn't count as the turn, so alternating faster than that counts less often than a steady beat: flipping every 42ms clears it in 0.93s, a press every 100ms in 0.88s. A calmer six presses a second gets out in about 1s. The cuts never bring a faint under 0.7s in all, a backstop that the 0.1s gap already keeps you clear of. It only counts on your feet; in hitstun the head is busy reeling. On touch the stick (or a drag) left and right counts the same, and on a pad both the stick and the d-pad do.
  - **How it fits Mashing loses.** The shake is a rhythm with a speed limit. Mashing one direction or holding it does nothing, mashing faster than the limit does worse than a steady beat, and the attack buttons still do nothing while fainted. At its best it turns 1.5s into 0.88s, which is still long enough for the other fighter to walk in and start a string, so a faint is still a punish. Mashers don't gain from it either; see the measurements in Botches.
- **Combo decay:** nothing loops. A button press cancels only as the next hit of a string from the table below, so mashing one button gives you that button's string and then you wait out the recovery (1,1,1 is three jabs; a fourth jab can't cancel out of the third). A move cancels into itself at most once in a row outside a string. Hitstun shrinks from the 3rd hit of a combo (100, 100, 85, 65, 45, then 30%), so a long chain drops and the defender can guard. Damage is full for the first three hits, then 80, 65 and 50%, and once one combo has done 30 damage the rest counts a quarter. Juggles keep their own scaling and the four-hit cap, whichever is lower. Counter hits still do 35% more damage and stun.
- P or Esc pauses (the pause menu, see Arcade flow), F1 shows the quick move strip along the bottom of a fight (the full MOVE LIST is in the pause menu), H shows hitboxes. On a `?scene=` page G toggles horde mode, R resets and P just pauses.
- **Online match:** Esc or P (pad Start or Select, touch LEAVE in the top-right gutter, where HORDE usually sits) asks whether to leave. Pause, reset, horde and the difficulty keys do nothing in an online match; H and F1 still work, since they only change your own screen.
- **Sound:** M turns the music on and off, N skips to the next track. The speaker button in the bottom-left corner (on a phone, the speaker button in the touch layer's top-right gutter) opens the sound panel: a SOUND switch for everything, a MUSIC switch, the track playing with NEXT, and MUSIC and EFFECTS volume sliders. The settings are remembered in localStorage (`stickfight-audio`). Browsers keep a page silent until it's touched, so the first tap or key starts the sound (the button pulses until then).
- **Fullscreen:** on desktop, F11 or the small corner-brackets button beside the speaker button (bottom-left) puts the game in fullscreen and takes it back out; Esc leaves it the browser's way, and the button's icon follows. It works from every screen (title, menus, a fight, the pause menu), and neither the key nor the click reaches the game as an input. A fight's key hints add `F11  FULLSCREEN`. One `toggleFullscreen()` in `src/fullscreen.js` serves F11, that button and the touch layer's fullscreen button; a touch screen only gets the touch layer's. Nothing is offered where it can't work: no Fullscreen API (iPhone Safari), installed as an app, or in a frame that doesn't allow fullscreen (the homepage's frame does). On a Mac, F11 is usually the system's Show Desktop key, so the button is the way in there.
- Gamepad, USB or Bluetooth (any pad the browser reports with the standard mapping: Xbox, PlayStation, 8BitDo, most Android pads): X/Y/A/B = 1/2/3/4, D-pad or left stick moves, L1/L2 guard, R1 throw (1+3), R2 run, Start or Select pause (in an online match, both ask to leave). R3 does nothing in the arcade flow. On a `?scene=` page Select restarts and R3 toggles horde. Menus are in the table below. Pressing any button hides the touch controls; touching the screen brings them back. Browsers don't count a pad press as a user gesture, so tap the screen once to turn the sound on.
- Touch devices get a floating stick (down crouches, away walks back and guards what's coming) and a 2x2 diamond of arcade buttons in the same 1 2 / 3 4 layout plus GUARD (src/touch.js).

### The look

Neon arcade: Bungee and Teko, cyan, pink, amber and violet on a deep purple night, square edges. Never a terminal look.

**Readable text never glows. Only decorative text may.** Glow smears small letters into the busy room behind them, so anything a player is meant to read is a solid color (the same neon family, a little lighter) inside a tight dark outline.

- **Readable, no glow:** menu items and buttons, labels, names, taglines, stats, move names, inputs and notes, hints, legends, status lines, toasts, room codes, typed fields, settings panels, the site's section headings and body copy.
- **Decorative, glow allowed:** the STICK FIGHT wordmarks, the big sign headings (SELECT FIGHTER, PAUSED, GAME OVER, a site page's one big title), arcade callouts and numerals (the combo and round banners, the timer, the continue countdown, the online set score), the digits and icons on the touch buttons, signs in the arena.
- **When it's unclear, it's readable.** A heading that carries something to read (a room code, a player's or crew's name) is plain even at heading size.
- A box's neon border or a button's glowing outline is decoration and stays. The rule is about the letters. Fighters in the arena never glow at all.

How to write it:

- **Canvas (the HUD):** `plainText()` in `src/combat/hud.js` for readable text, `neonText()` for decorative.
- **The DOM:** `PLAIN` in `src/plaintext.js` is the one `text-shadow` for readable text: a firm dark outline with a short dark falloff, never a color.
- **The menus (`src/flow/ui.js`):** `#flow` sets `text-shadow: var(--plain)` (that outline) and everything inherits it, so a new label is plain without doing anything. Only `.fl-h1`, `.fl-h2`, `.fl-count` and `.fl-sn` put a glow back; add `.fl-read` to a heading that carries a code or a name. The move list, the online panel, the sound panel, the controls legend and the touch labels do the same in their own stylesheets.
- **The site (`site/site.css`):** the backgrounds are flat and dark, so readable text is just a solid color with no shadow. Glow is on `.s-logo`, `.s-title`, `.s-h1` and `.s-pillar-n` only.
- Dark letters on a lit chip or a focused button take `text-shadow: none`.
- Never a colored `text-shadow`, a `drop-shadow` filter or a canvas `shadowBlur` on text that's read.

### HUD

The fight HUD is its own 2D canvas over the game (`src/combat/hud.js`), in the arena's neon (Bungee and Teko, no terminal look; glow on its decorative text only, see The look). Nothing on it may cover a live fighter (owner requirement 5): every block is laid out against the fighters' screen boxes and steps aside or fades.

- **The bars.** Two slanted health bars with a thin stamina bar under each (it flashes pink with LOW under 35, and shows FAINT while fainted), round pips at the inner end (one per round win the match needs), and the ringed timer with ROUND under it. The timer is a 33px ring with a 38px number (`TIMER` in `src/combat/hud.js`); its ring drains with the share of the round left, and with no time limit it shows ∞ on a full ring. In the last 10 seconds the ring and number turn pink and pulse once a second: the timer swells about 28% and flares the moment the number ticks over, then settles before the next one, on the sim's clock, so it holds in a pause or a hitstop. In an online fight the room's running tally shows small under ROUND, from your side on both screens: `YOU 3–2 RIVAL` (plus draws when there are any), from `flow.hud().tally`; it fades if a fighter is under it.
- **Name line.** The character's name in its own neon, then a small player marker: YOU or RIVAL online, P1 or P2 for a local player, CPU 7 for the computer at difficulty 7, TRAINER for a test scene's script, the stage (STAGE 3, BOSS) in the arcade ladder. The arcade score sits after it.
- **Move hints.** The line under the name cycles through that character's special moves every 3.6 seconds, input first in amber and then the name: `→→3 EXPRESS SLIDE`, `←2 SHOULDER CHECK`, `↓3, 3, 2 WRITE-OFF`, `1, 2, 3, 4 NEON TORNADO`. It reads the character's `moveList` (src/characters/), so a new character's moves show up with no HUD change. Arrows follow the move lists: → is forward, toward the opponent. Both bars show their own fighter's moves, so it teaches the matchup too. A keyboard screen adds the move list's short note; a touch screen (`touch-ui`) shows just the input and the name, bigger. Happy accidents appear only once this browser has found them (`discovered()` in `src/flow/techniques.js`, read only), as `3 › 4 SCISSOR KICK` in the accident green, and only for a character who can do them.
- **Overhead status track.** A compact readout over each fighter's head (the hero and the one he's on in horde), so you can read the fight without looking at the corners. Only what's active shows, top line first:
  - STUN (hitstun) with a red bar that drains to the middle as the stun runs out; GUARD (blockstun) with a cyan one; GUARD or LOW GUARD, dimmer, while the guard is up; FAINT with a violet bar (it drains faster with each head shake) and two stars chasing round the word; DOWN (or TANGLED after an air botch) while knocked down, with a violet bar draining over the second before he stands up by himself, GET UP with a filling bar; BOTCH during a botch; ARMOR while Security's shoulder check still has its armor; PARRY while Helpdesk's stance is live; OPEN during a whiffed strike's recovery (punish it).
  - Timed statuses (the sim's `status` and `selfStatus` hooks), a small tag each under the main line with a bar draining to the left: WRITTEN UP (pink, HR REP's Write-Up: half stamina regen) and WIRED (lime, BARISTA's Espresso Shot: faster startups). The tag is whatever the move's hook names.
  - SHOCKED (yellow, with the stun's bar) instead of STUN while a shock runs (frame data `shock`, ELECTRICIAN's Live Wire); STANCE while a stance is up (frame data `stance`, WELLNESS COACH's Tree Pose); ROOTED (yellow, a draining bar) while a root holds (frame data `root`, ELECTRICIAN's Ground Fault).
  - Flashes for half a second: COUNTER on the fighter who ate a counter hit, ARMOR when the armor absorbs one, PARRY when a stance or a timed tap catches one.
  - A thin stamina bar under it once any stamina is spent (amber, pink and flashing under 35, violet while fainted); it lingers a beat after refilling and then goes, so an idle fighter shows nothing.
  - Diamond pips for the air jumps left while a Window Washer is in the air.
  - It sits above the head, slides sideways off the other fighter, clamps on screen below the hint line, moves beside the head when a jump takes it to the top, and fades to a ghost when it has nowhere clear to go. The callouts step around it. It maps through `camera.mirror`, so the `?mirror=1` debug view still lines up.
- **Callouts and the hit counter** stack on the attacker's side under the hint line, else the other side, else the middle; banners (FIGHT, KO) take the first free slot. A happy accident found for the first time gets TECHNIQUE FOUND under them.
- **On the bodies** (`src/fx/status.js`, drawn on the FX emissive layer, which the compositor hides wherever a fighter is, so these show only as rims and glints around them): yellow-white arcs crackling off the joints while shocked; a pulsing yellow ring round each foot while rooted; a red halo and red light in hitstun that fade as the stun drains (thin and faint after a light hit, fuller after a medium one or three hits into a combo, the full pulsing halo after a counter); nothing for a guard that's just held (the guard mark in the fighter's color reads it), and a brief thin white-cyan glint arc on the guard side of a blocked strike, sized by the strike; stars circling the head and a wobbling violet ring while fainted (three, fewer as the faint runs down, and each head shake knocks one off, flying out the way the head whipped); an amber halo while armored and a flare when it absorbs; a white-cyan shield ring in front of a parry stance; a hot white halo and a harder body flash on a counter hit; a cyan ring kicked out under the feet when an air jump is spent; breath puffs under 35 stamina, plus sweat flicks and steam when nearly empty or fainted; a gold glint over the head when a happy accident lands. Tier 1 (`?tier=1`) drops the sweat, steam and the halos' outer pass.
- **Hit effects scale with the hit's weight** (`hitWeight` in `src/fx/status.js`, used by `main.js`; 2026-11-09, the owner: "Jabs can spark. But I don't think it needs the big ring effect"). Light (jab, low jab, the light kicks, anything under 9 damage that doesn't knock down): the contact flash and about 11 short, slow sparks, no ring, almost no shake. Medium (cross, body blow, 9+ damage that doesn't knock down): about 17 sparks, a small light, still no ring. Heavy (enders, launchers, knockdowns, splats, bounces, KOs): the full burst with the amber shockwave ring (`ring` on `fx.hit`, out to a radius of about 210 px on a KO), the smoke disc and the full shake and zoom punch, as before. A counter reads one step heavier, and its cyan and magenta double ring (`fx.counterFlash`, `scale`) shows on every weight because it's a signal, sized to the hit: about half size on a jab counter. Blocked hits get their own small set (next bullet). Shake on the release of the freeze is scaled by the same weight: peak camera offset on combo-test's jabs went from 15 px to 4, the cross from 17 to 10. Fighters never glow: all of this is on the FX layer around them.
- **Block effects scale the same way** (`blockWeight` in `src/fx/status.js`, used by `main.js`'s `BLOCK_FX` and `fx.guardSpark`; 2026-11-09, the owner: a block showed "a big blue shield effect, too much for something this common"). The big shield was the dashed cyan arc that status.js drew in front of every raised guard, brighter for all of blockstun, with a cyan light; it's gone. Holding guard with nothing coming now draws nothing on the FX layer (the guard mark in the fighter's color on the body still shows it). A blocked strike gets a small chevron glyph at the contact, a tiny cool-white core with a few short sparks kicked back at the attacker, a thin white-cyan glint arc on the guard side, and a faint light, all gone in 0.07 to 0.15 s. Light (a jab, a light kick: under 9 damage, no knockdown): the chevron at 55% size with two spark lines, 4 sparks, a 14 px glint, a little shake (trauma 0.015). Medium (a cross, a body blow, a sweep into down-back: 9+ damage or a knockdown): 75%, 6 sparks, 19 px, trauma 0.03. Heavy (an ender, a launcher, a splat, 14+ damage): the full chevron as before, 10 sparks, a 26 px glint, trauma 0.06, the old block shake. There's no ring and no zoom punch on any block (a block never releases a hit freeze), and the block sound was already scaled by the strike's damage (`sfx.block`). A parry keeps its PARRY flash, white ring and halo and the full chevron, a broken throw keeps the full chevron, and HELPDESK's stance ring is untouched. There's no guard crush in the game yet, so a future one should get its own signal instead of reusing these. `guard-test` phases 7 to 9 (a blocked jab, a sweep into down-back, 1,1,2,4 into a guard) show the three weights.
- The HUD and the status effects only read the sim (and its events, forwarded by `main.js` through `hud.event` and `statusFX.event`); they never write to it, so the sim stays deterministic.

### Camera

`updateCamera()` in `src/main.js` frames the fight the way Tekken does: two fighters in each other's face fill the frame's height. Everything is computed from the bodies, `sim.bounds` and the floors' data, never from a fixed stage width, so a wider stage needs no camera change.

- **Close range.** The view is the taller fighter's standing height (floor to the top of the head in the idle stance, from `rig._solve(STANCE)`, cached per body) plus 4 head heights of air over the head and 1 under the feet, where a head is `2 × rig.radius`. TEMP is 127 px tall with a 30 px head, which makes the view 277 world px tall and the zoom 2.60 on the 720 px frame; SECURITY (135 px, head 31) gives 2.46 and INTERN (121 px, head 29) 2.69. The feet sit 1 head over the bottom edge.
- **Apart.** The zoom eases out so both roots plus a leg's reach each side (0.95 of standing height, about 120 px) fit across the frame, down to the old wide framing (zoom 1) at full-screen distance. Between the two the vertical anchor blends from feet-at-the-bottom to the old center (the floor line less 120), so the wide shot is what it always was.
- **Nothing crops.** Every live body's drawn joints stay inside the frame: 28 px from the sides, 10 px from the bottom, and under the HUD strip at the top (`HUD_TOP` from `src/combat/hud.js`, the bars, names and move hints, plus 12 px). A jump or a launch pans up first and eases the zoom out only when the pan isn't enough. Two halves do this. `updateCamera()` steers its eased target from a prediction of where each body will be drawn, with a 48 px soft margin so it starts moving early. Then `fitCameraToDrawn()` runs in `render()` after `frameDraw()` has placed the frame's real drawing (the turnaround, snap fade and air catch-up) and clamps the camera to it. The prediction never forces anything, so a pose that jumps ahead of its drawing (the vault's drop, an air recovery) can't pop the frame.
- **Easing.** The zoom pushes in slowly (rate 3) and pulls out quickly (rate 9). A flying body is followed hard, as before. A new round cuts straight to the spawns instead of swooping back from the last round's floor.
- **Two floors.** A floor break or the follow-down frames both floors the same way, with the zoom allowed down to 0.85 as before. Horde frames the hero, the goon he's on and any other goon within 420 px of him.
- **Effects.** The zoom punch on a heavy hit and the KO slow-mo lean-in (12% for a finisher, 6.5% otherwise) are shares of the framing, so they read the same at any zoom, and neither pushes past the fit. Shake is scaled by `1.3 / zoom` so it's the same size on screen as at the old framing. Hitstop still freezes the camera. The view may still run 120 px past either wall. The far skyline is drawn at identity and placed by parallax, so `farDrawnW` caching is unaffected, and nothing in the arena or the fighters is a cached bitmap: at 2.6 everything is still vector-drawn at the layer's resolution.
- **Phones.** In portrait the 16:9 stage sits above the touch controls and frames exactly like a desktop. On a phone held sideways the gutters are narrow and the stick and the button cluster sit over the stage, so `touchInsets()` measures how far they reach into it (twice a second, from the layout) and the camera keeps the bodies between them. Up close nothing changes; apart, the zoom is lower so neither fighter stands under the buttons.

**Measured** (2026-11-09, Playwright Chromium at 1280x720, every frame outside hitstop): no drawn head or foot left the frame or went under the HUD strip in close range, mid range, full-screen apart, jump-in-test, juggle-test, Sky Spike, air-recovery-test, all three floor-break-test phases, wall-test, the Window Washer cross-up, horde-ai (3,000 to 4,000 frames), horde-floors-ai, ko, getup-test, stomp-test, ai-fight, ai-fight-2, ai-fight-3 and three attract bouts. Frame to frame (ai-fight, 3,000 frames), the zoom moves 0.02% at the median and 2.3% at the 99th percentile, and the pan 0.2 px at the median and 17.6 px at the 99th percentile. The only bigger jumps are the round-start cuts.

### Move list

A full command list for one fighter, like Tekken's (`src/flow/movelist.js`). It opens from the pause menu's MOVE LIST (the fighter you're playing) and from the character select's MOVE LIST (the fighter under the cursor), and F1 or pad Y opens it on either screen. It's an overlay, not a flow state, so the screen under it keeps its state (the game stays paused, the cursor stays put) and any screen change closes it. It covers the whole viewport rather than the 16:9 stage, so a phone held upright gets the full screen: the preview on top, the list under it.

- **Sections**, with a tab each: UNIQUE MOVES (SIGNATURE MOVES for TEMP, who has none), STRINGS, BASIC ATTACKS, SYSTEM and HAPPY ACCIDENTS. Unique moves are the character file's `moveList`, then any own move it doesn't name. Strings are the character's whole table (`c.strings`: the shared ones it keeps and its own, its own first with a UNIQUE chip), each with its hits, about how much damage it does from the first hit with combo decay, and chips for its payoff (knockdown, launch, wall splat, overhead, low...); dropped shared strings are named under them. Basic attacks are the shared button table with each move's height and payoff, struck through where one of the character's commands takes the input. System is the moves with no button of their own (walk, guard, low guard, crouch, parry, jump, run, throw break, get up, roll, air recovery) plus a row for a double jump or a wall jump. Happy accidents are the eight techniques (only those this character can do): found ones by name and buttons, the rest ??? with their hint.
- **All of it is read from the game's data** by `moveListOf()` in `src/combat/moveinfo.js`, which also holds the shared button table, the system rows and the notation, and which `site/data.mjs` imports for the fighter pages, so the two can't drift. A new character shows up with no change here.
- **The strings note.** The strings section opens with the rule people miss: *strings need every hit to connect (hit or blocked); if one whiffs, the next press is a mash and you botch*. Under it, a steady beat about 0.1 to 0.5 s between presses. Measured in the dummy scene with real key presses, TEMP's Neon Tornado landed all four hits with 60, 100, 150, 200, 300, 400, 500 and 600 ms between presses (three tries each) and dropped to 2 or 3 at 750 ms; the same presses from out of range whiffed the jab and botched.
- **Inputs** are written the way the HUD's move hints write them (→ toward, ← away, ↓, the button numbers), and after a pad press the numbers turn into the pad's own face buttons (1 X, 2 Y, 3 A, 4 B, or the PlayStation shapes), from `faceGlyph()` in `src/flow/controls.js`.
- **The preview.** Highlighting a row plays that move on the character's rig in the side pane, a string's presses chained at each recover key the way the fighter pages' move cards do (`site/rigs.js`), and replays it every second or so. System rows and accidents not yet found stand idle.
- **Controls.** Up and down move the highlight, left and right jump a section, confirm replays the preview, and back, Start, F1 or Y close it. On touch and with the mouse, tap a row, tap a tab, scroll the list, and CLOSE closes. The 30 second idle return doesn't run while it's open.
- **Online.** It isn't offered mid-match: online has no pause, and reading a list while your fighter stands there would hand the rival free hits. The pick screens have it (your first pick, and NEW CHARACTERS between matches), and it only covers your own screen there: the rival's game and any countdown carry on, and a match starting closes it. F1's quick strip still works in an online fight.

### Botches and happy accidents

Mashing doesn't just wait in the buffer any more. A strike pressed in the middle of another one, before that one is allowed to finish, fights it for the same body, and the fighter messes up.

**The rule.** Everything that legally carries on from a strike behaves exactly as before: a string's next press, a listed cancel (a move the CPU names), a throw pressed a frame after a jab or kick (1, then 3 a beat late), any press after a launch, knockdown or stomp connected (their recovery is cut short for the follow-up), any press while your juggle is in the air or on the wall, and anything in the last 8 steps (about 4 frames) of the recovery, which still buffers into the next move. Any other strike pressed during the startup, the active frames or the rest of the recovery is **mistimed** and botches. Throws, specials and character moves follow the same rule; holding a direction, guarding, jumping and moving never botch. In the air a second air attack pressed while the first is still swinging tangles you up (the jab on the way down comes only once the first has recovered) (after it connects, or just before you land, it buffers for the landing like before). A tangled fighter loses his presses until he's back.

**What happens comes from the forces involved.** The sim measures the strike that was out (which limb, which way it turns the body, startup, active or recovery, how fast the hips and the striking limb were moving, the lean, a glide or a lunge under it) against what the new press wants (its limb, its height, forward or not), and that picks one of five families:

| Family | Callout | Typical cause | What it looks like |
|---|---|---|---|
| Overbalance | OVERBALANCED | a forward strike on top of a lunge, a glide or a deep lean | lurches forward and catches himself with two steps, open the whole time |
| Spin-out | SPUN OUT | the body still turning one way (a spin kick, a rear-side strike) while the new strike turns it the other | the turn carries him round until his back is to you, a stooped beat, then round again; a hit while his back is turned is a counter |
| Trip | TRIPPED | a kick on top of a kick (worst with the same leg still up), a low on a kick | the feet cross and he goes down: a self-knockdown on the point simulation, then the usual getup |
| Flail | FLAIL | both arms at once | a weak, ugly double swing (it can touch, 2 to 3 damage, but never extends a combo) and he hangs there blowing |
| Whiff | WHIFF | the first strike mostly done | the new limb shoots out half-formed and hangs there, a long recovery |

A second air attack mid-swing is **TANGLED**: the body tumbles out of the air and lands in a heap. Every botch costs stamina (8 + 0.6 of the new move's price, more for two kicks, an ender under it or a harder botch, most for a flail; 20 to 40 in practice), and a botch with under 30 left empties the bar: he faints standing (never a trip, since a knockdown would wake him).

None of it is a canned animation. Each family is built on the spot from those numbers and the pose the body is in (`play('botch', { botch })` in `src/fighter/index.js`): play() blends into it from the current pose carried forward by its momentum, the trip and the tangle hand the body to the point simulation (`launch`), and the flail is a real, weak strike. Positions never teleport: a stumble's travel stops short of the other body and the wall, the root takes the step when the clip ends (or when a hit cuts it short), bodies stay solid, and sides follow the usual rules.

**Unpredictable, but the same every time.** The family comes from the forces, quantized to small integers (hip speed in 40 px/s steps, limb speed in 100 px/s steps, the lean in 5 degree steps, the phase), plus one draw from `sim.rng` for variety. That makes a botch feel random but exactly reproducible from the same state, which is what lets a player find the techniques, and it keeps rollback and every browser engine bit-identical. The new per-fighter state is plain unit fields (`botchKind`, `botchSev`, `botchShift`, `botchFwd`, `botchAt`, `activeAt`, `recoverAt`), which the snapshot copies; the generated clips ride the rig's `getState()` like any move. `NET_VERSION` is 7.

**Happy accidents.** A few presses that would botch, landing in a narrow window of a particular strike, come out as a hidden technique instead, with a HAPPY ACCIDENT callout: SCISSOR KICK, SUPERMAN PUNCH, PIVOT BACKFIST, FLASH KICK, HELICOPTER, FLYING TACKLE, CROSS KNEE and SPRING UPPERCUT. Everyone has all eight. They're strong (14 to 16 damage, launches, a wall splat, an unblockable tackle) and risky (long recoveries, little blockstun). They aren't in the move list until you find one; then the F1 move list shows it, the pause menu lists all eight as TECHNIQUES FOUND 3/8 (the rest as ???, each with a hint), and the character select shows the count. What you've found is kept in localStorage as `stick-fight-techniques`. A window's step count runs on the strike's own clock, so a hit's freeze holds it.

*Developer note:* the exact windows (which strike, which press, which steps) live in `ACCIDENTS` in `src/combat/botch.js`, and `?scene=accident-test` shows each one landing and the same press a step early and a step late botching instead. They're kept out of this section on purpose.

*Developer note:* the whiff, overbalance and spin-out mix the two moves per limb instead of playing a canned clip: the body carries on with the interrupted move (or the stumble) while the limb the new press wanted plays the new move's own keys part of the way, its elbow or knee trailing, and drags the torso a little after it (`src/fighter/limbBlend.js`). Trip, flail and the air tangle still use their own clips.

**The CPU.** It mostly holds a press that would botch until it's clean. The lower its difficulty, the more often it lets one go and mashes a button mid-strike on its own (about a third of strikes at INTERN's 0.2, a few percent at 0.7, never at 1.0 or for the showcase), so the bottom of the ladder shows the system off. Every CPU punishes a botch it sees, the better ones more often. The showcase (the attract demo and THE MANAGER) never botches but now and then presses into a technique's window for flavor.

**The switch.** On by default. BOTCHES: ON/OFF in the pause menu (from the next fight; kept in localStorage as `stick-fight-botch`), or `?botch=0` on the URL (`?botch=1` forces it on). Online, the host's setting rides the start message, so both sims play the same rules. With botches off the game is bit-for-bit the old one.

### Fundamentals

Four mechanics every character shares, built so the game is easy to learn and hard to master: each is one simple input with a timing or a read behind it. They're in the shared core (clips in `src/fighter/index.js`, frame data in `src/combat/frameData.js`, the rules in `src/combat/sim.js`), so every character has them with no character file changed.

**Getting up.** A knocked-down body lies there until its player picks (the `down` state). For the first 5 frames (`SQUASH_STEPS`) only a roll is read; after that:

| Input | What happens |
|---|---|
| nothing | he stands up by himself 1 second after touchdown (`DOWN_MAX`), so nobody can stall |
| up (held) | stands in place: the old getup, invulnerable while rising, at his hip on his own side |
| a fresh press away from him | **roll away**: 110 px back (less against a wall, down to a tuck in place), and he's still on his side |
| a fresh press toward him | **roll toward**: with the other fighter's root within 210 px of the hip (standing over the body, at its feet or just past them) and 60 px of floor behind him, it rolls **under him** and comes up 78 px past him, the one getup that changes sides; otherwise it rolls up to 80 px toward him and stops at least 130 px short, same side. With his back to the wall (no room past him) it's the short roll |
| 1 or 3 | **Wake Kick**: the knees curl up, then he springs forward along the floor onto his shoulders behind a straight kick rising into the shins of anyone standing at his feet. Mid, 8 damage, knockdown. Live about 9 frames after the press |
| 2 or 4, or down and any button | **Wake Sweep**: up on one hip, the lead leg scythes out flat along the floor. Low, 7 damage, knockdown. Live about 10 frames after the press, and it reaches a little farther |

A held direction never rolls, and away and toward go by the sides (Sides, below), so they mean the same whichever side of the screen he's on. The roll (`startRoll` and `rollStep` in `src/combat/sim.js`) first puts the body's root at its hip without moving the drawing (`rig.rebase`), so the ball turns about where the body lies and nothing jumps. The way the head points is a back roll (`rollBack`: the legs go up over the head), the way the feet point a forward roll (`rollFwd`: sit up, over the shoulder); both end crouched on the feet, he turns to face the other fighter (drawn as a turn) and stands (`rollUp`). The sim moves the body along the floor eased so it's already going its way on the first frame (half again the average speed, slowing to half), 40 steps for a roll and 48 for one crossing under him, aimed past wherever he stands now; the tumble clip is played at the rate that fills it. A roll is invulnerable and passes through bodies like any lying body, and the one crossing under him isn't stopped by him at all (`keepSides` and `keepOff` skip it). From the press to standing a roll takes about 0.6 s, standing up about 0.7.

A wake-up strike turns him to face the opponent first (a body lying with its head toward him turns over; the hip stays put), and springs the body forward 40 to 60 px, because a standing fighter can't stand closer than about 70 px to a lying body's hip from its feet side (Controls, Lying bodies). If he's standing closer than that on the head side, the body starts that much further back (`WAKE_SCOOT`), so the strike never carries the hip past him. It's invulnerable until it goes live, then it's a body on the floor until the clip's `stand` key: a hit there is a counter that puts him straight back down (and counts as that knockdown's ground hit). Then he rocks forward onto his feet through the getup's own stand-up keys, a little faster, and that rise is the price: both strikes are 17 to 24 frames minus on block (measured in getup-test), so a blocked Wake Kick (stand) or Wake Sweep (down-back) is a free punish. The strikes cost 12 stamina, which hardly matters after the knockdown refill.

The mixup runs both ways. The man standing over the body has to guess the height of a wake-up strike, or whether one is coming at all (a standing guard walks him back out of the sweep's reach, a crouching guard eats the kick), while the man on the floor chooses when to move as well as what.

**Sides.** Which side of the other fighter a body on the floor is on is fixed the moment it lands, by its hip (a launch, a throw or a cross-up may have carried it over him; `lieSide()`), and kept in both fighters' `home`, the same field that stops a standing man walking out the far side of a body. Two things change it: a roll that crosses under him, and him jumping over the body. Standing up, a wake-up strike, the 1-second stand and a roll away all rise on that side, facing him; the separation that parts a rising body from a man standing on it pushes each one toward his own side.

*Botches.* A press thrown in the middle of a wake-up strike, outside the last `BOTCH_GRACE` steps of its rise, is simply lost: there's no standing body to tangle. Presses made in the air on the way down are thrown away at touchdown, so a getup choice is always made on the floor.

*CPU.* Once per knockdown it plans a getup (`wakePlan` in `src/combat/ai.js`): it lies still for a random beat (longer and more varied the better it is), then stands, rolls away or toward, or wakes with a strike if he's standing close; the bottom of the ladder often just lies there until the clock stands it up. Away and toward go by the sides like a player's (`home`), and with the wall behind it and you standing near, a roll is toward you: under you, the way out of the corner. A strike starting at the body, or a whiff left open over it, changes the plan: a wake-up strike through it (more often the better the CPU) or a roll away (toward, under you, against the wall).

**Hitting a body on the floor.** A strike lands on a body lying on the floor only if its drawn limb touches the drawn body: the striking segment (elbow to fist, knee to foot) against the body's real lying joints drawn at their widths, within 3 px (`FLOOR_TOUCH`, `segGap()` in `src/combat/sim.js`), not the padded hurtboxes. So whether it lands can be read off the screen. What happens then:

- **A low** (frame data `height: 'low'`: the low jab, the low kick, the sweep, the characters' lows) that touches is that knockdown's **ground hit**: 55% of its damage (`GROUND.share`; the low kick does 3 to TEMP, the low jab 3, the sweep 5), counted in the combo it ends (so the decay and the soft cap apply), a 4-frame freeze with the hit spark and sound, and a jolt through the body (the hit reaction layered on the lying pose, a short crunch, and a 6 px pop). It can cancel into a jab or a cross for a meaty, as the old pokes did.
- **The Stomp** is still the best of them: down and 4 while the opponent lies on the floor within 175 px of your root (`stompOK`). Down and 3 there is the low kick (the stomp used to take both kicks, so no low kick ever reached a body).
- **Anything else that touches it** grazes: a high or a mid (the axe kick comes down on the shins), or any strike once that knockdown's ground hit is used. A graze is a 2-frame freeze, a 3 px flick, a small spark and a tap: no damage, no combo, no stamina refund, no cancel (`graze()`, the `graze` event). A strike that doesn't touch passes over as before.

Where each one reaches: the attacker always ends up at a body's feet (it lands feet toward whoever knocked it down), where the low kick and the stomp touch it; the low jab's fist is at crouch height, over the shins, so it touches only from the head side (over the body after a jump, or a body that landed past you); the sweep's foot falls about 30 px short of the feet from outside the stomp's range. The stomp: the rear knee comes up to the chest and the heel drives down onto the body as he steps in over the legs (a short `travel` that's allowed past the point where a standing body otherwise stops, though never past the hip). 9 damage, scaled by the character's damage and counted in the combo it ends, live about 10 frames after the press.

The mind game is in its recovery:

- **On hit** the body is pinned under the heel for 22 frames (`pin`, the `downPin` unit field), timed so the stomper is free a few frames before the fastest wake-up strike can land. Guard and the Wake Kick is blocked (and its rise punished); keep pressing buttons and it lands on you.
- **On a whiff** (a roll, a wake-up strike rising through its startup, a body that already stood up) it's about 25 frames of open recovery, and a wake-up strike thrown into its startup is a counter hit.
- **No loops:** every ground hit, the stomp and the lows alike, counts once per knockdown (`otgHit`), and the stomp can't be cancelled: a press in its recovery botches like any other. A body hit out of a wake-up strike counts as having taken its ground hit too. After that a low or a second stomp that touches the body only grazes it.

*CPU.* Over a body that stays down it stomps (more often the better it is), now and then low-kicks the feet (its ground hit), or waits over it with its guard up. After a stomp lands it guards the wake-up strike (20% at the bottom of the ladder, 80% at the top).

**In the air.** Three ways to act while falling, each with a timing to learn:

- **Air recovery.** Juggled or launched into the air, press any button once 18 frames have passed since the last hit (`AIR_TECH` in `src/combat/frameData.js`) and the body snaps out of the tumble into a tuck, rolls upright and lands on its feet with a short absorb (`airTech`, then `airLand`), facing the opponent, with a RECOVER callout. In the first 5 frames of that window it comes with a jump jab (RECOVER · JAB), so the timing is the skill. Each juggle hit, wall bounce and ground bounce restarts the wait, so a juggle that keeps going (the d+2 into jabs, Sky Spike, Neon Tornado) still connects. A press before the window locks the recovery out for 12 frames, and every press while locked keeps it locked, so mashing through a juggle never recovers. No recovery out of a wall splat, a throw, a floor break's fall down the stairwell, or your own trip or tangle.
- **Attack on a fall.** Dropping off the vault after a floor break (the clip's drop), a press is an air attack on the way down: the body lets go of the vault where it is and swings (`vaultFall`). The landing works like any air attack's. After an air recovery the usual one air attack is there too.
- **A second air attack.** One per jump is now two: once an air attack has recovered without touching anything, a press on the way down is a quick jump jab. A press while the first is still swinging is still TANGLED (Botches), and one that connected or was blocked keeps the old rule: the press waits for the landing and starts the ground string.

*CPU.* Juggled, it recovers more often the better it is (never at the bottom of the ladder) and closer to the jab window; after a whiffed air attack it throws the second jab when you're close; off the vault it swings at you below.

**The parry.** Every character can parry by **tapping** toward the opponent within 6 frames (`PARRY.win`, 12 steps, `src/combat/frameData.js`) before a strike lands: no damage, the PARRY flash and sound (the same event HELPDESK's stance uses), both freeze for 8 frames, and the striker reels for 16 frames (his string and anything buffered end), so a jab or cross punishes. Mistime it and you're just hit, because the tap moved you forward instead of guarding. The rules (`uParry` in `src/combat/sim.js`):

- **A tap, never a hold:** only a fresh press of forward counts, from idle, walking, crouching or a raised guard, on your feet and not fainted. It starts a 20-frame lockout (`PARRY.lock`) in which another tap doesn't count and restarts the lockout, so mashing forward never parries, and neither does the second tap of a forward dash. A tap within 12 frames of a button press doesn't count either (`PARRY.quiet`), so a hand mashing buttons and directions never parries by accident (the first build without this rule gave a random masher one parry every three matches).
- **Heights:** a standing tap parries highs, mids, overheads and air attacks (a jump-in is parried standing). Lows need the tap with down held (down-forward), and down-forward parries only lows, so it's a read either way.
- **Never a throw**, a trade, or a hit on a body that's already reeling, floored or in the air.
- **One strike per tap:** a multi-hit's next hit needs another tap, which the lockout won't give it, so PERFORMANCE REVIEW's hooks get one parried at most.
- HELPDESK's Ticket Closed is unchanged and much stronger: a stance that catches anything high or mid for its whole startup and hold, stuns for 46 frames and answers with its own reversal.
- *Botches:* a tap is movement, not a press, so it never botches; a tap during your own strike simply doesn't count.

*CPU.* Only above difficulty 0.55 (JANITOR up): it waits until a strike it saw coming (see the CPU's reaction time under Arcade flow) is about to go live and taps toward it (down-forward for a low), for up to 31% of strikes at difficulty 1.0 and 30% for the showcase. A strike faster than its reaction time can't be parried by it at all. The bottom of the ladder never parries.

- **The stairs** go both ways. A fighter on a flight stands on the line through the treads' middles, and the rig's pose is fitted to the steps (`slopePose()` in `src/combat/sim.js`): each foot near the floor goes onto the tread under it, its knee half as far, and a body lying down is laid along the slope on the treads' front edges (see Bodies on the floor below). Joints are the hurtboxes and hitboxes, so that fitting is the geometry the fight uses.
  - **Up** from the lower floor: walk past a foot. The lower floor is the room between the feet, and past a foot the ground is the flight going up; at the top you walk off the head onto the main floor.
  - **Down** from the main floor: at a stair head, hold **down and toward the flight** (down-forward toward the middle). Within 24px short of the head to 40px down the flight that steps you onto it, and for the first 60px down holding it keeps walking instead of crouching. A crouch at the head with no direction, or a crouch-walk toward the wall, stays upstairs. Walking along the main floor over the hole (the walking strip behind the rail) never takes you down; that's the only branch, because a flight's foot meets the lower floor's own end.
  - **Fighting on the steps:** stand, walk, run, guard, strike, jump, get hit, knocked down and lie there, get up, roll and wake up all work on a flight. The higher fighter has the height because his body is higher: a jab from above meets the head, a standing guard holds, a string carries the lower man down the steps. Lows follow the treads (a planted foot sits on the tread under it), so a sweep up the steps still takes the feet. Throws pull the victim along the slope; knockdowns and KO'd bodies lie along it; the stomp and the ground hits work on a body lying there. Two fighters can touch (hits, pushboxes, stomps, throws, the guard's threat) when they're on the same floor, on the same flight within 170px of height, on a flight and the floor at its foot within 170px, or on a flight within 70px of its head and the main floor (`sameLevel()`); anyone further down a flight is in the hole, under the floor the other one walks on. There are no walls on a flight (the walls are the building's ends), and the lying-body rules (stand over a body, never come out its far side) work along x as before.
  - *CPU.* When its opponent is on another level it takes the stairs (`src/combat/stairNav.js`): from the lower floor to the foot of the flight that makes the shorter trip and up it, from the main floor to that flight's head and down with down + toward, along a flight toward his height. ### Adding a character

Replace your character's file in `src/characters/` with a default export like `courier.js` and `security.js`. Nothing else needs editing unless you need a mechanic no hook covers. Then add a generic hook in `src/combat/sim.js`, read from frame data or `mechanics`, and document it here. The definition:

- `id` (the file's name: `intern`, `helpdesk`, `janitor`, `manager`, `accountant`, `windowWasher`), `name` (caps, on the HUD and the select screen), `tagline`.
- `color` (the body's neon), `altColor` (P2 in a mirror match), `accent` (the accessory and highlights). Neon arcade only: no monospace, no terminal look.
- `stats`, each relative to TEMP (all default 1 except health): `health` (out of 100), `walk`, `backWalk` (a share of the walk), `run`, `jump`, `dash` (multiplies every `travel`), `weight` (knockback taken: x by 1/weight, y by 1/sqrt(weight)), `stamina` (the bar's size), `regen`, `damage` (every hit he lands).
- `body`, for the rig (`createFighter({ body })`, `rig.setBody`): `scale`, `headR`, `upperArm`, `lowerArm`, `upperLeg`, `lowerLeg`, `lowerTorso`, `upperTorso`, `limbW`, `limbTip`, `torsoW`, `hipW` (defaults in `RIG`, `src/fighter/index.js`), `lean` (degrees of extra forward pitch), `stance` (degrees each leg spreads), and `accessory(ctx, joints, { scale, facing, color, accent, headR })`: a few strokes drawn over the head on the figures layer, so it's lit like the body. Hit and hurt radii and the contact surface scale with `scale` and the limb and torso widths, and a walk or run cycle plays at the rate that keeps feet planted at the character's speed. Watch the reach: a longer arm or a thicker fist wins the poke game outright (SECURITY's first build won three rounds in four on jabs and crosses alone).
- `cloth` (optional): a list of things that hang and swing (a tie, a lanyard and badge, an apron's hem, a ponytail, a tool on a lead), each a short chain the life layer swings (see Layout, The life layer, Cloth). An item is `{ draw, axis, at, off, dir, len, seg }` plus optional tuning, lengths in px at scale 1:
  - `axis: [a, b]` two joints for the body frame (down runs from `a` to `b`, forward is the facing side; `['head', 'neck']` for something on the head), `at` how far from `a` to `b` the anchor sits and `off: [forward, down]` px from there;
  - `dir: [forward, down]` its rest direction in that frame (an array of pairs gives each segment its own; a function `(J, facing) => { x, y }` computes it), `hang` 0..1 leaning it toward plain world down, `len` its length and `seg` its segment count (2 to 5 is right; `len` may be an array of segment lengths);
  - `hz` how firmly it holds its rest shape (2 is a tie), `damping` how fast a swing dies (0.2 loose, 0.45 heavy cloth), `air` drag in a run, `gravity`, `limit` the most a segment swings off its rest (radians), `side: 'front'` or `'back'` with `clear` px to keep it off the body line, `push` thigh joints that shove it aside, `end` a joint to pin the last point to (a cord between the hip and the hand), `kick` how hard a hit flings it, and `layer: 'back'` to draw it behind the far arm, the body and the head (the default draws it over the chest after the head and the accessory);
  - `draw(ctx, P, { scale, facing, color, accent, R, headR, pose, J })` gets the chain's points, anchor first. Without the life layer `P` is the rest shape. `src/fighter/cloth.js` has helpers for the strokes (`chainPath`, `ribbonPath`, `chainAt`, `chainNormal`, `coilPath`).
  A rigid part stays in `accessory`; only what hangs goes in `cloth`. A tie, for example, is one line: `cloth: [{ draw: tie, axis: ['neck', 'chest'], off: [3.6, 4], dir: [0.12, 1], len: 20.5, seg: 3, hz: 1.8, damping: 0.25, side: 'front', clear: 3.6 }]`. Drawn only, so it costs the sim nothing; flat color, never a glow.
- `life` (optional): how it moves, drawn only: `{ spring, damp, eye, breath, breathAmp, sway, swayHz, bounce, bounceHz, habits, laugh, ko }`, every field optional (see Layout, The life layer, Signatures). Give a new character at least its own numbers, so nobody moves identically.
- `dance` (optional, every character has one): `{ keys, blend }`, a looping clip built with the same `K`/`F` kit as the moves. The registry adds it as `<id>_dance` (a clip only: no frame data, so nothing can press it). When a match is won, the winner breaks into it the moment it's standing free on the ground in the sim's `match` phase (the `celebrate` state in `src/combat/sim.js`: no input, no movement) and loops it through the WINS card; never in horde. It's sim state like any clip, so both machines in an online match play it the same (`NET_VERSION` 14). Each fighter page shows it as a CELEBRATION card. The 18: TEMP's stunned double fist pump and brow wipe, INTERN's star jump and spin, HELPDESK's robot and reboot slump, COURIER's running man, SECURITY's folded arms and double flex, JANITOR's mop shuffle, THE MANAGER's tie, golf clap and point, ACCOUNTANT's finger count and tidy fist pump, WINDOW WASHER's wax-on circles, RECEPTIONIST's phone at the ear and hip sway, LAWYER's point and lapel strut, THE CEO's make it rain, HR REP's clipboard scribble and two thumbs up, SALES REP's finger guns, BARISTA's shaker, CHEF's kiss and stir, WELLNESS COACH's tree pose and bow, ELECTRICIAN's boogaloo wave. A spin ends on a 360° copy of the first key with `d: 0`, so the loop wraps without unwinding.
- `perfect` (optional, every character has one): the perfect round finisher (Arcade flow, Perfect rounds). `{ name, note, stamp, hand, hold, fly, slide, keys }`. `keys` is a clip built with the same kit, usually opening with `stoop()` and `lift()` from `src/characters/perfectKit.js`; it needs one key with `ev: 'grab'` (the body leaves the floor for `hand`, `'lHand'` or `'rHand'`) and one with `ev: 'release'` (it's thrown), and its last key is the pose he holds while the body slides down the glass. The registry adds it as `<id>_perfect` and warns when a key is missing. `hold` is how the body hangs from the hand: `'collar'`, `'ankle'` or `'carry'` (laid across the hands). `fly: { spin, flip, arc, wobble }` is whole turns of spin and of pancake flip (so it lands upright), the arc's height in px and a wobble. `slide: { dx, rate, chute, squeegee, blink }` is how it goes down the glass. `stamp` is the word stamped on the glass, `note` is the fighter page's line. A spin in the clip ends on a 360° key followed by a `d: 0` key at 0°, so the idle after it doesn't unwind. Each fighter page shows it as a PERFECT card: `PerfectView` in `site/rigs.js` plays the clip on a TEMP lying in front of him and draws the thrown body with the game's own `src/fx/perfect.js` (the card stands in for the screen), beside the finisher's name, the note and the stamp.
- `moves`: `{ name: { rig, frame } }`. Names are global: never reuse a shared or another character's name (registration throws). `rig` is a clip in the `MOVE_DEFS` format, built with `RIG_KIT` from `src/fighter/index.js`: `K(pose, ms, ease, ev)`, the IK helpers `F`, `L`, `leg`, the guard feet and hip `LF`, `RF`, `HIP`, the crouch `crouchP` and `CH`, and `base(name)` with `deepKeys` to start from a shared clip. A clip has `blend`, `limb` (the joint that carries the hitbox: `lHand`, `rHand`, `lFoot`, `rFoot`, `lKnee`, `rKnee`, `lElbow`, `rElbow`; button 1 is the lead hand, 2 the rear, 3 the lead foot, 4 the rear), `keys` with one `'active'` key (more for a multi-hit) and a `'recover'` key (the cancel window runs from it), and optionally `shift` (root travel when it ends), `air`, `chainFrom`. `frame` is a `FRAME_DATA` entry (`src/combat/frameData.js`; `addFrameData` fills what's left out): `limb` ('hand' or 'foot', for its radius), `damage`, `kb`, `hitstun`, `blockstun`, `hitstop`, `knockdown`, `height` ('high', 'mid', 'low', 'overhead', 'throw'), `cost`, `cancels`, `reach`, `flashR`, `juggle`, `splat`, `groundBounce`, `ender`, `callout`, `tc`, `react` (a reaction clip), and the hooks below. A frame-only entry (no `rig`) plays another clip through `anims: ['clip']` (SAME DAY's ender plays the slide).
- `commands`: `{ button, motion, move }`. Buttons '1' to '4', '1+3', '2+4'; motions '' (neutral), 'f', 'b', 'd', 'df', 'db', 'ff' (dashing: running or just after), 'run', 'rise' (released down), 'air', 'airDown'. A command replaces the shared move for that button and motion, and the most specific motion wins. A string continuation still beats a command.
- `strings`: `{ drop: ['SKY SPIKE'], add: [{ name, keys, moves }] }`. Keys are tokens ('1'..'4', 'd1'..'d4'; after the first, a plain token also matches its down variant), moves the move for each press, the last being the ender. Strings that share a prefix must agree on its moves. Registration warns about conflicts, including a sequence that collides through the down variant (1, 2, d3 is UPTOWN).
- `mechanics`: `airJumps` (extra jumps on a fresh jump press in the air; each refreshes the air attack), `wallJump` (a jump press within 34 px of a wall kicks off it, at most twice a jump), `airJumpClip` (the clip a double jump plays, 'jump' by default; its own clip gets the jump's landing beat too). After an air jump or a wall jump, an air attack doesn't home on the body (from that height the homing swung the leg back under him and lunged the hips past the defender), it connects only once the drawn limb touches the drawn body (2 px), and seating it never slides the defender under the attacker and out the far side.
- `ai`: `style` (the CPU's default personality: null, 'turtle', 'rushdown', 'grappler', 'aerial'; an arcade stage's or the demo's style wins) and `specials`: `{ move, min, max, when, chance, run, cooldown }`. In range [min, max] px and when `when` holds (a function `(me, opp, sim, dist)`, or 'standing', 'crouching', 'guarding', 'attacking', 'whiff', 'wall', 'far'), it's pressed with that chance (scaled by difficulty); a little short of range it walks in (runs with `run: true`). The CPU also runs the character's own strings through its usual string logic. A special can carry `plan(me, opp, sim, dist, toward, kit)` instead of a single move (then `name` keys its cooldown and `cost` is the stamina it needs): it returns the CPU's own list of acts, built with the kit (`move`, `attack`, `press`, `blockFor`, `closer`, `landed`, `chance`), for what one press can't do: a jump, a second jump, a wall jump, a press of a token so a string carries on (WINDOW WASHER's and INTERN's files are the examples). An act's `until` and `onlyIf` see `(me, opp)` every step, so a plan can react mid-air.
- `moveList`: `{ name, input, note }` for the select screen, the HUD's move hints and the top of the MOVE LIST (arrows and digits, e.g. '→→ 3'). The MOVE LIST adds any own move the list leaves out and every string on its own, so the list only needs the moves worth leading with.

**Hooks** (frame data fields the sim reads, `src/combat/sim.js`):
- `travel: { vx, at, ms }`: the body glides vx px/s (x the dash stat) from `at` ms into the clip for `ms`, stopping at the body.
- `armor: { hits, dmg }`: absorbs that many hits from the press until recovery, taking `dmg` of each (0.5 by default), with an ARMOR callout. Throws still take him.
- `parry: { heights, reversal, stun, callout }` (HELPDESK's counter stance): a strike of one of those heights (high and mid by default; never a throw or an air attack) landing in the move's startup or active frames is caught. The striker reels for `stun` frames (40 by default), PARRY (or the callout) pops, and the stance turns into the `reversal` move, which then hits the ordinary way. The stance itself never strikes (its own frame data is never tested as a hit), anything the parrying side had buffered or queued is dropped, and the reversal's step-in glide or `travel` waits out the parry's freeze instead of running down during it.
- `bothSides: true` (JANITOR's Mop Spin): the strike can land behind him. A hit sends the body the way the striking limb points from his root (not toward his facing), it seats on the body on that side, a hit behind makes that his side of her for the side-keeping rule (`home`), and the move is never re-aimed at a jumper or a juggled body, so the spin keeps its shape.
- `throw: true, grab: true, range, hold, noBreak` (a command grab): range px at the press, held `hold` frames, `noBreak` refuses the 1+3 break; `unblockable`, `splat` and the stairwell toss work as on a throw.
- `hits: n` (MANAGER's multi-hit): each later `'active'` key in the clip may connect again, up to n hits. `hitKey` (a unit field) counts the active keys; the first one never re-opens, since a strike can already land in the 45 ms before its key. `rush: { ... }` holds frame data fields for every hit but the last (PERFORMANCE REVIEW's hooks: light, no knockdown, `ender: false, callout: null`); the hit on the last active key is the move itself, so only it knocks down, calls out and scores as an ender. A blocked earlier hit doesn't bounce the attacker off (the rest still meet the guard). Every hit counts in the combo, so the decay and the soft cap apply hit by hit.
- A character's own move that opens one of its strings, named directly by the CPU (`ai.specials`), starts that string from its first key, the way a shared move starts one from its button (ACCOUNTANT's Fine Print).
- `height: 'overhead'`: a mid (a crouch can't duck or low-guard it, a standing guard holds) flagged as an overhead for the CPU and the move list.
- `lowInvuln: true`: lows pass under it from the press until recovery (a hop, a flying knee).
- `wallBounce: true`: near a wall the body bounces off it into a juggle (like WALL SPIN).
- `status: { regen, speed, ms, tag }` (HR REP's Write-Up) lands on the defender with a clean hit (not a block, a juggle or an on-the-ground hit); `selfStatus` (BARISTA's Espresso Shot) lands on the attacker at the move's first active key. `regen` multiplies his stamina regen, `speed` the rate his strikes' startups play at (the rig clock in the startup phase only, so every window downstream moves with it), for `ms`; a fresh one replaces the old, a new round clears both. Plain unit fields (`regenMul`, `regenEnd`, `regenLen`, `regenTag`, `speedMul`, `speedEnd`, `speedLen`, `speedTag`), and the HUD's overhead track shows the tag with a draining bar. A `status` that knocks down would be wasted (a knockdown refills the bar), so EXIT INTERVIEW's doesn't.
- `feint: { ms, into: { pressed: comesOut } }` (SALES REP's Cold Call): a press that resolves to one of the `into` keys (a button press through the commands, or a move the CPU names), made in the strike's first `ms` of startup, replaces it at once with the mapped move. It's a designed cancel, so the botch rule treats it as legal; after the window the same press botches. Map the follow-ups to frame-only versions with their own `travel` or `range` when the strike's lunge has already started (`sr_pitchFeint`, `sr_closeFeint`).
- `react: 'clip'` with a rig-only move (no frame data) as the clip: HR REP's `hr_shoved` backpedals the root 64 px (`shift`), so a standing hit can push him out of range without a knockdown.
- `throwCounter: { reversal, callout }` (LAWYER's Objection!, a sibling of `parry` for grabs): a throw or command grab (anything with `throw: true`, ESCORT included) landing on the move in its startup or active frames is caught. The thrower's grab is dropped (he's left standing, nothing buffered), the callout pops (with the parry's flash and sound), and the stance becomes its `reversal`, which is started and grabs him at once (the reversal's first key is the catch pose, since the grab freezes it there for the hold). Strikes aren't caught: a strike in the stance's startup is a counter hit. Pair it with `noHit` so the stance itself never strikes. A fainted fighter's stance catches nothing.
- `thrownClip: true`: the victim takes the shared `thrown` reaction (lifted, flipped over, slammed down) the way the plain throw does, instead of the generic knockdown (LAWYER's reversal).
- `backThrow: true` (RECEPTIONIST's Transfer): on landing, the throw sends the body back up over the thrower's head (kb.x away from where he was, kb.y up) on the point simulation, and it comes down on the thrower's other side: a real side change you watch happen, in one continuous arc. The victim keeps facing the thrower in the air (no mirror snap) and lands facing away; both `home` sides are cleared so the side-keeping rule doesn't drag the thrower after the body; the thrower doesn't ride after it. With a wall closer than 150 px behind the thrower there's no room, and it's a plain throw forward instead.
- `invuln: { at, ms }` (THE CEO's Golden Parachute): from `at` to `at + ms` ms after the press (on the move's own clock), strikes and throws pass through him. A throw that would have grabbed him in that window loses its lock (it can't grab him later in its active frames), and each strike or throw let through is logged once (`dodge`, for measurement; `dodgedId`, a unit field). It only exists while the move plays: a botch, a hit out of it or the recovery ends it, and pressing it mid-strike botches like anything else.
- `wake: true` (the shared Wake Kick and Wake Sweep): only from lying down (`down`), invulnerable until live, a lying body until the clip's `stand` key (`wakeUp`, a unit field: 1 lying, 2 rising), presses thrown into it are lost. Its clip starts from the knockdown rest pose and ends standing with a `shift` like the getup.
- `otg: true, pin: frames` (the shared Stomp): the strike lands on a floored body for its full damage (once per knockdown, like every ground hit), counted in the combo, never cancelled, and holds the body down `pin` frames (`downPin`).
- `noHit: true`: the move never strikes (its own frame data is never tested as a hit): a stance, a step out.
- `onJuggle: { ... }` (THE CEO's Hostile Takeover): frame data fields used when the hit lands on a juggled or splatted body. The same press is a launcher from the ground and, in the air, an ender with a big kb.x and a splat that carries the body across the floor into the wall.
- `blockPush: px/s` (LAWYER's Cross-Examination): how hard the attacker bounces off a guard (520 by default; a negative value steps him in), so a throw still reaches after a blocked tick.
- `owner` (set by registration): only that character can press it, by button or by the CPU naming it.
- `stance: { moves, hold, min, exit }` (WELLNESS COACH's Tree Pose): from the press until the clip's recovery key, a press of a button in `moves` (`{ 2: 'move', 3: ..., 4: ... }`) is that move, whatever the stick says, and it comes out at once (it never botches, and a held stance button plus another isn't read as a throw). With `hold` (a button, '1'..'4') let go after `min` ms the stance ends in `exit`; held, it lasts as long as the clip's hold keys, then recovers. The stance itself never strikes (nor does a move with `noHit: true`, like the step out), and a hit or a throw ends it like any strike (a hit in its startup is a counter). `stanceOnly: true` keeps a move to the stance: pressed or named outside it, nothing comes out. No new unit state: it reads `attackStart` and the held input.
- `shock: { frames, clip }` (ELECTRICIAN's Live Wire): on a standing hit, `frames` more of stun on top of the hitstun, scaled by the combo's stun decay (`COMBO_STUN`) and once per combo (`shockUsed`, cleared when a new combo starts), so it never loops. `clip` plays on the rig's additive reaction layer (`rig.react`), a jitter over whatever the reaction is doing; `shockT` (a unit field) runs with the stun for the HUD's SHOCKED and the crackle, and a `shock` event fires.
- `root: frames` (ELECTRICIAN's Ground Fault): on a standing hit, `rootT` (a unit field) holds `frames`, counted down once the hit- or blockstun is over: no walking, running, crouch-walking or jumping (the stick does nothing but guard: holding back still blocks, crouching still works, strikes still come out). A knockdown clears it.
- `flashColor: [r, g, b]`: the hit flash's color (`fx.hit`, read by `main.js`), with `flashR` for its size (CHEF's Flambé, orange and 92 px).
- The pose channel `ext` (RECEPTIONIST's phone cord, `src/fighter/index.js` and `src/combat/hitboxes.js`): px past the striking hand that something held reaches. Keys set it like any pose field (a pose without it has none, so every other clip is bit-for-bit the same). While it's over 4 the hitbox is only its far end (two thin circles at the full length and three quarters of it, out along the forearm), so the hand itself hits nothing up close; the accessory gets the pose (`pose` in its options) to draw the object out there. The reach the CPU measures (`sim.reachOf`) includes it.
- `ai.specials` entries with `reflex: true` are checked every step (when the CPU is idle, walking, guarding, crouching or in blockstun) instead of only when it decides, so a character can answer something with a few frames of startup: LAWYER's Objection at a grab starting up, THE CEO's Golden Parachute at a strike. The chance is per step, so keep it small.

The CPU's reach comes from measuring each character's clips on its own rig (`sim.reachOf(unit, move)`, keyed `id:move`), so a new body needs nothing extra. Rollback needs nothing extra either, as long as new per-fighter state lives in plain unit fields (the snapshot copies every one; `armorLeft`, `hitN`, `airJumpsUsed`, `wallJumps` and the travel `glide` are examples) and any math the sim depends on uses `src/combat/dmath.js` (drawing code like an accessory may use `Math`). A new sim field that isn't on a unit belongs in `SIM_SCALARS` in `src/combat/snapshot.js`. Test it the way courier-test and security-test do: a phase per unique move in `PHASES` in `src/main.js`, with the character as P1 in `SCENE_CHARS`.

## Multiplayer

Two players, each on their own phone or computer, fight online. One hosts a room and gets a four-character code and a share link (`https://askscottpierce.com/stick-fight/play/?room=K7QX`; the old `/stick-fight/?room=` links still work, see Site); the other opens the link or types the code. Codes skip 0, O, 1, I and L so they survive being read aloud.

**How it fits together.**

- `worker/index.ts`: `POST /stick-fight/api/rooms` makes a room and returns its code; `GET /stick-fight/api/rooms/<code>/ws?role=host|guest` opens the room's WebSocket. Each room is one Durable Object (hibernating WebSockets). It passes every message from one player to the other unchanged, and writes only its own `{"t":"sys"}` notices: welcome, peer joined or left, and errors (`no-room`, `full`, `busy`, `flood`). `GET /stick-fight/api/ice` returns `{ iceServers, ttl, turn }`: Cloudflare STUN plus TURN credentials good for an hour (see Hosting, Secrets), or public STUN only with `turn: false` when the Worker has no TURN key or Cloudflare doesn't answer. Each Worker isolate reuses one set of credentials for 10 minutes, so every set handed out has at least 50 minutes left.
- `src/net/link.js`: fetches `api/ice` as the link opens (2.5 seconds at most, else public STUN), then the WebSocket carries the WebRTC offer, answer and ICE candidates; game packets then go peer to peer over a DataChannel (unordered, no retransmits). With TURN, two phones on carrier NAT that can't reach each other directly still get a DataChannel, through Cloudflare's TURN servers. If the DataChannel isn't open within 5 seconds, packets go through the room's WebSocket instead (the relay); a DataChannel that opens later takes over. `link.candidate` says which path it took (`host` on the same network, `srflx` through a NAT, `relay` through TURN). `?relay=1` on the URL forces the WebSocket relay, and `?ice=relay` allows TURN candidates only, both for testing.
- **Limits** (`worker/index.ts`, `wrangler.jsonc`): per client IP (an IPv6 address counts by its /64), 10 new rooms a minute, 5 new crew rooms a minute, 30 WebSocket joins a minute (quick and crew rooms together) and 20 profile and sign-in calls a minute, counted per Cloudflare location (the sign-in caps per email and per hour are in D1; see Profiles and sign-in). Over the limit, `POST /rooms` answers 429 `{"error":"busy","message":"Too many tries from your network. Try again shortly."}` with `Retry-After: 60`, and a join gets a socket that sends `{"t":"sys","ev":"error","reason":"busy"}` and closes, so the page can say why; the menus show SERVER BUSY: TRY AGAIN SHORTLY. In a room, a message over 16 KB is dropped, and each socket gets a bucket of 480 messages refilling at 240 a second (about 4x a match's traffic); past it, messages are dropped, and after 1,000 drops the socket gets `reason: "flood"` and is closed. A room nobody has joined lasts 30 minutes; once its players have all left, its code stops working after 5 minutes (time to reload a page), and the alarm then deletes its storage and itself, leaving nothing behind.
- `src/net/rollback.js`: rollback netcode, GGPO style (see Rollback below). Both machines run the whole sim. Each runs its own input after a 2-frame delay (17 ms at 120 Hz), guesses the other player's input by repeating the last one it got, and keeps going; when the real input arrives and differs from the guess, it loads the state saved before that frame and re-runs the sim to the present, silently. Each side sends its input with every input the other side hasn't acknowledged, so a lost packet is covered by the next one. Every 30 frames, once a frame is confirmed (both real inputs in), each side hashes the sim (`src/net/hash.js`: positions, velocities, states, health, stamina, timers and every rig joint, by exact bits) and sends the hash; on a mismatch the host sends the guest its confirmed state and the guest loads it and runs back up to the present (see Resync below), and both log the fields that differ to the console.
- `src/net/codec.js`: an input is 11 bits (direction, jump, guard, crouch, run, the four limbs, and whether it came from the touch stick, which turns off double-tap run). An input packet is 15 bytes (with the match number) plus 2 per frame.
- `src/net/online.js`: the session (host, join, start, leave), the connection readout (bottom-left; centered under the timer on a touch screen: `P2P 13 MS · RB 3 · DELAY 2`, the round trip, how many frames the last correction re-ran, and the input delay; amber when relayed, plus a brief RESYNC after a resync, WAITING FOR RIVAL while the link can't keep up, and DESYNC only for a mismatch no resync has fixed in 3 seconds), and a lobby panel. The host is P1 (left), the guest P2; each plays the character picked on the pick screen in the room (`net.setCharacter(id)` sets where that screen's cursor opens and rides the `ready` message; the `pick` messages carry the live choice; the host's `start` message carries `chars: [host's, guest's]` and both sims build their fighters from it), in its own neon (a mirror match gives the guest the character's alt color; TEMP vs TEMP is white and orange as before). The HUD names them YOU and RIVAL after the character's name. Both screens show the same thing: the host is P1 on the left and the guest P2 on the right, the HUD's YOU bar on whichever side is yours (nobody's view is mirrored; two players in the same room see the same layout on both screens). When both are linked the host picks the seed and both start the `online` scene from frame 0. A match ends on a frame both machines agree on, and the room stays open for the next one (see Between matches below). If the other player leaves, nothing arrives for 15 seconds, the match has stalled for 20 seconds with packets still coming, or the two sides can't agree on the final state for 15 seconds, the match ends on both sides as CONNECTION LOST (the side that gives up tells the other with `{t:'lost'}`); with the arcade flow running that's its VERSUS ONLINE end screen (YOUR RIVAL LEFT, CONNECTION LOST), and on a `?scene=` page it's a notice and the demo.

**Starting a match.** The game's menus call the API on `window.__net` (also returned by `createOnline` in `main.js`): `net.host(opts)` resolves to `{ code, url }`, `net.join(code, opts)` (the menus pass `{ pickFirst: true }` for every room, quick or crew, so the host's first message is a `go` at match 0 and both open on the pick screen; a `?scene=` page's lobby panel leaves it off and starts at once), `net.leave()`, `net.roomFromUrl()` reads `?room=`, and `net.on('status' | 'connected' | 'start' | 'peer-left' | 'end' | 'desync', fn)`. `net.openLobby('menu' | 'host' | 'join', code?)` opens the built-in panel (keyboard, gamepad and touch: arrows or D-pad move, Enter or A presses, Esc or B backs out, and on the code box up and down turn the letter like arcade initials). `net.busy` is true while that panel is up, so the title screen shouldn't start a game then. The menu flow (`src/flow/`) owns the VERSUS ONLINE entry, its own HOST and JOIN screens and the `?room=` hand-off; it talks to `online.js` only through `src/flow/netApi.js` (`adaptOnline`), ignores its own input while `net.busy`, and gets the end of a match through the `endMatch` hook in `main.js` (which closes the lobby's notice in favor of the flow's screen).

**No mirrored view.** Online, nobody's view is flipped: both screens show the host on the left and the guest on the right. `?mirror=1` on the URL still draws any scene mirrored left-right as a debug view (`main.js` `syncMirror()`: the WebGL canvas gets a CSS `scaleX(-1)`, the HUD reads `camera.mirror`, `src/combat/input.js` flips `dx` at capture, and the stereo pan flips), but it never turns on by itself.

**Between matches (the room session).** `online.js` keeps the room's session after a match: the match number `n`, the tally, and the post-match and pick choices. The agreement rules are its, the screens the flow's.

- **The end of a match.** `rollback.js` notes the frame on which the sim first shows the result (`phase` becomes `'match'`; a correction that re-runs that frame finds it again). `online.js` halts the netcode 150 frames later (`END_HOLD`, 1.25 s of the WINS card; the sim's own 1.8 s hold would reseed and start another match) and ends the match once that frame is confirmed and both sides have said so with the same state hash (`{t:'end', n, f, h, e}`), so both machines stop on the same state and count the same result from `sim.wins`. The halt itself is the netcode's (`endHold`), so a correction that moves the result moves the halt with it. Two different end states are a desync like any other: the host's state goes to the guest and the guest says again; a word from before the other side's last resync (its epoch `e`) doesn't count against it. The finished netcode keeps sending its inputs and acks every 100 ms until the next match starts, so the other side can confirm its last frames even if the final packets were lost. Each side then hashes the final state; the host sends `{t:'result', n, tally, hash, f}` and the guest checks the hash and takes the host's tally if its own ever differs (it hasn't in testing).
- **The tally** counts matches (the host's best-of), host wins, guest wins and draws, plus rounds, for the room session; `net.tally` (and the flow's `hud().tally`, for the fight HUD) gives it from this side: `{ you, rival, draw, roundsYou, roundsRival, games }`. Each `start` message carries the host's tally too. **All time:** each browser keeps a random id (`stick-fight-pid` in localStorage) that rides the `ready` message, and a win, loss and draw count per rival id (`stick-fight-rivals`, the 30 most recent rivals). It's from this browser's side only and resets if either player clears site data. That's the record for quick rooms; in a crew match the record is the crew's, kept on the server (see Crew rooms), and this one isn't touched. The `ready` message also carries the player's name (`net.setName`), which the post-match and pick screens show in place of RIVAL.
- **Messages** (control JSON through the room, all carrying `n` so a late one from another match is dropped): `post` (each side's choice, `want`: rematch, chars or wait, its cursor, `focus`, and `poke` for a press that stops the auto countdown), `cd` (host to guest: a countdown's kind, `auto`, `agree` or `host`, and the ms left; the host's clock runs every countdown and starts the match), `go` (host to guest: NEW CHARACTERS), `pick` (each side's card and whether it's ready), `result`, `alive` (every 3 s between matches; 15 s without a word from the other side is CONNECTION LOST), `start` (`seed`, `chars`, `botch`, `n`, `tally`), `end` (the final state, above) and `lost` (this side gave up on the link). The netcode's own, tagged with the match number `m`: `hash` (`f`, `h`, the sender's resync epoch `e`), `dump`, `resync?` (the guest asks) and `sync` (the host's state in parts, below). Every input packet carries the match number (one byte) and every hash and desync dump the match number too, so nothing from one match can land in the next one's input history or hash check.
- **Pick first, tested** (2026-11-09, local Worker and Vite, Playwright, each player in its own Chromium): VERSUS ONLINE went straight to the online menu; a host remembered on INTERN and a guest from `?room=CODE&pick=security` both landed on the pick screen on those cards, saw each other's cursor, locked in (the host moved to HELPDESK first) and the match started HELPDESK vs SECURITY on both. A crew match (one desktop on the keyboard, one phone landscape by touch: tap a card, tap again) did the same with the crew's name in the subtitle. A guest closing the tab on the first pick screen gave the host YOUR RIVAL LEFT with HOST AGAIN; a guest's LEAVE ROOM there went to the online menu.
- **Without the menus** (a `?scene=` page, which only has `online.js`'s lobby panel) nobody sees a post-match screen, so the host's auto countdown starts the next match every time, as rematches did before.
- **Robustness.** Both pressing at once: the host decides, so crossed messages settle on the host's side (a guest's NEW CHARACTERS arriving after the host's REMATCH stops the agree countdown, puts the request on the host's screen, and the host presses again; a guest request that arrives after the host started is ignored, and the guest follows the `start`). A guest whose last frames confirm late still follows: a `start` or `go` that arrives before its match ended ends it and applies. A player who leaves, closes the tab or loses the connection between matches ends the room for the other with YOUR RIVAL LEFT or CONNECTION LOST. The room server only passes messages on, so none of this needed a Worker change, and a room stays alive while either player is connected. `NET_VERSION` is 22 (8 was the room session; 9 adds the name in `ready` and the crew match's `go` at match 0; 10 is the side-swap fixes and the stamina change, Controls, Sides and Stamina; 16 opens quick rooms on the pick screen too, which an older guest would sit through waiting for a `start`; 17 is resync, the agreed end of a match and the reach fix, Rollback below; 18 is the stamina refunds and the no-faint save on a connecting hit, Stamina and Faint; 19 keeps bodies on top of the floor, which moves the rig's joints (the hitboxes), Floors; 20 is the faint shake-off, Faint; 21 is getups by the sides and lows on a floored body, Getups; 22 is the perfect round finisher, Arcade flow, Perfect rounds): older builds get YOUR GAMES DIFFER: RELOAD BOTH.
- **Tested** with two browsers (Chromium host, Firefox guest) through the local Worker: an auto rematch, the guest asking for REMATCH and the host accepting, the guest asking for NEW CHARACTERS and the host overriding with REMATCH, crossed presses, NEW CHARACTERS with the guest on a gamepad and the host's START by touch, the guest leaving from the post-match screen, 32 idle seconds on it with both still in the room and the host then leaving, a guest vanishing on the pick screen, a stale room code and a version mismatch. Every match's hash checks and its final state hash matched on both sides, and both tallies agreed after every match.

**Crew rooms** (bookmarkable rooms for a group of friends). A quick room is a one-off four-letter code; a crew room is a permanent link the crew keeps, `https://askscottpierce.com/stick-fight/play/?crew=tuesday-crew-7k2qm` (links made before the game moved, without `play/`, are forwarded): the crew's name in lower case with dashes, then five random characters (no 0/o, 1/i/l), so it reads well and can't be guessed (28 million per name, behind the join limit). It's a query parameter rather than a path because the page is one static `index.html` with relative asset paths; `?crew=` needs no routing. While you're in the lobby the address bar holds that link (`history.replaceState`), so a bookmark taken there works; leaving the crew takes it off.

- **Making and joining one.** CREATE CREW ROOM asks for a crew name (3 to 20 letters, digits and spaces) and `POST /stick-fight/api/crews` makes the room. JOIN A CREW takes the code (the part after `crew=`) typed, or the whole link pasted. Opening the link does the same. Every crew you open goes to the top of your crew list (the profile's `crews`), and the online menu shows the three most recent.
- **The lobby** (`crewLobby`): the crew's name and link, COPY LINK and SHARE (the phone's share sheet where there is one), the standings (every member who has opened the link, most wins first: wins, losses, draws, your record against each of them, and each one's favorite fighter in its neon), the last three results, a status line, and PLAY (focused), ONLINE MENU and MAIN MENU. A square dot before each name is presence over the room's WebSocket: cyan HERE, amber READY (with a chip), pink PLAYING, hollow for a member who isn't here.
- **Playing.** PLAY means "I'll fight whoever else is ready" (it turns into CANCEL while you wait; a press while still connecting counts). When two members are ready, the one who pressed first hosts: the crew room claims a quick room code and tells each page its role, and both go to the pick screen (VS BOB, opening on each one's last pick in this crew, else the favorite) and then the match, all on the usual quick-room machinery (`online.js` with `pickFirst`). After each match the post-match screen works as always (rematch countdowns, NEW CHARACTERS, the host's final call); its LEAVE ROOM reads BACK TO CREW, and the other player's notice says ALICE WENT BACK TO THE CREW with BACK TO CREW. A rival who never connects sends you back to the lobby after 20 seconds (BOB DIDN'T CONNECT).
- **Winner stays on.** A third member who presses PLAY while two are fighting waits (PLAY THE WINNER). When that match ends with a winner, the crew room tells both players: the screen says YOU STAY ON or BACK TO THE CREW, WINNER STAYS ON · CAROL IS NEXT, the rematch countdown stops, and after 4 seconds both go back to the lobby, where the winner is ready at once at the front of the line and gets paired with the one waiting. - **Recording.** The host's page is authoritative, as in every online match: when a match ends it sends `{ t: 'result', match, n, winner, wins, chars }` over the crew socket. The crew room accepts it only from the member it made host of that match, and counts it once, keyed by `<match id>:<n>`, so a resend or a reconnect can't count it twice. It updates both members' wins, losses, draws, rounds and last pick, their play count per fighter (the favorite is the most played), the head to head for the pair, and the recent list, then sends the new standings to everyone in the lobby. The post-match screen shows CREW RECORD VS BOB 3–2 from the server instead of this browser's record.
- **What a crew room keeps** (its Durable Object's own SQLite storage, `worker/crew.ts`): the crew's name, slug and dates; each member's display name, first and last seen, wins, losses, draws, rounds won and lost, and last pick; play counts per fighter; head to head for every pair that has played (wins each, draws, rounds each); the last 300 matches (when, who hosted, who joined, the winner, rounds, fighters; the lobby shows the latest); and the matches it started (a day). Members are stored by a hash of the player id salted with the crew's slug, never the id itself. At most 50 members (a 51st gets THIS CREW IS FULL) and 80 open sockets.
- **Expiry.** Every visit and every result pushes the crew's expiry to 90 days out and re-arms its alarm; when the alarm finds it past due and nobody connected, it deletes all of the crew's storage and its alarm. A link to a deleted (or mistyped) crew shows NO CREW AT THAT LINK with ONLINE MENU and MAIN MENU. With `DEV_HOOKS=1` (`.dev.vars` only), `POST /stick-fight/api/crews/<slug>/dev-expire` expires a crew at once, for testing.
- **Messages** on the crew socket (JSON; `src/net/crew.js` on the page, which reconnects by itself after a drop and keeps a pending PLAY): from the page `hello {pid, name}` (first), `name`, `play {on, stay}`, `lobby` (back from a match), `result`; from the room `welcome {you}`, `state {crew, members, h2h, recent}` (to everyone, on every change), `match {id, code, role, rival}`, `rotate {match, stay, next}` and `error {reason}` (`no-crew`, `crew-full`, `full`, `bad-hello`, `flood`; the Worker's `busy`). **Determinism.** Netplay that runs the sim on both machines only works if both compute the same sim to the last bit. Run the same recorded input log through the sim in Chromium, Firefox and WebKit, with the builtin `Math.sin`, `cos`, `atan2`, `acos`, `hypot` and `pow`, and the rig's joints differ in the last bit by step 6 to 40 in every engine pair (the outcome still matched over 100 seconds, but every hash check would fail and the drift can flip a close hit). The sim and the rig now use `src/combat/dmath.js` instead: fdlibm's polynomials written with only + - * / and `Math.sqrt`, which IEEE 754 makes identical on every engine. With it, all three engines produce identical hashes on every step over 6000 steps, for a scripted bout and for a CPU-vs-CPU match. A match also starts with `sim.resetMatch({ fresh: true })`, which clears every leftover of earlier play (unit fields, the rig's jump arc and fall surfaces, the reach table the sim learns from hits): without it, each player's attract demo leaked in and the first hash check already failed.

**Rollback.** `src/net/rollback.js` keeps every frame's real inputs for both players in a 1024-frame history and moves the sim only through `simulate(frame)`.

- **Guessing.** A remote input that hasn't arrived is guessed as the newest one held. Before a frame runs on a guess, the whole sim is saved (`sim.saveState()`) into a ring of reused snapshots; frames run on real inputs need no snapshot. When a real input arrives and differs from the guess used for its frame, the next `advance()` loads the snapshot from before that frame and re-runs `simulate()` up to the present.
- **Depth.** At most 12 frames (100 ms) ever run on guesses (`MAX_ROLLBACK`); past that the sim waits for the other side (a stall: WAITING FOR RIVAL after 300 ms). Time spent stalled is given up, not banked, so a side doesn't burst ahead and stall again. The side that's ahead of the other (from the frame number in each packet and half the ping) runs 10% slow, 30% past 6 frames.
- **Delay.** The local input runs 2 frames late (17 ms). When half the ping plus the jitter is longer than the rollback window covers, the delay grows one frame a second (up to 10), and a second with stalls while not ahead adds one; it comes back down with headroom.
- **Save and restore.** `src/combat/snapshot.js` (`sim.saveState(reuse?)` / `sim.loadState(s)`) captures everything that feeds the next tick: the sim's fields (phase, timers, round, wins, card, callouts, combo, the horde and its ragdolls, the measurement log), the rng's state (`mulberry32` exposes `rng.state`), the reach table the sim learns from hits, the bounds, every unit field by value (its `prevJoints` points copied), each rig through `rig.getState()` / `rig.setState()`, and the arena state `tick()` mutates (its clock, door swings, the body pile and how settled each body is). The rig's state is its closure: the move and key list, the clock inside it, the pose and its velocity, the reaction layer, the springs, the point simulation (every point), the crossfade, the jump arc and landing ease, the fall surfaces and walls. What the rig mutates in place is copied both ways; poses, keys and move defs never change, so they're shared. A restore writes into the same unit and rig objects, so events, the HUD and the camera keep valid references. Saving takes about 20 µs, loading about 20 µs.
- **Effects.** The sim's events go through `sim.eventFilter` while the netcode runs it. The first simulation of a frame fires all its events and records them by identity (type, the units involved, move, callout text; position only for events with no unit, coarsely). A re-run of that frame fires only events beyond what already fired for it, counted, so two footsteps stay two: a hit the guess missed sparks and sounds up to 100 ms late, and nothing fires twice. An effect from a wrong guess isn't taken back (a stray spark or whoosh now and then). Sound, particles, lights, shake, callouts and the flow's scoring all hang off these events, so they all follow this policy; the HUD draws the current state, so a correction shows at once.
- **Hashes.** Only confirmed frames are hashed and compared: a frame is confirmed once both real inputs are in and no correction is waiting to re-run it. Every 30th frame's hash goes out then. The hash covers the rng's state and the reach table the sim steps strings in by (only the two fighters' entries, in any key order: each machine also keeps the reach of every character its demo has shown).
- **Resync.** A mismatch at a frame past the last resync makes the host send its confirmed state: the state after its newest confirmed frame (the live sim when nothing past it has run, else the snapshot saved before the next frame, which ran on a guess), as text (`src/net/state.js`), in 12,000-character parts over the reliable room socket (the room drops messages over 16 KB). A state is 17 to 34 KB: plain values, plus references the guest already has (its units and rigs, the controllers, the character definitions and the rig's clips, which the rig compares by identity), numbers JSON can't carry (`-0`, `NaN`, infinities, `undefined`) marked, and shared objects kept shared. The guest loads it and re-runs the sim from that frame to where it was, on the inputs it has (a guest that was behind jumps ahead), in a few milliseconds. Each resync bumps an epoch: hash checks of frames before the resync point stop counting, and the host ignores the guest's hashes from an older epoch, so a stale hash in flight doesn't set off another resync. The host sends at most one every 0.7 s and the guest asks (`resync?`) at most once a second. Both show RESYNC for 1.5 s. A host that diverged is still the authority: the point is that both screens show one fight.
- **Why it desynced** (2026-11-09, found with the harness below). A character's reach table (`reachSeen`, which a string's step-in and the auto guard read) was measured on the live rig the first time that phone showed the character: mid-demo, on the stairs, ragdolled or mid-jump, and at whatever x the rig stood (the last bits of `h.x - rig.x` depend on it). Two phones that had shown different demos got different tables, and the first step-in on a cancelled string came out a few last bits apart (`u1.vx: -176.9906555925494 vs -176.99065559255004`), which could grow into a hit on one screen and a whiff on the other. `calibrate()` now runs on the rig reset to one fixed state and spot, and puts the rig's own state back. The hash didn't cover the table, so nothing caught it until positions drifted; now it does. With no recovery, any desync ran apart for the rest of the match, and a match's end decided by one side's sim moved that side to the next match while the other was still fighting: the report from the car.
- **What was checked and is fine.** The draw never touches the sim: the harness hashes the whole sim (everything `saveState()` holds) before and after the life layer's joints are swapped onto each rig, drawn and swapped back, on 30 Hz, 60 Hz, 120 Hz and uneven frames, with no difference; `render()` now puts the real joints back in a `finally`, so an exception mid-draw can't leave the drawn ones on the rig, and `rig.sway` is outside `getState()` and the hash. Nothing outside the sim moves it during a match: `main.js` now runs the flow's per-frame hooks only on its `onlineFighting` screen while a match is on (its demo screens hold a KO card longer and start a new bout after one round, which on one phone would split the fights). No `Math.random`, `Date` or object iteration order reaches the sim (the life layer's randomness is its own). The celebration dance and the CPU dwell are in the sim or the CPU only. Long dropouts: each side stalls 12 frames past the other's last input, so neither runs far ahead, the backlog never passes 64 inputs a packet, and the 1,024-frame history is never at risk (a side whose inputs did fall out of it ends the match as CONNECTION LOST instead of playing on with a hole); stalls during a dropout no longer count as a long trip, so the input delay doesn't climb a frame per second of silence; and the 15 second timeout (it was 10) rides out a 10 second dropout as WAITING FOR RIVAL.

## Performance

The target is a steady 60 fps (every frame under 16.7 ms, no long-frame spikes) on a mid-range phone about three years old (iPhone 12 or 13, Pixel 6a class), and playable on a $150 Android. **No real phone was measured for this pass.** Every number below comes from this repo's harness on an Apple M3 Pro, and each table says which stand-in it used. `?perf=1` (below) is how to check a real phone.

### The overlay: `?perf=1`

`play/?perf=1` (also forwarded from the homepage) shows a small panel over the game, refreshed four times a second: the frame interval (p50, p95 and p99 over the last 10 s, and fps), the main-thread work inside the frame and its split into sim, 2D draw, GL and HUD, long frames (over 25 ms) a minute, the last and the worst rollback re-sim (ms and frames), the tier (and whether it's adaptive or pinned), the device pixel ratio, the HUD canvas's scale and the GL canvas's size. It's `src/perf.js`: a few `performance.now()` reads a frame into fixed typed-array rings, always on (so `window.__perf.summary()` works on any page), with no garbage per frame. `?tier=1|2|3` pins a tier, as before, and `?cache=0` turns the scenery caches off for a comparison.

### What changed, and why

- **The attract demo was choking on its own title.** The HUD drew every neon label with a live `shadowBlur`, and the attract card's 70 px "STICK FIGHT" with a 35-50 px blur that changes every frame made Chrome's canvas flush (`Canvas2DResourceProviderSharedImage::ProduceCanvasResource`) take ~3.1 s of every 4 s on the main thread: 10 fps at a 4x CPU throttle on the demo the owner saw at 20 fps on a Pixel 7. Neon text is now drawn once into a small bitmap at the HUD's resolution and stamped from then on (`neonText` in `src/combat/hud.js`: keyed by text, size, color, font, weight and glow in 0.05 steps, the 96 most recent kept, emptied when a web font finishes loading; text widths are cached the same way). Under any transform but the HUD's own, a label draws live as before.
- **Static scenery is cached** (`src/arena/cache.js`). Both floors of the building and the still part of its glow are drawn into world-space bitmaps covering the view plus a 50% margin, at the camera's zoom rounded up to the next 1/8 octave (never stretched, so they stay crisp at the close framing). They're redrawn only when the camera leaves the region, the zoom moves out of the bitmap's range (it draws a step ahead when zooming in, and serves until it's 30% bigger than needed), or the key changes (the mirror, the palette). The background goes straight to the compositor as a texture with a uv map (`fx.bgSource`, `u_bgMap` in the scene shader), so it's neither drawn nor uploaded per frame; a door swinging open (horde) draws it live for that second. The glow cache is one `drawImage` into the emissive layer, and what moves is drawn live over it (`drawBuildingEmissive(ctx, cam, lights, 'static' | 'live')`): the city's lit windows (now one prebuilt `Path2D` per tower instead of a hash and an occlusion test per window per frame), the flickering tubes, the vending machine and the fairy lights. A redraw is 0.3-0.5 ms of main thread at a 6x throttle (the first one, up to 37 ms); in a CPU fight it happens about every 1-2 s. The far skyline already had its own cache.
- **The scene shader walks the lights once.** The background light (with contact shadows), the figures' light and rim, and the haze were three loops over the same light array per pixel; they're one now (`lightAll` in `src/fx/shaders.js`), with the same sums, and the figure terms only where there's a figure.
- **The HUD canvas is no bigger than the screen it covers.** It was 2x the 1280x720 stage everywhere; a Pixel 7 held sideways shows the stage about 1920 device px wide, so it drew 2560 and shrank it. Now it's the stage's real width in device px (in 0.25 steps, 1x to 2x). The GL canvas stays 1280x720 (`createFX` sizes it), upscaled by the browser.
- **Less garbage.** Particle lighting (`fx.lightAt` per particle, over every light, with `Math.hypot`) and the particles' screen positions now write into scratch arrays: a 1v1 allocates 22 MB a second instead of 42 (Chrome's sampling heap profiler, `scripts/perf/profile.mjs --alloc`). What's left is spread thin: particle spawns, HUD color strings.
- **Rollback.** The reach table (~190 entries) was copied into every snapshot and rewritten by every active hit test; it now has a version that changes only when a value does, and snapshots of one version share one frozen copy (`touchReach` in `src/combat/snapshot.js`, the version kept off the snapshot in a WeakMap so a snapshot's content is still exactly the state). `saveState` 42 → 17 µs, `loadState` 43 → 18 µs. `segSeg`'s closure is hoisted, `penetration` walks index loops instead of destructuring iterators (100 pairs a step), and the CPU copies its opponent with `for...in` instead of `Object.assign`: a sim step 0.061 → 0.037 ms at the median (Node, M3, `scripts/perf/simbench.mjs`). Draw-only work (the life layer, cloth, `frameDraw`) runs from `render()` only, never from `sim.tick()`, so a re-sim never pays for it. The sim is unchanged: 48,000 steps of seeded CPU bouts hash the same as before, and `npm run netsim:proof` passes (0 of 5,587 restored steps and 0 of 4,320 resynced steps differ). No `NET_VERSION` bump.
- **Load.** The two faces are self-hosted (Latin subsets, 30 KB, `public/fonts/`, with their OFL files) and preloaded, instead of a render-blocking stylesheet from another origin, and the first frame no longer waits up to 2.5 s for them: the game draws at once and the HUD redraws in the real faces when they land. `__gauntlet.ready` still waits for the fonts, so captures see no load race. The bundle is all game code; the online code could be split out, but `main.js` uses it synchronously and that refactor wasn't worth the ~40 KB.
- **Tiers.** Each step down is a deliberate trade, not a blur (`TIERS` in `src/fx/index.js`): tier 2 drops the contact shadows and star streaks, keeps 20 lights and lights the scene at 0.8 of the canvas (64% of the pixels); tier 1 also drops the haze and the widest glow, keeps 12 lights, and draws the scene and the backdrop at half size but the fighters at 0.75, so their edges and outlines stay sharper than a uniform half-size tier. That costs about 10% more GPU work than the old all-half tier 1 (the SwiftShader table below), set in `TIERS[1].figScale`. Tier 2 used to be only 6% cheaper than tier 3; now it's about 25% cheaper. `scripts/perf/results/tiers.png` shows the three side by side.
- **The adaptive tier.** Phones still start at tier 2. Frame intervals are judged every half second; a window is slow only when both its average and its median miss ~55 fps, so one long frame (a GC, a cache redraw) never counts, and under ~33 fps it's very slow. One very slow window or two slow ones step down. A tier that failed becomes the ceiling (so it never flaps back and forth); a tier under the ceiling is climbed back to after 5 good seconds, and a failed tier gets one retry after a good minute. The window after a change is skipped while the canvases resize. Tested with a scripted per-frame load: 0 ms then 22 ms then a single 300 ms hitch then 9 ms. It stepped down from tier 3 to 2 within a second of the load and to 1 a second and a half later, the hitch changed nothing, and it never flapped.
- **What players get.** The `perf` analytics event (see Analytics) sends, once a session, the tier it settled on, where it started, touch or mouse, and the frame time p95 and p50. For example: `SELECT blob2 AS tier, blob4 AS input, count() AS n, avg(double1) AS p50 FROM stick_fight_events WHERE blob1 = 'perf' GROUP BY tier, input`.

### The life layer

What a puppeteer adds on top of the keyframes (`src/fighter/life.js`). The clips carry the acting; this layer makes the figure look like it's watching, carrying weight, getting tired, reacting to the other fighter and fidgeting like itself.

**Drawn only, always.** The rig's joints drive the hitboxes, and online play runs the rig on both machines and saves and hashes it for rollback. The life layer never touches any of that: `render()` in `src/main.js` takes the joints `frameDraw()` produced for this frame (the turnaround and snap fade already applied), and `life.apply(u, joints, sim, dt, floor)` returns a moved copy that only the drawing uses, the same way the draw smoothing works. `floor` is the floor guard (Floors, Bodies on the floor): the springs, takes and hit wave can push a joint a few px past where the clip put it, so the copy is fitted back on top of the floor before the cloth hangs off it. Its springs live in the layer, keyed by unit, and step once per rendered frame on real time, so a rollback re-running sim steps never runs them twice; they reset with the draw smoothing on a scene change and a new round, and stand still whenever the sim does (paused, a menu over the fight) and in a hit's freeze, so a contact frame still holds. The cloth's chains reach the rig's `draw()` as `rig.cloth` (one array of points per item), set before the draw and cleared after; it isn't part of `getState()`. `?life=0` turns the layer off for an A/B, and `window.__game.life.on` does the same live (`window.__game.life.extras = false` keeps the eyeline, springs and fatigue and drops the takes, signatures and habits).

- **Eyeline.** The head pitches toward what the fighter is watching: the other fighter's chest by default, the striking limb while a strike winds up at him (FRAME_DATA `joint`), the hip of a body on the floor, the loser after a KO. A critically damped turn of about 0.1 s, at most 12 degrees up and 15 down, and weighted by state (full in idle, walk, crouch and guard, about half in an attack, none launched, thrown or knocked down), so the clips' own head keys run the big moves. Think, then move: as his own strike starts (or a step), the head nods 7 degrees toward the target and leads by 2 px, gone in about 0.1 s.
- **Springs.** The head lags the neck on a loose spring (3.2 Hz, at most 3.5 px), the hands trail a little outside a strike (6 Hz, 2.5 px), and a hit sends a wave up the body after the freeze: the hips first, the chest 30 ms later, the shoulders and arms at 55 to 75, the head at 90, each a 150 ms push away from the attacker of 3.5 to 8 px by the damage. The feet never move.
- **Cloth.** Everything that hangs off a fighter is a short chain (`cloth` in the character's file, `src/fighter/cloth.js`). Each is 1 to 5 verlet points anchored on a joint and stepped at a fixed 240 Hz on real frame time: pulled toward the item's rest shape (the first link stiffest and the last at 55% of it, so the end lags the middle and a tie flips, then settles), damped against the anchor's own motion so a steady walk leaves it hanging, with a little air drag so a run streams it back, and gravity. Then follow-the-leader constraints hold every segment to its length (nothing stretches), no segment swings more than its `limit` off its rest direction, a `side` item stays clear of the body's line, so a tie never goes through the chest and a ponytail never through the head, and every point keeps its drawn thickness above the floor (`thick`, and `endR` for a badge or a cup on the end), so on a body lying down it lies along the floor and slides instead of hanging through it. The facing eases across a turn in 70 ms, so a turn swings a chain across the body instead of mirroring it. A hit flings it away from the attacker with a strength of 4 to 14 by the damage (the free end gets 38 px/s across and 14 px/s up per point of it), 1.7 times on a launch or knockdown and 2.2 times on the KO; it lands as the hit's freeze ends, and the freeze holds the chain like everything else. Launches, throws, falls and spins move the anchors fast, so they fling things on their own. Idle breathing barely moves them. A chain that jumps more than 120 px in a frame (a respawn, a reset) starts again at rest. Without the life layer (`?life=0`, the character select, the move list, the fighter pages' move cards, the build's roster sprites) the rig draws the rest shape.

What stays rigid, on purpose: hats and glasses (COURIER's cap, JANITOR's bucket hat, ELECTRICIAN's hard hat, CHEF's toque, ACCOUNTANT's and LAWYER's glasses, SECURITY's shades), headsets (HELPDESK, RECEPTIONIST), SECURITY's earpiece wire (clipped down the neck), THE CEO's tie (tucked into his jacket at the V) and watch, the aprons' bibs above the waist tie, WINDOW WASHER's harness straps and holstered squeegee, ELECTRICIAN's pouch, WELLNESS COACH's mat (strapped to the back), and anything held in a hand (HR REP's clipboard, SALES REP's phone, the RECEPTIONIST's handset, BARISTA's cup at the mouth).

- **Fatigue.** Under 40% stamina (all of it by 10%) the shoulders, arms and head heave with the breath, 1.6 breaths a second rising to 3.2, up to 4.5 px; the shoulders round forward 2 px, the guard's hands sag 9 px toward the belt (the elbows 4), and the head hangs 3.5 px. It eases in over a quarter second and out over 0.6 as the bar refills, only in idle, walk, crouch and guard; a faint keeps its own dizzy clip.

- **Takes.** Reactions to the other fighter, the way a Muppet's best moments are its reactions. The sim emits nothing new for them: the layer compares unit fields frame to frame (`botchAt`, `faintAt`, a strike going into `hitstun` with no damage taken, `sim.phase === 'ko'` with `sim.winner`). Each is a short keyed curve (smoothstep between keys, so every key is a still point and nothing steps) on the head, torso and arms, eased in and out by a weight, and plays only over idle, walk, crouch and guard: if the fighter starts a strike, gets hit or knocked down mid-take, the weight eases out in about 70 ms. One take at a time, and a new one starts at least 0.6 s after the last began.

| Take | When | What it looks like |
|---|---|---|
| double take | the other fighter botches | a beat, the head snaps toward them, back, a second smaller look (0.9 s); with `laugh`, a little shoulder shake of a laugh |

| flinch | this fighter's strike is parried | "oh!": the head pulls back, the shoulders come up, at 60% over the reel clip (0.5 s) |

| KO hold | this fighter wins the round | once standing, a held silhouette for up to 0.8 s (the kabuki *mie*): stand tall, chin up, guard lowered; THE MANAGER straightens his tie, the TEMP slumps, exhausted and relieved |

- **Signatures.** A character's `life` entry (in its file, next to `cloth`) tunes how it moves, so nobody moves identically. Every field is optional: `spring` and `damp` multiply the head and hand springs, `eye` how fast the eyeline turns, `breath` the breath's tempo (the fatigue heave included), `breathAmp` px of an everyday breath while standing, `sway` and `swayHz` an idle weight sway, `bounce` and `bounceHz` a light bounce on the toes, `habits` the idle habits it picks from (a name twice is twice as likely), `laugh` the laugh in its double take, `ko` its KO hold (`'tie'`, `'slump'`, or the generic stand-tall). The sway, bounce and breath play only while standing idle and ease in and out over a quarter second.
- **Habits.** Idle business, like a puppeteer's: after a randomized 1.8 to 3.6 s of quiet (standing idle, not fainted or tired, no take playing, the other fighter not attacking or jumping and more than 130 px away), a habit from the character's list plays (1 to 2.6 s), never the same one twice running when it has others, and the next waits 3.5 to 6.5 s more. Anything happening eases it out in about 80 ms. Habits move the guard a few px at most and never point a limb at the other fighter, so one never hides a guard or reads as a strike. The randomness is the layer's own (`Math.random`), never the sim's rng.

## Sound

Everything audio lives in `src/audio/`, and none of it uses sample files.

- `index.js` — the router: turns sim and fighter events into effects, pans each by the fighter's screen x (flipped by `gameAudio.setMirror(true)` in a mirrored view), and watches for whiffs (a strike reaching recovery without contact) and for which pool the music belongs in. It also owns the unlock on the first touch or key, M and N, the settings, and the phone's media player (`navigator.mediaSession`: "Stick Fight · <track>" with play, pause, next and previous). `window.__audio` exposes it for tests.
- `sfx.js` — the effects, built on the spot from a second of white noise and a few oscillators, each with a little random variation: whooshes by limb (a jab short and high, kicks longer and lower, the spinning enders longest), hits, block, counter (the heaviest hit short of an ender, a second snap and a bright ping), footsteps, landings, the jump, a body fall with a slide, wall splat, wall bounce, ground bounce, the throw (a grab rustle, then a slam), whiff, the exhale of a faint, ROUND and FIGHT, KO, the slow-motion ender KO (pitched down with a long tail of echoes), combo notes that climb with the hit count, the ender stinger, a horde goon down, the match end, and UI clicks. The multi-floor events have theirs too: a floor break (a crash, debris and a railing clanging), a knock per stair tread, a vault landing, and a floor-clear stinger. The perfect round finisher has the throw's whoosh, the body on the glass, the squeak down it and the unstick (Arcade flow, Perfect rounds). A hit is built in layers scaled by its weight (a jab light, a cross a bit more, a heavy, a counter, an ender or a KO the most): a crack of a few milliseconds for the contact, a punch falling through 300 to 120 Hz that a phone speaker can play, a sub thump into 40 to 55 Hz for headphones, a lowpassed tail, a crunch through a tanh shaper on the heavies, and on an ender or a KO a long low boom with a harmonic a phone can hear. A light hit stays about 0.15 s long so a fast string doesn't smear, and the combo note and the ender stinger come in 15 and 30 ms behind the crack, under it. Effects go through a compressor, a limiter and a soft clip, so a horde pile-up can't clip. Impacts (hits, wall splats and bounces, the ground bounce) skip the compressor on a bus of their own, because through it every hit came out at the same peak, a jab as loud as a KO. At most 16 sound at once (a new one steals the oldest of the lowest priority; footsteps go first). The effects have their own AudioContext.
- `music.js` + `tracks.js` — the soundtrack, written as [Strudel](https://strudel.cc) code and played through Strudel, after cf-quarry's player. Strudel is only imported the first time music turns on. A track plays its form twice, then the next track in the current pool starts. The pool follows the game: `menu` on the title and its attract demo, the mode select, the online menus, the high score tables, game over, initials and the ending; `fight` for a normal match, `horde` in horde mode (each cleared floor moves to the next horde track), `calm` in training (the dummy scene). The arcade flow names the pool for each screen through `gameAudio.setMusicPool(pool)` (null hands it back); without the flow (a `?scene=` page) the audio module guesses it from the sim four times a second, and `?scene=attract` plays `menu`. The music ducks under the KO stingers, the slow-motion ender, the floor break and FIGHT, and gets a quick sidechain-style dip under a hit (`music.pump`): none for a jab, so a fast string doesn't wobble it, about 2.5 dB for a cross, 6 for a heavy, 8 for a counter or a throw, and 10.5 for an ender or a wall splat, down in 10 ms and back in 0.1 to 0.35 s. A silent looping `<audio>` plays beside it so a phone shows its media player.
- `ui.js` — the sound panel and the speaker button. Its sliders are drawn in the DOM and driven by pointer events, because `touch.js` cancels every touchmove on the page.

The tracks share one theme (`THEME`, a four-bar call, answer, fall and rest), one set of changes (i VI VII i, iv VI VII v), and one form (an intro, `a` with the drums, `b` with the theme, a `drop` without drums, and `c` with everything). They use only Strudel's built-in synths and noises, so nothing is fetched to play them, and any of them pasted into strudel.cc plays there.

**Phones get a lighter mix.** On a touch device (`pointer: coarse`) `music.js` thins each track before playing it: supersaws drop to 2 unison voices and the distortion and bit-crush worklets come out, because the full mix was more than a phone's audio thread could keep up with alongside the game (choppy music). Reverb, delays and filters stay.

**The Strudel bundle.** `public/vendor/strudel.mjs` is the `@strudel/web` 1.3.0 bundle (850 KB), copied from cf-quarry with one marked patch (the cyclist looks 0.45s ahead instead of 0.1, so a long game frame on a phone doesn't make it skip slices of the music; search the file for "stick-fight patch"), with its license text beside it in `public/vendor/LICENSE`. It lives in `public/` so Vite copies it into the build untouched; `music.js` imports it at runtime by URL, because the bundle resolves its own helper files relative to itself. Its source is at https://codeberg.org/uzu/strudel.

## Practices

- No framework, no npm deps at runtime. Game modules stay plain `.js` (not `.ts`) so the capture tool's raw file server can load them; the Worker is TypeScript, built by wrangler. Playwright (global) only for `gauntlet/capture.mjs`.
- Logical resolution 1280x720, DPR-aware. Everything positions in logical pixels. The building is 2560 logical pixels wide; the camera shows part of it.
- Each module owns its folder and its demo page. Cross-module contracts live in `gauntlet/BRIEF.md`.
- Commit after every gauntlet round with the round number in the subject.
- The capture tool serves files raw, without Vite, so anything `main.js` imports has to be plain JavaScript; that's why `src/flow/` is JS with JSDoc types rather than TypeScript.
- Capture output is large (about 1.3 MB per frame). Delete capture folders when a round is done; `gauntlet/captures/` is gitignored.
